## 1. 지난 보고(8/4) 이후 끝난 것

### 1-1. 네 서비스 배포 완료

| 서비스 | 상태 | 확인 방법 |
|---|---|---|
| 서버(백엔드) | 2벌 · 서로 다른 가용 영역 | `/api/v1/health` HTTP 200 (양쪽 노드) |
| 화면(프론트엔드) | 2벌 | 주요 경로 4개 HTTP 200 |
| 캡차 | 2벌 | `/health/ready` HTTP 200 |
| 행동 판별 | 2벌 | 모델 적재 확인 · 캡차와 연동 동작 확인 |

밖에서 들어오는 경로 여덟 가지를 양쪽 노드에서 전수 확인했고 **전부 정상 응답**합니다.

### 1-1-A. ★입구 이중화가 실제로 동작하는 것을 인터넷에서 확인했습니다

8/4 보고에서 **"두 번째 로드밸런서는 대상에 아직 배포가 없어 오류 상태이며, 배포 뒤
정상이 되는지가 도메인 전환 전제 조건"** 이라고 말씀드렸습니다. **닫혔습니다.**

```
고가용성 그룹 주소 → 공인 IP 2개
  210.109.55.233   (가용 영역 2-a)
  61.109.239.102   (가용 영역 2-b)

★두 IP 를 각각 따로 호출했습니다
  210.109.55.233   주요 경로 4개 → 전부 HTTP 200
  61.109.239.102   주요 경로 4개 → 전부 HTTP 200
  HTTPS 인증서     ★양쪽이 동일한 인증서
```

★**주소 하나가 IP 두 개를 돌려준다는 사실만으로는 둘 다 살아 있다는 증거가 되지
않습니다.** 그래서 **각 IP 를 개별로 호출**해 확인했습니다. **한쪽 가용 영역이 정지해도
반대쪽이 같은 인증서로 같은 응답을 줍니다.**

### 1-2. 비밀값 관리 방식 정리

앱이 기동할 때 비밀 보관소에서 값을 직접 읽어 오도록 바꿨습니다. 쿠버네티스에는
보관소를 열 열쇠 두 줄만 남습니다. 값을 바꿀 때 **쿠버네티스를 건드리지 않아도 됩니다.**

넣기 전에 **모든 값이 실제로 통하는지 확인**했습니다 — 데이터베이스 접속, 저장소 조회,
메일 로그인을 각각 성공시킨 뒤에 등록했습니다.

### 1-3. 배포 계정의 권한 정리

배포 전용 계정이 갖고 있던 클러스터 전체 권한을 조회 권한으로 좁혔습니다.

★**다만 이 조치만으로는 충분하지 않다는 것을 확인했습니다.** 클러스터 권한 설정과
별개로 **클라우드 계정의 역할이 그 위에서 통과시킵니다.** 컨테이너 저장소에 이미지를
올리려면 그 역할이 필요한데, 그 역할이 있으면 클러스터도 열립니다.

→ **권한을 좁히는 길이 막혀 있어, 「자격증명을 아예 두지 않는」 배포 방식으로 바꾸는 것이
구조적인 해답입니다.** 설계는 마쳤고 도메인 전환 뒤에 진행합니다.

## 2. ★새로 만든 것 — 서비스 상태를 보는 장치

### 2-1. 없다는 것을 먼저 확인했습니다

기존 방식은 서버 다섯 대에 각각 측정 프로그램을 깔고 그 프로그램이 숫자를 보내는
구조였습니다. 새 환경은 **앱이 수시로 다시 뜨고 서버를 옮겨 다녀서 프로그램을 깔아 둘
고정된 대상이 없습니다.**

또한 카카오클라우드 기술문서에 다음과 같이 적혀 있는 것을 확인했습니다.

> *"카카오클라우드의 Kubernetes Engine은 기본 모니터링을 제공하지 않으며,
> 모든 모니터링 스택을 사용자가 직접 구축해야 합니다"*

가상 서버와 데이터베이스는 콘솔에서 그래프를 볼 수 있는데 **쿠버네티스만 그것이 없습니다.**

### 2-3. 운영 콘솔에도 같은 숫자를 연결했습니다

기존 운영 콘솔의 서버 상태 화면이 새 환경에서 두 가지로 어긋나 있었습니다.

```
① 서버가 2벌이 되면서 둘이 ★같은 칸에 자기 숫자를 덮어썼습니다
   같은 순간에 재 보니 한쪽 2.5% · 다른 쪽 1.2% — 새로고침할 때마다 값이 튀었습니다
② 컨테이너 안에서 잰 값이 ★앱이 아니라 서버 전체였습니다
   앱이 보고한 메모리 총량이 서버 용량과 정확히 같았습니다
```

측정 방식을 바꿔 해결했습니다. **화면과 그래프 코드는 그대로 두고 값의 출처만
교체했으므로, 운영자가 보던 화면은 달라지지 않습니다.**

## 3. 구축하면서 확인한 것

### 3-1. 안내 문서의 설치 파일이 4년 전 버전이었습니다

카카오클라우드 안내 문서가 가리키는 설치 파일이 **2022년 5월에 멈춰 있었습니다.**
지금 쓰는 클러스터 버전과 맞지 않아, 현재 유지되는 저장소에서 같은 버전의 파일을 찾고
**실제로 실행해 버전을 확인한 뒤** 그것으로 설치했습니다.

### 3-2. 저장 공간이 앱과 다른 건물에 만들어졌습니다

지표를 쌓을 디스크를 시험 삼아 만들어 봤더니 **앱이 앉을 자리와 다른 가용 영역에**
생겼습니다. 블록 디스크는 가용 영역을 넘지 못하므로, 앱이 반대쪽에 배치되면
**디스크를 붙이지 못해 기동하지 못합니다.**

만드는 시점을 **"앱이 자리를 잡은 뒤"** 로 바꿔 해결했고, 같은 시험을 다시 돌려
디스크가 앱을 따라가는 것을 확인했습니다.

### 3-3. 여러 벌이 동시에 기록하다 충돌했습니다

배포 직후 첫 주기에 수집기 넷이 같은 항목을 동시에 기록하려다 충돌해,
**그 주기의 수집이 통째로 실패**했습니다. 한 번 물러났다가 다시 기록하도록 고쳤고,
같은 상황을 재현해 확인했습니다.

## 4. ★데이터베이스 이중화 — 확인한 것과 못 한 것

### 4-1. 확인한 것

두 대가 **물리적으로 다른 서버**임을 서버 고유 번호로 확인했습니다.

```
쓰기·읽기를 받는 쪽   read_only=0 · 고유번호 ef47c0af…
대기 중인 복사본       read_only=1 · 고유번호 d541f877…
```

접속 주소의 구조도 확정했습니다. **포트가 역할을 가리키고, 호스트 이름은 어느 가용
영역에서 들어가는지를 가리킵니다.** 두 입구 어느 쪽으로 들어가도 같은 서버에 닿는 것을
직접 재서 확인했습니다.

장애 조치 중 주소의 IP 가 바뀔 수 있다는 문서 내용에 대해서는, **주소의 유효기간이
1초로 설정되어 있어 앱이 즉시 새 값을 따라가는 것**을 확인했습니다. 애플리케이션도
연결을 꺼내 쓰기 전에 살아 있는지 확인하도록 설정되어 있습니다.

### 4-2. ★아직 확인하지 못한 것

**가용 영역 하나가 통째로 정지했을 때 접속 주소가 어떻게 되는지는 확인하지 못했습니다.**
지금 앱이 쓰는 주소의 입구가 그 영역 안에 있어서, 그 영역이 정지하면 입구도 함께
정지합니다. 카카오클라우드가 그때 주소를 살아 있는 쪽으로 돌려 주는지는 **기술문서에
기재되어 있지 않습니다.**

돌려 주지 않는 경우 **설정 한 줄을 바꾸고 앱을 다시 띄우면 복구**되며, 몇 분이 걸립니다.
확인되는 대로 문서를 갱신하겠습니다.

### 4-3. ⬜자동 백업 설정을 확인해야 합니다

기술문서가 **"자동 백업 옵션을 활성화한 후"** 라고 기술하고 있어, 기본값으로 켜져 있지
않을 가능성이 있습니다. **켜져 있지 않다면 현재 백업이 없는 상태**이므로 우선 확인하겠습니다.

★**이중화와 백업은 서로 다른 문제를 막습니다.** 이중화는 서버 고장을 막고, 백업은
사람의 실수를 막습니다. 실수로 지운 데이터는 대기 중인 복사본에도 똑같이 지워지므로
이중화로는 되돌릴 수 없습니다.
