# ① Kubernetes 배포 권한 — **모든 경우에 필요합니다**

| 무엇을 | 어디서 | 소요 |
|---|---|---|
| `clusterrolebinding` 1개 생성 | **콘솔 아님 — `kubectl`** | 5~15분(첫 설정 포함) |

## 지금 상태

저희 서비스 계정은 apiserver에 **인증까지 통과**합니다. 계정을 인식하고 **`401`이 아니라 `403`** 을 돌려줍니다.

| 단계 | 저희 상태 |
|---|---|
| 네트워크 도달 | ✅ VPC 안 서버에서 443으로 붙습니다 |
| 인증 (누구인지) | ✅ `catchap-…@kc.serviceaccount.com` 으로 인식됩니다 |
| **인가 (무엇을 할 수 있나)** | ❌ **권한이 하나도 없습니다** |

```
클러스터   catchap-cluster-prod  (326e4ae3-5981-41b6-a793-2ed0dc1278fc)
버전      1.33   ·  노드 풀 catchap-nodpol-prod  ·  워커 2대
엔드포인트  https://04c32b21-7670-4cd9-b970-aecc2f648343-internal.ke.kr-central-2.kakaocloud.com:443
                                                     ^^^^^^^^  프라이빗
```

**즉 kubeconfig 파일이 필요한 게 아니라 권한이 없는 상태입니다.**

## 왜 강사님만 하실 수 있나

`clusterrolebinding` 생성은 **인가의 최상위 작업**이라, 자기 자신에게 주려면 이미 권한이 있어야 합니다.
지금 그 권한을 가진 것은 **클러스터를 생성하신 계정**입니다
(쿠버네티스는 클러스터 생성자를 `cluster-admin`으로 자동 등록합니다).

그리고 **Kubernetes는 전용 IAM 역할이 프로젝트 역할 25개 목록에 아예 없어** 콘솔로도 안 됩니다.
→ **어떤 프로젝트 역할을 주셔도 이 항목은 대체되지 않습니다.**

## 왜 `edit`이 아니라 `cluster-admin`인가

처음에는 `edit`으로 요청드리려 했으나 **그러면 배포 단계에서 다시 부탁드려야 합니다.**
[인그레스 컨트롤러 배포](https://docs.kakaocloud.com/service/container-pack/k8se/how-to-guides/k8se-ingress) 문서의 배포 명령이 이렇습니다.

```bash
kubectl create namespace ingress-nginx
kubectl apply -f https://raw.githubusercontent.com/kakaoenterprise/kakaocloud-tutorials/\
refs/heads/k8se-public-guides/controller-v1.12.1/deploy.yaml
```

이 YAML은 `Namespace` · `ClusterRole` · `ClusterRoleBinding` · `IngressClass` 등
**클러스터 범위 리소스**를 만듭니다. `edit`은 **네임스페이스 안 리소스만** 다뤄 여기서 막힙니다.

**다른 조에는 영향이 없습니다.** 프로젝트 역할과 달리 **Kubernetes 권한은 이 클러스터 안으로만** 미칩니다.
`catchap-cluster-prod`는 프로젝트에 하나뿐이고 워커 2대 모두 `Team1-VPC`에 있어 **1조 전용**입니다.
2조·3조는 클러스터가 없어 이 권한이 그쪽 자원에 닿지 않습니다.

## 클러스터 접속 방법 — 처음부터

### 0. 전체 그림 먼저

카카오클라우드 Kubernetes는 **표준 `kubectl`을 쓰지만 인증 방식이 다릅니다.**
kubeconfig 안에 비밀번호나 토큰이 들어 있지 않고, **`kic-iam-auth`라는 카카오클라우드 전용
실행파일이 IAM 액세스 키로 매번 토큰을 발급**해 apiserver에 넘깁니다.

```
kubectl  ──(exec)──►  kic-iam-auth  ──(IAM 액세스 키)──►  iam.kakaocloud.com
                            │                                    │
                            └──────── 토큰 ◄─────────────────────┘
                            │
kubectl  ──(토큰)──►  apiserver (…-internal.ke.kr-central-2.kakaocloud.com:443)
```

**준비물 4가지**

| | 무엇 | 어디서 |
|---|---|---|
| 1 | `kubectl` | Kubernetes 공식 배포 |
| 2 | `kubeconfig` 파일 | 콘솔에서 다운로드 |
| 3 | `kic-iam-auth` 실행파일 | 같은 콘솔 팝업에서 다운로드 (버전 0.1.2) |
| 4 | **IAM 액세스 키** (ID + 보안 키) | 강사님 계정의 것 |

**그리고 실행 장소가 중요합니다.** 아래 1번을 먼저 읽어 주십시오.

### 1. ★실행 장소 — 사무실 PC에서는 안 됩니다

이 클러스터의 API 서버 엔드포인트에 **`-internal`** 이 붙어 있습니다.

```
https://04c32b21-7670-4cd9-b970-aecc2f648343-internal.ke.kr-central-2.kakaocloud.com:443
                                             ^^^^^^^^
```

**인터넷에서는 DNS도 안 풀리고 도달도 안 됩니다.** 같은 VPC 안에서만 됩니다.

**미리 확인해 보는 방법** — 어느 장비에서든 아래를 실행해 보시면 됩니다.

```bash
nslookup 04c32b21-7670-4cd9-b970-aecc2f648343-internal.ke.kr-central-2.kakaocloud.com
```

- 사설 IP(`10.0.x.x`)가 나오면 → 그 장비에서 하실 수 있습니다
- 응답이 없거나 타임아웃 → VPC 안에서 하셔야 합니다

### 실행 장소 3가지 중 편하신 쪽으로

| | 방법 | 강사님 수고 | 저희 준비 |
|---|---|---|---|
| **(가)** | **저희 점프서버를 쓰신다** | SSH 접속 후 **키만 붙여넣고 명령 1줄** | `kubectl`·`kic-iam-auth`·kubeconfig **미리 설치·배치** |
| (나) | 강사님 VM에서 하신다 | 준비물 4개 직접 | 없음 |
| (다) | 강사님 키를 저희에게 주신다 | 없음 | **권하지 않습니다** — 강사님 자격증명이 저희 서버에 남습니다 |

### 2. 방법 (가) — 저희 점프서버를 쓰시는 경우 ★가장 간단합니다

**말씀만 주시면 저희가 아래를 미리 다 해 두겠습니다.**

```
서버      210.109.82.148   (Team1-VM-1-N · 사설 10.0.1.241 · Team1-VPC_public_sn1)
준비      · 강사님 전용 리눅스 계정 생성 (sudo 없이, 홈 디렉터리만)
          · kubectl 설치
          · kic-iam-auth 설치 + PATH 등록
          · kubeconfig 배치 (~/kubeconfig.yaml)  ← 액세스 키 칸만 비워 둠
          · SSH 접속용 키 전달 또는 강사님 공개키 등록
```

**강사님이 하실 일 — 3단계, 3분**

```bash
# ① 접속
ssh {강사님계정}@210.109.82.148

# ② 액세스 키 두 줄만 채우기 (파일은 이미 놔뒀습니다)
nano ~/kubeconfig.yaml
#     OS_APPLICATION_CREDENTIAL_ID       ← 액세스 키 ID
#     OS_APPLICATION_CREDENTIAL_SECRET   ← 보안 액세스 키

# ③ 확인하고 권한 부여
kubectl --kubeconfig=~/kubeconfig.yaml get nodes

kubectl --kubeconfig=~/kubeconfig.yaml create clusterrolebinding catchap-ops-admin \
  --clusterrole=cluster-admin \
  --user=catchap-ops-kc-sfacspace05@kc.serviceaccount.com

# ④ 끝나면 키가 든 파일을 지워 주십시오
shred -u ~/kubeconfig.yaml   # 또는  rm ~/kubeconfig.yaml
```

★ **강사님 IAM 키가 저희 서버에 남지 않도록**, 작업 후 ④를 해주시면 됩니다.
   저희가 그 계정을 지우는 것으로 마무리해도 됩니다. 말씀해 주십시오.

### 3. 방법 (나) — 강사님 VM(또는 다른 VPC 내부 장비)에서 하시는 경우

전체 절차입니다. [kubectl 제어 설정](https://docs.kakaocloud.com/service/container-pack/k8se/how-to-guides/k8se-kubectl) 문서 기준입니다.

#### Step 1. kubectl 설치

이미 있으시면 건너뛰십시오. 없으시면 (Ubuntu 기준)

```bash
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl && sudo mv kubectl /usr/local/bin/
kubectl version --client
```

#### Step 2. kubeconfig 다운로드

```
콘솔 > Container Pack > Kubernetes Engine > 클러스터
  → catchap-cluster-prod 클릭
  → 우측 상단 [kubeconfig 파일] 버튼
  → 팝업의 [kubeconfig 파일 다운로드] 버튼
```

`kubeconfig-catchap-cluster-prod` 형식으로 저장됩니다. 환경 변수로 잡아 두면 편합니다.

```bash
export KUBE_CONFIG="{다운로드경로}/kubeconfig-catchap-cluster-prod.yaml"
```
```bat
:: Windows 명령 프롬프트
set KUBE_CONFIG={다운로드경로}\kubeconfig-catchap-cluster-prod.yaml
```

#### Step 3. 카카오클라우드 인증 클라이언트(`kic-iam-auth`) 설치

**같은 팝업**에 OS별 다운로드 링크가 있습니다(현재 버전 **0.1.2**).
Linux x86_64 / Linux ARM64 / Linux i386 / Windows x86_64 / Windows i386 / Mac x86_64 / Mac ARM64.

```bash
# 파일명을 반드시 kic-iam-auth 로 바꿔야 합니다 (kubectl이 이 이름으로 실행합니다)
mv {다운로드파일} kic-iam-auth
chmod +x kic-iam-auth

# PATH 등록 — 둘 중 하나
export PATH="{디렉터리경로}:$PATH"
sudo cp kic-iam-auth /usr/local/bin/
```

★ **Windows에서는 백신(Windows Defender 등)이 이 파일을 감지해 실행을 막거나 자동 삭제할 수 있습니다.**
   그 경우 **백신의 허용 목록에 등록**해야 합니다. (문서에 명시된 주의사항입니다)

#### Step 4. kubeconfig 에 IAM 액세스 키 입력

내려받은 `kubeconfig` 파일을 열어 **`users > user > exec > env`** 에 아래 5개를 넣습니다.

### 4. 잘 안 될 때 — 증상별 원인

| 증상 | 원인 | 조치 |
|---|---|---|
| `Unable to connect to the server: dial tcp: lookup … no such host` 또는 타임아웃 | **VPC 밖에서 실행** | 위 1번 참고. VPC 안에서 실행 |
| `error: exec: executable kic-iam-auth not found` | PATH에 없음 | Step 3의 PATH 등록 또는 `/usr/local/bin` 복사 |
| Windows에서 `kic-iam-auth`가 사라짐 | **백신이 삭제** | 백신 허용 목록에 등록 |
| **`401 Unauthorized`** | **인증 실패** — 액세스 키 ID/시크릿이 틀렸거나 프로젝트가 다름 | Step 4의 두 값 재확인 |
| **`403 Forbidden`** | **인증은 됐고 권한이 없음** | **정상 반응입니다.** 저희 계정이 지금 이 상태입니다 |
| `Error from server (AlreadyExists)` | 같은 이름의 바인딩이 이미 있음 | 아래 확인 방법으로 내용을 보시고, 맞으면 그대로 두시면 됩니다 |

★ **`401`과 `403`의 구분이 중요합니다.** `403`이면 **접속과 인증은 성공**한 것이고 권한만 없는 것입니다.
   저희가 "인증은 되는데 권한이 없다"고 말씀드리는 근거가 이것입니다.

## 왜 필요한가

### (1) 포트가 `443`이면 실패합니다

문서상 **HTTPS 리스너에는 대상 그룹 프로토콜이 `HTTP`만 가능**합니다(현재 설정이 맞습니다).
즉 **로드밸런서가 TLS를 종료하고 노드에는 평문 HTTP를 보냅니다.**
그런데 대상 포트가 `443`이면 인그레스 컨트롤러는 그 포트에서 TLS를 기대하므로 어긋납니다.

```
지금     LB(TLS 종료) → 평문 HTTP → 노드:443   ✗ 어긋남
맞는 것   LB(TLS 종료) → 평문 HTTP → 노드:80    ✓
```

### (2) ~~워커가 2대인데 로드밸런서가 1대만 봅니다~~ → **넣을 수 없음이 확인됨**

```

워커 2   10.0.6.202   private_sn6 (10.0.6.0/24)   kr-central-2-b   ← 대상 목록에 안 나옴
```

**로드밸런서가 `kr-central-2-a` 단일 가용영역에 있어 다른 영역의 인스턴스는 대상이 될 수 없습니다.**
자세한 내용은 위 정정 상자를 봐 주십시오. **이 항목은 요청에서 뺍니다.**

이 경우 컨트롤러가 **노드의 80 포트를 직접 점유**하는데, 로드밸런서에서 거기로 들어오는 트래픽이 막힙니다.

## ★ 건너뛰셔도 되는 이유

**NodePort 대역(30000-32767)이 이미 열려 있습니다.** 저희가 인그레스를 `30080`으로 띄우면
보안 그룹을 바꾸지 않고도 됩니다.

> **③을 하시면** → ②의 포트를 `80`으로.
> **③을 건너뛰시면** → ②의 포트를 전부 **`30080`** 으로 읽어 주십시오.
> **어느 쪽이든 지금의 `443`은 틀립니다.**

80을 여는 쪽을 택했습니다 — 카카오클라우드가 제공하는 표준 YAML을 손대지 않아도 되기 때문입니다.
(NodePort `30080`으로 우회하는 방법도 있었지만 표준 YAML을 고쳐야 합니다.)

## 만들어 주실 계정의 역할 — ★변경 불가라 한 번에 맞춰야 합니다

```
catchap-ops
    프로젝트 리더 (Reader)
    Secrets Manager 매니저 (Manager)
    KMS 사용자 (User)
    Object Storage 매니저 (Manager)
    Alert Center 프로젝트 매니저 (Manager)
    Codeflow 매니저 (Manager)
```

| 역할 | 왜 필요한가 |
|---|---|
| **프로젝트 리더** | VPC·인스턴스·로드밸런서·Kubernetes·MySQL·MemStore·Monitoring **조회**. 이 서비스들은 **전용 역할이 아예 없어 리더가 유일한 조회 통로**입니다 |
| **Secrets Manager 매니저** | 시크릿 등록·수정(`DATABASE_URL`, LLM API 키 등). ★`뷰어`는 문서상 *"단, **시크릿 값을 조회하거나** … 수행할 수 없습니다"* |
| **KMS 사용자 (User)** | ★**리더만으로는 시크릿 값을 못 읽습니다.** 등록은 되는데 확인이 안 됩니다. `KMS 뷰어`는 *"암호화 작업(암호화, 복호화, 서명, 검증)을 수행할 수 없습니다"* |
| **Object Storage 매니저** | 버킷 목록 조회·관리 |
| **Alert Center 프로젝트 매니저** | 알림 정책·수신 채널 (`catchap-monitoring` 대체) |
| **Codeflow 매니저** | CI 파이프라인. ★매니저만으로는 PR 리뷰어 지정 시 사용자 목록을 못 보는데 **위 `프로젝트 리더`가 함께 있어 해결**됩니다 |

★ 이 계정에 **`프로젝트 멤버`는 넣지 말아 주십시오.** 멤버면 다른 조의 VM·로드밸런서·MySQL까지
지울 수 있는데, **이 계정의 키는 서버 파일로 저장**되기 때문입니다.

★ **`뷰어` 역할은 요청하지 않습니다** — 상위 역할이 하위를 자동 포함하고, 문서가 `리더 + 서비스 뷰어`를
**중복**으로 명시합니다.

## 무엇을 확인했나

**1) push는 `프로젝트 멤버` 이상이 필요합니다 — 문서 추론이 실측으로 확정됐습니다.**

```

토큰요청 repository:catchap-backend-repo/backend:push,pull                  200
   → access=[{"actions":["pull"]}]        ★push,pull 을 요청했는데 pull 만 돌아옴
```

> **이미지 Push는 Container Registry 관리자와 프로젝트 멤버 권한이 있어야** 할 수 있습니다.
> — [이미지 관리](https://docs.kakaocloud.com/service/container-pack/container-registry/how-to-guides/) · `20-카카오문서/CR-03-이미지관리-PushPull.png`

**2) ★저장소별 `리포지토리 멤버`로 우회할 수 없습니다 — 서비스 계정은 대상이 아닙니다.**

콘솔 `권한 설정` 팝업에 `catchap-ops`를 넣어 봤더니 **"추가할 수 없는 계정입니다"** 였습니다.
짧은 이름·전체 식별자 둘 다 같았습니다. 콘솔이 부르는 API를 열어 보니 원인이 나왔습니다.

```
GET iam.kakaocloud.com/api/v1/domains/{도메인}/users/name/suggest
    ?name=catchap-ops-kc-sfacspace05@kc.serviceaccount.com&user_type=user
                                                           ^^^^^^^^^^^^^^^ 콘솔이 고정
응답  200  {"users":null}
```

문서도 그 화면이 **"프로젝트 밖" 사용자용**임을 명시합니다 — *"단, **프로젝트에 속하지 않은 멤버**도
해당 리포지토리에 리포지토리 멤버 역할을 부여받게 되면 이미지를 Push할 수 있습니다."*
`catchap-ops`는 프로젝트 안의 계정이라 애초에 그 길의 대상이 아니었습니다.

**3) pull(런타임)은 이미 해결돼 있습니다.**

*"이미지 Pull은 해당 프로젝트에 속한 멤버라면 누구나 할 수 있습니다"* — `catchap-ops`로
`actions:["pull"]`이 실측 확인됐으므로 **K8s `imagePullSecret`은 이 계정으로 씁니다.**

## 그래서 저희가 어떻게 할지

**빌드 시점에 `프로젝트 멤버`를 가진 계정으로 push합니다.** 지금 만들지 않는 이유는
**빌드할 기계가 아직 없어서**입니다(이 PC·새 VPC 5대 모두 Docker 미설치). 순서를 이렇게 잡았습니다.


CI를 붙일 때는 **`프로젝트 멤버` 하나만 가진 서비스 계정**을 새로 만듭니다(역할은 생성 후 변경

## (1) KMS `kms11` 허용 대상에 새 앱 계정 추가

### 설정 절차 — [접근 제어 설정](https://docs.kakaocloud.com/service/security/kms/how-to-guides/kms-access-control) 문서 기준

```
  → 좌측 메뉴 [사용자 키] → 목록에서  kms11  클릭
  → [접근 제어] 탭 → 허용 대상 영역에 새 앱 계정 추가
```

바로 가는 주소

```
https://console.kakaocloud.com/kms/user-keys?project_id=5f428f1b341249c983ab19c6f8f3fdb4&region=kr-central-2
```

문서 원문 — *"카카오клауд 콘솔 > Security > KMS 메뉴로 이동합니다.
**사용자 키 목록에서 … 키의 이름을 클릭합니다. 상세 페이지에서 접근 제어 탭**을 클릭합니다. …
접근 제어를 사용할 경우 **허용 대상을 추가**할 수 있습니다."*

**선택 가능한 대상** — *"동일 프로젝트에 있는 사용자, 그룹, **서비스 계정**, 서비스 에이전트 계정"*

**왜** — 콘솔에서 우리 키 2개의 상태가 갈립니다.

| 키 | 접근 제어 | 저희 계정에서 |
|---|---|---|
| `kms12` (`292d0657-…`) | **미사용** | 상세까지 다 보임 |
| **`kms11`** (`e3ac9ecb-****`) | **사용** | ID조차 마스킹 |

[KMS 문서](https://docs.kakaocloud.com/service/security/kms/kms-main) 원문입니다.

> **접근 제어 사용**: 허용 대상을 설정할 수 있습니다. 설정 가능한 대상은 동일 프로젝트 내
> 사용자, 그룹, **서비스 계정**, 서비스 에이전트 계정이며, 실제 사용 권한은 해당 IAM 역할을 따릅니다.
> **접근 제어 미사용**: 키 사용에 필요한 **IAM 역할을 가진 대상은** 해당 키를 사용할 수 있습니다.

즉 **`kms11`은 IAM 역할만으로는 안 되고 허용 명단에 있어야 합니다.**
그런데 **프로덕션 시크릿 4건이 전부 `kms11`** 로 암호화돼 있습니다.

```
catchap-auth-jwt-secret        9ff8ffb3-d6c0-4331-bd42-88e6408dde32   kms11
catchap-smtp-app-password      a9b8f1a9-554c-4723-8088-179b9fe3b019   kms11
catchap-stt-worker-token       3bbc4b05-da46-4235-ad2d-9adc550af106   kms11
catchap-metrics-ingest-token   6dafcf38-4756-46b2-a2d4-390129efa552   kms11
```

**명단에 없으면 앱이 시크릿을 못 읽어 뜨지 않습니다.**

### ★ 주의 3가지 (문서 명시)

```
① 접근 제어를 미사용으로 바꾸지 말아 주십시오
   → "허용 대상 목록은 초기화됩니다. 다시 사용으로 변경 시, 허용 대상 목록을 새로 구성해야 합니다"
   접근 제어가 걸려 있는 편이 안전하고, 저희도 그 설정을 우회하지 않겠습니다

② "대상을 추가하기 위해서는 프로젝트의 IAM 리소스를 조회할 수 있는 권한이 필요합니다"

③ "대상 목록에는 소유자가 표시되지 않습니다"
   → 소유자인 강사님 계정은 목록에 안 보이는 것이 정상입니다
```

## (2) 버킷 권한에 새 앱 계정 추가

### 설정 절차 — [버킷 권한 관리](https://docs.kakaocloud.com/service/storage/object-storage/how-to-guides/object-storage-manage-permission) 문서 기준

```
콘솔  https://console.kakaocloud.com
  → [모든 서비스] → Storage > Object Storage
  → 좌측 메뉴 [일반 버킷] → 목록에서  catchap-storage-prod-team1  클릭
  → [권한] 탭 → [역할] 영역 → [역할 추가] 버튼
  → 팝업에서  유형 = 서비스 계정 ·  대상 = 새 앱 계정
             역할 = 스토리지 객체 관리자 (storage.objectAdmin)
  → [저장]
```

바로 가는 주소

```
https://console.kakaocloud.com/object-storage/buckets/catchap-storage-prod-team1/objects?project_id=5f428f1b341249c983ab19c6f8f3fdb4&region=kr-central-2
```

문서 원문 — *"카카오클라우드 콘솔 > Storage > Object Storage 메뉴로 이동합니다.
**일반 버킷 메뉴에서 역할을 추가할 버킷을 선택합니다. 권한 탭 > 역할에서, [역할 추가] 버튼**을
클릭합니다. **유형과 역할을 선택 후 [저장]** 버튼을 클릭합니다."*

**역할 추가 화면의 유형** — *"개인, 그룹, **서비스 계정**, 역할 그룹"* 중 **서비스 계정**을 고르십시오.

★ **`AllUserGroup`은 절대 고르지 말아 주십시오.** 문서 경고 —
  *"AllUserGroup에게 Write(쓰기) 권한을 포함한 역할을 부여하면, **인증되지 않은 익명의 모든 사용자가**
  해당 버킷과 객체에 대해 업로드·수정·삭제를 수행할 수 있습니다."*

**왜** — Object Storage는 **2단 권한 구조**입니다.

> IAM에서 프로젝트 관리자·멤버·뷰어·Object Storage 매니저·뷰어 역할은
> **최초에 버킷에 대한 생성 및 목록 조회에 대한 권한만** 가질 수 있습니다.
> 다만 버킷을 생성하면 **생성 시 초기 역할 정보에 따라 Object Storage 역할이 버킷에 부여**됩니다.

**IAM 역할만으로는 객체를 읽고 쓸 수 없습니다.** 기존 `catchap-backend`가 되는 이유는
**그 계정이 이 버킷을 직접 만들어** 생성 시점에 역할을 받았기 때문입니다.

**왜 `storage.objectAdmin`인가** — 앱은 객체만 다루면 되고 버킷 설정을 바꿀 이유가 없습니다.

| 역할 | 권한 | 판단 |
|---|---|---|
| `storage.admin` | 버킷 삭제·권한정책까지 전부 | 과함 |
| `storage.editor` | 버킷 수정 + 객체 전체 | 과함 |
| **`storage.objectAdmin`** | **객체 생성·삭제·조회·수정만** | **적정** |
| `storage.objectReader` | 객체 읽기만 | 업로드 불가 |

# ■ 참고 — 미리 알려드리는 구조적 사실

**역할은 프로젝트 단위까지만 좁혀지고 그 아래로는 내려가지 않습니다.**

```
조직  kc-kdt-sfacspace2025
 └ 프로젝트 kc-sfacspace05        ← 권한의 최소 단위
     ├ 1조 자원  VM 5 + K8s 워커 2 + MySQL + MemStore + LB
     ├ 2조 자원  VM 5
     └ 3조 자원  VM 3
```

**"1조 자원만 다루는 역할"은 존재하지 않습니다.** 어떤 프로젝트 역할이든 3개 팀 자원 전부에 적용됩니다.
그래서 저희가 **`프로젝트 멤버` 이상을 서비스 계정에 넣지 말아 달라고** 부탁드리는 것입니다.

**전용 역할이 아예 없는 서비스** — 선택 가능한 프로젝트 역할 25개를 전수 확인한 결과입니다.

```
VPC · 로드밸런서 · Kubernetes Engine · Container Registry
MySQL · MemStore · Monitoring · Certificate Manager · Beyond Compute Service(VM)
```

**이 서비스들은 조회조차 `프로젝트 리더` 이상이 있어야 열립니다.**
그래서 저희가 지금 VPC·인스턴스·로드밸런서 화면을 열 수 없고, 확인할 일마다 여쭤보고 있습니다.
