## A-1. `catchap-app` 신규 생성

| | |
|---|---|

# B. 권한 명단 — 역할만으로는 안 되는 것

## B-1. KMS `kms11` 접근 제어에 계정 추가

| | |
|---|---|
| **무엇을** | `kms11`의 접근 제어 명단에 `catchap-app` 추가 |
| **어디서** | KMS → 사용자 키 → kms11 → 접근 제어 |
| **왜** | 우리 시크릿 4건이 **kms11로 암호화**돼 있음. 명단에 없으면 **역할이 맞아도 복호화 실패**. 계정을 새로 만들면 ID가 달라져 기존 `catchap-backend`가 있던 자리를 물려받지 못함 |
| **누가** | **멘토님만 가능** — `kms11`은 접근 제어가 걸려 있어 사장님 콘솔에서 **상세 열람조차 안 됨**(목록에서 값이 `*****`로 마스킹, 상세 링크 없음) |
| **언제** | `catchap-app` 생성 직후 |
| **조건** | A-3 시험에서 "명단 없이도 복호화됨"으로 나오면 **불필요** |

## D-2b. ★퍼블릭 보안그룹의 6379 규칙 삭제

| | |
|---|---|
| **무엇을** | `SG-Team1-Public-Bastion`의 인바운드 규칙 중 **`TCP / 0.0.0.0/0 / 6379`** 삭제 |

| **왜** | **출발지가 `0.0.0.0/0`(인터넷 전체)입니다.** 프라이빗 쪽(`SG-Team1-Private-Internal`)에 넣은 것은 `10.0.0.0/16`이라 정상인데, 이쪽은 전 세계 개방입니다.<br>이 보안그룹은 **VM1(공인 IP `210.109.82.148`)에 붙어 있습니다.**<br><br>**지금 당장은 위험하지 않습니다** — VM1에 6379로 듣는 프로세스가 없습니다(열린 포트 22·53뿐, 실측).<br>다만 **나중에 그 서버에서 Redis를 띄우면 그 순간 전 세계에 열립니다.** 그때는 이 규칙을 아무도 기억하지 못합니다. 게다가 **Valkey는 현재 비밀번호가 없어**(2026-07-29 확인) 붙기만 하면 다 읽힙니다.<br><br>**방화벽 규칙은 받는 쪽에 붙은 것만 판정에 씁니다.** MemStore는 사설 서브넷에 있으므로 프라이빗 보안그룹만으로 충분하고, 이 규칙은 아무 효과도 없이 위험만 남깁니다 |

| **덧** | 같은 보안그룹에 `0.0.0.0/0 → 22`(SSH)도 열려 있습니다. 점프서버라 흔한 구성이지만, 접속 대역을 좁힐 수 있으면 좁히는 편이 낫습니다 |
