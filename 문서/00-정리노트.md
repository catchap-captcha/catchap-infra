```

다른 포트  → 다른 mysqld
```

### ★해소됨 — 이름만 private이고 실제로는 전부 "퍼블릭 서브넷" (2026-07-30)

한때 "문서와 실측이 어긋난다"고 적었으나, **[라우팅 테이블 문서](https://docs.kakaocloud.com/service/networking/vpc/main/vpc-route-table)를 읽으니
어긋나는 게 아니었습니다.** 인터넷 게이트웨이 문서만 보고 라우팅 테이블 문서를 안 본 탓이었습니다.

> 로컬 외 모든 IPv4 트래픽(`0.0.0.0/0`)에 대해 인터넷에 액세스할 수 있는 인터넷 게이트웨이를 대상으로 설정할 수 있습니다.
> **인터넷 게이트웨이를 포함한 라우팅 테이블에 연결된 서브넷을 퍼블릭 서브넷이라고 합니다.**

**즉 퍼블릭/프라이빗을 가르는 것은 서브넷 이름이 아니라 라우팅 테이블입니다.**
우리 서브넷은 전부 `0.0.0.0/0 → IGW` 경로를 가진 테이블에 붙어 있으므로 **문서 정의상 모두 퍼블릭 서브넷**입니다(0804 에 4개로 정리한 뒤에도 성질은 그대로).
이름의 `private_`는 만든 사람이 붙인 이름일 뿐 동작과 무관합니다.

```
콘솔 실물 확인 (2026-07-30)
  Team1-VPC_10aa8_route_table   0.0.0.0/0 → IGW   ← catchap-core-2a · catchap-gpu-2a 연결
  main                          0.0.0.0/0 → IGW   ← catchap-jump-2a · catchap-core-2b 연결
```

★ **NAT 인스턴스가 필요 없는 이유가 이것입니다.** NAT 인스턴스는 *IGW 경로가 없는* 서브넷을 위한 우회책인데,
우리는 애초에 IGW 경로가 있습니다. 캡처: `09-네트워크-VPC/20260730-11·12·29-라우팅테이블-…-경로.png`

**남은 미세한 의문 한 가지** — 인터넷 게이트웨이 문서는 "서브넷의 인스턴스에 퍼블릭 IP가 연결되어야 인터넷에
통신할 수 있다"고 하는데, VM2(10.0.2.165)는 퍼블릭 IP가 없는데도 `210.109.82.130`으로 나갑니다.
경로 추적에 `100.64.0.0/10`(통신사 NAT 대역)이 보이므로 **카카오클라우드 IGW가 공유 SNAT을 해 주는 것**으로 보입니다.
AWS와 다른 점이라 알아 둘 만하지만, 동작에 문제는 없습니다.

### ★NAT — 카카오클라우드에는 관리형 NAT 게이트웨이가 없습니다

AWS의 `NAT Gateway` 같은 별도 서비스가 없고, 문서에도 **`NAT 인스턴스`** 로만 나옵니다.
즉 **VM을 하나 띄워서 그 VM을 NAT 장비로 만드는 방식**(AWS의 옛 NAT Instance 패턴)입니다.

> 프라이빗 서브넷에 있는 인스턴스를 인터넷에 연결하려면 **NAT 인스턴스를 시작하는 방법**이 있습니다.
> 그 후 프라이빗 서브넷의 라우팅 테이블에 `0.0.0.0/0`을 **NAT 인스턴스로 전달하는 라우팅**을 추가합니다.

[부록 문서](https://docs.kakaocloud.com/service/networking/vpc/how-to-guides/vpc-appx-1)가 정한 5단계 —
캡처: `20-카카오문서/VPC-03-NAT인스턴스-부록.png`

| 단계 | 할 일 |
|---|---|
| 1 | 퍼블릭 서브넷(IGW 경로 있음) · 프라이빗 서브넷(IGW 경로 없음)을 각각 만들고 라우팅 테이블 연결 |
| 2 | **퍼블릭** 서브넷에 VM 생성 → 퍼블릭 IP 연결 → `net.ipv4.ip_forward=1` + `iptables -t nat -A POSTROUTING -j MASQUERADE` |
| 3 | 콘솔 `Virtual Machine → [⋮] → 패킷 송신 허용 IP 수정`에 `0.0.0.0/0` 추가 (AWS의 source/dest check 끄기에 해당) |
| 4 | NAT 인스턴스 보안 그룹: 인바운드 = 프라이빗 CIDR의 80·443 + 관리자 IP의 22 / 아웃바운드 = `0.0.0.0/0`의 80·443 |
| 5 | 프라이빗 서브넷 라우팅 테이블에 `0.0.0.0/0 → 인스턴스(NAT VM)` 추가 |

★ **우리는 이 작업이 전혀 필요 없습니다.** 서브넷이 전부 이미 IGW 경로를 갖고 있기 때문입니다.

★★**0804 에 다시 검토하고 「안 만든다」로 확정했습니다.** 만들면 **사설 서버 전부의 출구가
VM 한 대에 모여** 없던 단일 장애점이 생깁니다. 그리고 `catchap-core-2b`(2-b)가
**`catchap-jump-2a`·입구 A 와 `main` 라우팅 테이블을 같이 쓰기 때문에**, 기본 경로를 바꾸려면
테이블부터 갈라야 하고 잘못하면 점프서버가 끊깁니다. **얻는 것은 서류상 성질 하나**이고
**들어오는 문은 지금도 공인 IP 가 없어 닫혀 있습니다.** 컷오버 뒤 보안 강화 항목으로 킵.

### ①의 상세 (요청서와 같은 내용, 참고용)

**이 클러스터는 웹훅 인가자를 씁니다**(`webhook authorizer does not support user rule resolution`).
그래서 밖에서는 권한 부여 경로를 확인할 수 없어 **클러스터 안에서 바인딩**해 주셔야 합니다.
