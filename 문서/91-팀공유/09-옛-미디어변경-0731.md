# 미디어 저장 방식이 바뀝니다 — 팀 공유

1조 김태형 · 2026-07-31 · 백엔드 브랜치 `th-after` (`c55999b`)

**★지금 당장 바뀌는 건 없습니다.** 기본값이 예전 그대로라 배포해도 동작이 같습니다.
다만 **앞으로 미디어를 다루는 코드를 쓸 때 알아야 할 것**이 생겨서 공유드립니다.

---

## 1. 한 줄 요약

강의 영상·자료·문항 이미지를 **서버 디스크가 아니라 Object Storage(버킷)** 에 둘 수 있게
저장소 계층을 만들었습니다. 환경변수 하나로 예전 방식과 새 방식을 오갑니다.

```
MEDIA_STORAGE_BACKEND=local    ← 지금 기본값. 예전과 100% 동일
MEDIA_STORAGE_BACKEND=object   ← 버킷 사용
```

---

## 2. 왜 바꾸나 — 파드가 2개가 되면 깨집니다

지금은 서버 한 대에 백엔드 컨테이너가 하나라 아무 문제가 없습니다.

```
지금:  [백엔드 컨테이너 1개] ──▶ /app/media  (그 서버의 디스크)
       강사가 올림 → 그 디스크에 저장 → 같은 컨테이너가 읽음 → 정상
```

쿠버네티스로 옮기고 파드를 2개로 늘리면 이렇게 됩니다.

```
K8s:   [파드 A · 워커1] ──▶ 워커1 디스크
       [파드 B · 워커2] ──▶ 워커2 디스크      ← 서로 다른 디스크

       강사가 업로드 → 로드밸런서가 A로 보냄 → A 디스크에 저장
       학생이 재생   → 로드밸런서가 B로 보냄 → B에는 그 파일이 없음 → 404
```

**요청이 어느 파드로 가느냐에 따라 되기도 하고 안 되기도 합니다.** 재현이 안 되는 장애라
디버깅이 가장 괴로운 종류입니다. 게다가 파드는 죽으면 새로 뜨는데 그때 디스크가 사라집니다.

버킷은 파드 밖에 있으므로 **파드가 몇 개든, 죽었다 살아나든 같은 파일을 봅니다.**
이게 "무상태화(stateless)"이고, K8s로 옮기는 실제 이유입니다.

---

## 3. 코드 쓰실 때 달라지는 것 — 이것만 기억하시면 됩니다

### 함수 이름이 바뀌었습니다 (`_path` → `_key`)

```python
# 예전
_video_path(lec)            # → Path 객체
_thumbnail_path(lec)
_material_path(mat)
_question_image_path(ref)

# 지금
_video_key(lec)             # → "lectures/{id}.mp4"  문자열
_thumbnail_key(lec)         # → "lectures/thumbnails/{id}.png"
_material_key(mat)          # → "lectures/materials/{id}.pdf"
_question_image_key(ref)    # → "lectures/questions/{id}.png"
```

`_media_dir()` · `_thumbnails_dir()` · `_materials_dir()` · `_question_images_dir()` 은 **없어졌습니다.**

★**이름을 일부러 바꿨습니다.** 이름을 그대로 두고 반환형만 `Path` → `str` 로 바꾸면,
안 고친 코드가 문자열을 `Path`처럼 다뤄 **조용히 잘못 동작**합니다.
이름을 바꾸면 `NameError` 로 즉시 터집니다. **실패는 시끄러운 게 낫습니다.**

### 파일을 다루는 방법

```python
from app.services.media_storage import get_media_storage, media_response, local_file

st = get_media_storage()

# 저장 (업로드는 임시파일을 거친 뒤 이걸로)
st.save_path(key, tmp_path)     # 임시파일을 옮긴다(성공하면 임시파일은 사라짐)
st.save(key, fileobj)           # 파일 객체에서 바로

# 조회
st.stat(key)                    # → MediaStat(size=...) 또는 None
                                #   예전 path.is_file() 자리

# 삭제 (멱등 — 없어도 예외 없음)
st.delete(key)                  # 예전 path.unlink(missing_ok=True) 자리

# 서빙 — FileResponse 대신
return media_response(key, media_type="video/mp4",
                      range_header=request.headers.get("range"))

# 외부 라이브러리에 "파일 경로"를 넘겨야 할 때 (예: STT 워커)
with local_file(key, suffix=".mp4") as p:
    transcribe(p)               # 로컬 백엔드면 원본 경로를 그대로 줌(복사 없음)
```

### 새 엔드포인트에서 파일을 서빙하신다면

`Range` 헤더를 받으셔야 합니다. 함수 인자에 `request: Request` 를 넣고 넘겨 주세요.

```python
@router.get("/…")
def something(request: Request, ...):
    return media_response(key, media_type=..., range_header=request.headers.get("range"))
```

이게 없으면 **영상 탐색(seek)이 안 되고**, 브라우저가 전체를 받을 때까지 재생이 시작되지 않습니다.

## 4. 설계 판단 — 왜 이렇게 했는지

### ① 한 번에 갈아엎지 않고 추상화 계층을 먼저 뒀습니다

`local` 이면 예전과 **100% 같은 동작**입니다. 그래서

- **로컬 개발에 버킷 자격증명이 필요 없습니다.** 지금처럼 그냥 돌아갑니다
- 이전 중 문제가 생기면 **환경변수 한 줄로 되돌립니다.** 이미지 재빌드도 필요 없습니다

되돌릴 방법이 없는 변경은 만들지 않는다 — 이게 첫 번째 원칙이었습니다.

### ★② 서명 URL을 안 쓰고 백엔드가 중계합니다 — 동시 시청 차단 때문에

영상을 버킷에 두면 보통 **서명 URL(presigned)** 을 발급해 브라우저가 버킷에서 직접 받게 합니다.
백엔드 부하가 0이라 그게 정석입니다. **그런데 그러면 동시 시청 차단이 무력화됩니다.**

`lectures.py` 스트리밍 엔드포인트 주석에 의도가 명시돼 있습니다.

> takeover로 세션이 교체된 순간 **이전 기기의 스트림 URL이 즉시 죽는다**
> (동시 차단이 '진도 인정'만이 아니라 **영상 바이트 전달에도** 걸린다).

즉 **매 Range 요청마다 세션을 다시 확인하는 것 자체가 기능**입니다. 서명 URL을 한 번 내주면
그 뒤로 백엔드를 안 거치므로, 다른 기기에서 재생을 시작해도 이전 기기가 계속 봅니다.
만료를 짧게 줘도 `<video>` 태그가 URL을 스스로 갱신하지 않아 재생이 끊깁니다.

→ **백엔드가 중계합니다.** 버킷→백엔드는 같은 VPC 내부라 외부 대역폭이 안 늘고,
파일을 통째로 메모리에 올리지 않고 1MiB씩 흘려보내서 메모리도 일정합니다.

### ③ 설정이 빠지면 조용히 넘어가지 않고 예외를 냅니다

`object` 인데 버킷 이름이나 키가 비어 있으면 **`RuntimeError`** 가 납니다.
로컬로 슬쩍 떨어지면 설정 누락이 *"파일이 없습니다"* 로 둔갑해서 원인을 못 찾습니다.

## 5. 이미 옮겨 둔 것

프로덕션 미디어 **3,462개 · 3.24GB** 를 버킷에 복사했습니다(원본은 그대로 둠).

```
media/lectures/      영상 19개 (3.1GB) + 문항 이미지 1개
media/captcha/       배경 766개 + 조각 2,676개 (169MB)

검증  누락 0 · 크기 불일치 0 · 표본 md5 6개 일치
      실제 이전한 영상을 앱으로 스트리밍해 206·Content-Range·md5 확인
```

★참고로 지금 미디어의 실체는 **영상 19개가 3.1GB**이고, 나머지 3,442개는 캡차 자산입니다.
썸네일·자료는 아직 업로드된 적이 없습니다.

## 6. ★캡차 담당자분께 — 아직 안 바꿨습니다

캡차 자산도 버킷에 **올려는 뒀지만 코드는 그대로**입니다. 구조가 달라서입니다.

```
강의 미디어   경로를 DB에 저장하지 않고 {id}{확장자}로 유도    → 전환 완료
캡차 자산     DB(image_path·piece_path)에 상대경로를 저장하고
             safe_asset(relative) 로 찾음                    → 미전환
```

캡차는 **런타임에 업로드되지 않고 미리 만들어 두는 읽기 전용 자산**이라 선택지가 하나 더 있습니다.

```
가) 저장소 계층으로 전환      강의 미디어와 같은 방식
나) 이미지에 굽는다           169MB · 불변이라 가능 · 버킷 왕복이 없어 더 빠름
                            단 캡차 뱅크를 새로 만들 때마다 이미지 재빌드
```

**어느 쪽이 나은지 의견 주시면 반영하겠습니다.** 이전이 끝난 뒤 정해도 됩니다.

## 7. 검증한 것

```
저장소 계층·HTTP 응답          43건 통과
실제 버킷 대상                 18건 통과
엔드투엔드(업로드→서빙→삭제)     21건 통과
기존 테스트 전체               394 passed / 1 failed
                              실패 1건은 origin/jy 에서도 동일하게 실패하는 기존 건
                              (별도 워크트리로 대조 확인)
```

### 검증이 제 실수 2개를 잡았습니다

**① `local` 백엔드가 파일 위치를 바꿔 버렸습니다.** 그러면 기존 3.3GB가 전부 "없는 파일"이
됩니다. "local이면 예전과 100% 같다"는 목표를 제가 깬 것이었습니다.

**② 저장소를 캐시해서 미디어 경로가 첫 호출값에 얼어붙었습니다.** 원래 코드는 매번 설정을
읽었는데 그 동작을 바꿔 버렸습니다.

둘 다 **기존 테스트를 돌려서** 드러났습니다. 안 돌렸으면 프로덕션에서 터졌을 것입니다.

   백엔드 부담이 됩니다. 차단 방식을 바꿔서라도 서명 URL로 가는 게 나을 수도 있습니다
