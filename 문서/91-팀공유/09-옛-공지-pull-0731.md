김태형 · 오늘 백엔드 `th-after` 에 푸시했습니다.

## 1. 왜 코드를 바꾸게 됐나 — 이야기의 시작은 쿠버네티스입니다

지금 서비스는 **서버 4대에 앱이 한 벌씩 통째로** 떠 있습니다.

```
프론트 서버   catchap-frontend 컨테이너 1개 + Caddy
백엔드 서버   catchap-backend 컨테이너 1개 + AI + Caddy
DB 서버       MySQL
GPU 서버      STT 워커
```

이 구조의 한계가 명확합니다.

```
서버가 죽으면          그 서비스가 통째로 멈춘다. 사람이 손으로 살려야 한다
트래픽이 몰리면        늘릴 방법이 없다 (서버를 새로 만들고 수동 배포)
배포할 때             서버에 들어가서 docker compose 를 친다
```

**그래서 쿠버네티스로 옮깁니다.** 파드가 죽으면 알아서 다시 뜨고, 필요하면 2개·3개로 늘립니다.

### 그런데 파드를 늘리려면 앱이 "무상태(stateless)" 여야 합니다

파드를 2개로 늘리면 **요청이 둘 중 아무 데나 갑니다.** 그래서 파드가 자기 안에 뭔가를
들고 있으면 깨집니다. 지금 우리 앱은 **상태를 세 곳에** 들고 있습니다.

```
① 로그인 세션    프로세스 메모리        → 파드 2개면 로그인이 자꾸 풀린다
② 미디어 파일    서버 로컬 디스크       → A 파드로 올린 영상을 B 파드가 못 찾는다  ★오늘 이것
③ 설정(.env)     서버에 놓인 파일       → 서버마다 따로 관리해야 한다
```

**오늘 ②를 뺐습니다.** 나머지 둘은 아직 남아 있습니다.

### ② 가 왜 문제인지 구체적으로

```
지금:  [백엔드 컨테이너 1개] ──▶ /app/media  (그 서버의 디스크)
       올림 → 그 디스크에 저장 → 같은 컨테이너가 읽음 → 정상

K8s:   [파드 A · 워커1] ──▶ 워커1 디스크
       [파드 B · 워커2] ──▶ 워커2 디스크      ← 서로 다른 디스크

       강사가 업로드 → 로드밸런서가 A로 → A 디스크에 저장
       학생이 재생   → 로드밸런서가 B로 → B에는 없음 → 404
```

**요청이 어느 파드로 가느냐에 따라 되기도 하고 안 되기도 합니다.** 재현이 안 되는 장애라
가장 잡기 어려운 종류입니다. 게다가 파드는 죽으면 새로 뜨는데 그때 디스크가 사라집니다.

→ **파일을 파드 밖(Object Storage 버킷)에 두면** 파드가 몇 개든, 죽었다 살아나든 같은 파일을 봅니다.
   이게 오늘 코드가 바뀐 이유입니다.

## 2. 그래서 무엇을 만들었나

`app/services/media_storage.py` — **저장소를 갈아 끼울 수 있게** 추상화했습니다.

```
MediaStorage
  ├─ LocalMediaStorage    서버 디스크 — 지금까지의 동작
  └─ ObjectMediaStorage   버킷 (S3 호환 API)
```

환경변수 하나로 오갑니다.

```
MEDIA_STORAGE_BACKEND=local    ← 현재 기본값. 예전과 100% 동일
MEDIA_STORAGE_BACKEND=object   ← 버킷 사용
```

**★한 번에 갈아엎지 않은 이유**는 두 가지입니다. ① 로컬 개발에 버킷 자격증명이 필요 없어야
하고 ② 이전 중 문제가 생기면 **환경변수 한 줄로 되돌릴 수 있어야** 합니다(이미지 재빌드 없이).
되돌릴 방법이 없는 변경은 만들지 않는 게 원칙입니다.

**미디어 3,462개 3.24GB 는 이미 버킷에 복사해 뒀습니다**(원본은 그대로). 검증 통과했습니다.

## 6. 미디어 코드를 만지실 때만 — 함수 이름이 바뀌었습니다

```
_video_path(lec)          →  _video_key(lec)            "lectures/{id}.mp4"
_thumbnail_path(lec)      →  _thumbnail_key(lec)
_material_path(mat)       →  _material_key(mat)
_question_image_path(ref) →  _question_image_key(ref)

_media_dir() · _thumbnails_dir() · _materials_dir() · _question_images_dir()  →  삭제
```

```python
from app.services.media_storage import get_media_storage, media_response
st = get_media_storage()

st.stat(key)                 # 예전 path.is_file()
st.delete(key)               # 예전 path.unlink(missing_ok=True) · 없어도 예외 X
st.save_path(key, tmp_path)  # 예전 os.replace(tmp, final)

return media_response(key, media_type="video/mp4",       # 예전 FileResponse
                      range_header=request.headers.get("range"))
```

★서빙 엔드포인트에는 **`request: Request` 를 인자에 넣어** `Range` 를 넘겨 주세요.
없으면 **영상 탐색(seek)이 안 됩니다.** 예전엔 `FileResponse` 가 알아서 해 줬는데,
버킷 객체는 starlette 가 모르기 때문에 우리가 직접 처리합니다.

★이름을 일부러 바꿨습니다 — 반환형만 바꾸면 안 고친 코드가 문자열을 `Path` 처럼 다뤄
**조용히 잘못 동작**합니다. 이름이 바뀌면 `NameError` 로 즉시 터집니다.

## 7. 캡차 자산도 저장소 계층으로 바꿨습니다 (★캐시 동반)

캡차 배경·조각도 서버 로컬 디스크에 있어서, K8s 에서 파드를 늘리면 **강의 미디어와 똑같이
파드마다 못 찾는 문제**가 생깁니다. 그래서 같은 저장소 계층으로 옮겼습니다.

### 다만 그냥 옮기면 느려집니다 — 그래서 캐시를 같이 넣었습니다

버킷에서 **작은 객체 하나를 읽는 데 VPC 안에서도 약 0.27초**가 걸립니다(실측).

```
11KB ~ 119KB 모두 0.26~0.30초    ← 크기가 아니라 왕복 지연이 지배
  연결 0.002s · TLS 0.025s · 나머지 0.24s
```

캡차 자산 서빙은 **챌린지당 배경 1 + 조각 N 번 호출되는 핫패스**입니다(코드 주석에도
그렇게 적혀 있습니다). 조각이 6개면 7회 × 0.27초 = **캡차 한 번 푸는 데 2초쯤 그대로
느려집니다.** 지금은 로컬 디스크라 1ms도 안 걸리던 것입니다.

**캡차 자산은 캐시에 딱 맞습니다** — 유한하고(배경 766 + 조각 2,676) 내용이 변하지 않습니다
(뱅크를 새로 만들면 새 파일이 생길 뿐입니다).

```
실측:  첫 읽기 615ms  →  캐시 후 0ms
```

### 바뀐 함수

```
safe_asset(relative) -> Path            →  safe_asset_key(relative) -> (키, Content-Type)
asset_path(cid, aid) -> Path            →  asset_key(cid, aid)      -> (키, Content-Type)
_final_dir()                            →  삭제
```

★**이미지에 굽는 방식은 안 택했습니다.** 빠르긴 하지만 백엔드 이미지가 362MB → 530MB 로
커져 파드가 뜰 때마다 더 받아야 하고, **캡차 뱅크를 갱신할 때마다 이미지를 다시 빌드·배포**
해야 합니다. 캡차는 계속 늘려 갈 자산이라 부담이 됩니다.

★**보안 성질은 그대로입니다.** 종전에는 `resolve()` 후 루트 하위인지 봤고, 지금은 저장소
계층이 상위경로·절대경로·비허용문자를 막고 **확장자 화이트리스트를 한 번 더** 봅니다
(SVG 금지 유지 — `<img>` 인라인 서빙이라 스크립트 삽입 위험). 차단 6가지 시험 통과했습니다.
