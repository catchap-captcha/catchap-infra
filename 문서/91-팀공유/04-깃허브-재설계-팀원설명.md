## 4. ★각자 해야 할 일 — 두 가지

### ① 이름이 바뀐 저장소는 주소를 고칩니다

```
ai-service        →  ★catchap-captcha
catchap-service   →  ★catchap-legacy
catchap-backend · catchap-frontend  →  ★그대로입니다
```

**`ai-service` 를 쓰시는 분 (ms님·sw님)**

```bash
cd <ai-service 폴더>
git remote set-url origin https://github.com/catchap-captcha/catchap-captcha.git
git remote -v
```

**`catchap-service` 를 쓰시는 분**

```bash
cd <catchap-service 폴더>
git remote set-url origin https://github.com/catchap-captcha/catchap-legacy.git
git remote -v
```

마지막 줄이 새 주소로 보이면 끝입니다.

★**안 고쳐도 당장은 됩니다 — 그래도 고쳐 두시는 게 낫습니다.**
GitHub 이 옛 이름을 새 이름으로 자동으로 넘겨 줘서 지금 하시던 `push`·`pull` 은 바로 안 깨집니다.
⚠️다만 **넘겨 주는 건 옛 이름이 비어 있을 때만**입니다. 나중에 누군가 `ai-service` 라는 이름으로
새 저장소를 만들면 **그쪽으로 가 버립니다.** 한 줄이니 지금 고쳐 두시는 편이 안전합니다.

**잘 안 되면**

```
"remote origin already exists"   set-url 이 아니라 add 를 쓰신 것입니다. set-url 로 다시
"repository not found"           주소 오타이거나 저장소 접근 권한이 없는 경우입니다
그 외                            지금 remote 주소(git remote -v 결과)를 알려 주세요
```

### ② 작업 중인 것을 올려 두세요 (★정리 전에)

로컬에만 있고 GitHub 에 없는 커밋이 있으면, 정리하는 동안 어느 쪽이 최신인지 헷갈립니다.


## 5. ★앞으로 일하는 방식

### PR 이 무엇인가

**PR(Pull Request) = 「내가 만든 것을 `main` 에 넣어 달라」는 요청서**입니다.
우리 저장소는 지금까지 한 번도 안 썼습니다 — 각자 자기 브랜치에 올리고 바로 병합해 왔습니다.

```
PR 에 담기는 것
  어느 브랜치를 → 어디로     feature/pro-rata-refund → main
  무엇이 바뀌었나            바뀐 파일·줄이 좌우로 나란히
  왜 바꿨나                  설명 (내가 씁니다)
  ★CI 결과                   시험이 통과했는지 초록/빨강
  대화                       나중에 "왜 이렇게 했더라" 를 되짚을 수 있습니다
```

### 흐름

```
main 에서 브랜치를 딴다
  ↓  작업 · 커밋 · push
PR 을 연다
  ↓  ★CI(자동 시험) 통과      ← ★유일한 관문
★squash merge — main 에 커밋 하나로 들어감
브랜치 자동 삭제 · ★자동배포
```

### ★리뷰 승인은 필요 없습니다 (0806 결정)

```
· 직접 push 금지 — PR 로만
· ★리뷰 승인 0명 — 본인이 열고 ★본인이 병합할 수 있습니다
· ★CI 통과가 병합 조건        ← 이것만 막습니다
· force push·삭제 금지
```

★**왜 승인을 0명으로 두나** — 5명 팀에서 **자기 PR 은 자기가 승인할 수 없어**(GitHub 제품 규칙)
새벽에 급한 수정을 하면 아침까지 배포가 막힙니다. **CI 관문은 그대로 두고 사람은 안 기다립니다.**

### 명령 두 줄이면 끝납니다

```bash
git switch -c fix/payment-refund && git push -u origin HEAD
```

```bash
gh pr create --fill && gh pr merge --auto --squash
```

★`--auto` 를 걸어 두면 **그 뒤로 손댈 게 없습니다.** CI 가 6분 뒤 통과하면
저절로 병합되고 배포됩니다. 기다릴 필요도 없습니다.

### 그러면 직접 push 와 무엇이 다른가

```
직접 push       깨진 코드도 그냥 들어갑니다   ← 8/5~8/6 이 그랬습니다
PR + CI 필수    ★깨진 코드는 병합 버튼이 막힙니다
```

혼자 하는 건 똑같은데 **관문이 하나 생기는 것**입니다. 덤으로 남는 것도 있습니다.

```
★되돌리기    squash 로 커밋 하나 → git revert 한 줄
★기록        무엇이 왜 바뀌었나 · CI 결과 · 그때의 판단
```

⚠️**staging 환경이 없어서 `main` 병합이 곧 실서비스 배포입니다.**
그래서 CI 를 반드시 통과해야 합니다.

### CI 는 무엇을 하나

백엔드는 push 할 때마다 **전체 시험(437개)** 이 자동으로 돕니다(`pytest`). 5~7분 걸립니다.
빨간불이면 PR 을 병합할 수 없습니다.

⚠️**8월 5일부터 8월 6일까지 CI 가 빨간불이었습니다.** 코드 문제가 아니라 **시험이 옛 정책을
검사하고 있어서**였습니다(환불이 진행률 기반 비율 환불로 바뀐 것을 시험이 안 따라감).

우리가 지금 만드는 것은 **새로 지어낸 규칙이 아닙니다.** 이름이 있고, 지금 업계에서 제일 많이 쓰는 방식입니다.

### ★GitHub Flow (트렁크 기반)

```
main 하나가 ★항상 배포 가능한 상태
   → 짧게 브랜치를 딴다 → PR → CI → 병합 → 배포 → ★브랜치 삭제
```

GitHub·Netflix·토스·당근 같은 곳이 이 방식입니다.
**웹 서비스처럼 하루에도 여러 번 배포하는 곳의 기본형**입니다.

★핵심은 딱 하나입니다 — **오래 사는 브랜치를 만들지 않는다.**
브랜치가 길어질수록 `main` 과 벌어지고, 나중에 합칠 때 충돌이 커집니다.

### 다른 방식도 있습니다 — ★Git Flow

```
main / develop / release/* / hotfix/* / feature/*
2010년에 나와 크게 유행했습니다
```

⚠️**원작자가 2020년에 직접 「웹 앱에는 쓰지 마라」고 덧붙였습니다.**
배포가 잦으면 `develop → release → main` 을 오가는 비용만 커지기 때문입니다.

지금도 Git Flow 를 쓰는 곳은 **버전을 찍어 내보내는 제품**입니다.

```
쓰는 곳    설치형 소프트웨어 · 앱스토어 심사가 있는 모바일 · 펌웨어
           → "v1.4.2 를 언제 내보낼지" 를 사람이 정해야 하는 제품
안 쓰는 곳  ★우리처럼 서버에 바로 올리는 서비스
```

★**우리 저장소에 `develop` 이 있는 건 초기에 Git Flow 로 시작했다가 아무도 안 쓰게 된 흔적입니다.**
실제로 `develop` 은 **6/29 커밋에서 멈춰 있습니다.** 그래서 없앱니다.

### ★실무에서 더 붙이는 것들 — 우리가 「일부러」 뺀 것

| 실무에서 흔한 것 | 우리 | 언제 넣나 |
|---|---|---|
| 리뷰 승인 1~2명 | ★0명 | ⬜팀이 8명을 넘으면 1명으로 |
| staging 환경 | ★없음 (병합 = 실서비스) | ⬜결제·개인정보를 더 건드리면 |
| CODEOWNERS (파일별 담당자 자동 지정) | 없음 | ⬜사람이 늘면 |
| 릴리스 태그 `v1.2.0` | 없음 | ⬜지금은 squash 커밋 하나가 그 역할 |
| feature flag (코드는 올리고 기능은 꺼 둠) | 없음 | ⬜큰 기능을 여러 명이 나눠 만들 때 |
| merge queue (순서대로 CI 돌려 병합) | 없음 | ⬜동시에 PR 이 여러 개 쌓이면 |

★**빠뜨린 게 아니라 미룬 것입니다.**
5명이 하루 몇 번 배포하는 지금 규모에서 이것들은 **안전을 늘리는 것보다 속도를 깎는 쪽이 큽니다.**

⚠️다만 **staging 이 없다는 것은 실제 약점입니다.** `main` 병합이 곧 실서비스입니다.
그래서 **CI 를 유일한 관문으로 두고 반드시 통과시키는 것**이고,
**프론트는 배포 뒤 사람이 화면을 한 번 열어 봐야 합니다**(프론트 CI 에 동작 시험이 없음).

### ★규모가 커지면 이렇게 갑니다

```
5명 (지금)   main + 짧은 브랜치 · 승인 0명 · CI 만 관문
20명         승인 1명 · CODEOWNERS · staging 환경
100명+       merge queue · 배포를 10% → 50% → 100% 로 단계별 확대
```

★**바뀌는 건 관문의 개수지 뼈대가 아닙니다.**
`main 하나 + 짧은 브랜치 + PR` 은 끝까지 그대로 갑니다.
그래서 **지금 이 모양으로 잡아 두면 나중에 갈아엎을 일이 없습니다.**

### ★이건 그대로 경력이 됩니다

```
지금까지     자기 이름 브랜치에 직접 push → 바로 병합
앞으로       ★PR 로 협업 · ★CI 통과 후 자동 배포 · ★squash 로 이력 관리
```

★**「PR 기반 협업」·「CI/CD 파이프라인」은 이력서와 면접에서 그대로 물어보는 항목입니다.**
설명할 수 있는 경험의 종류가 달라집니다.

## 6. 자주 나올 질문

**Q. 내 브랜치가 없어지나요?**
아니요. 작업 중인 브랜치는 그대로 두고, 멈춘 브랜치는 `catchap-legacy` 로 **옮깁니다**(삭제 아님).
커밋 해시까지 그대로 남습니다.

**Q. ★PR 을 병합하면 제 작업 브랜치가 자동으로 지워진다던데요?**
맞습니다. **병합이 끝난 브랜치만** 자동으로 지워집니다. 놀라실 수 있어 자세히 적습니다.

```
지워지는 것    ★병합이 끝난 그 작업 브랜치 하나 (feature/… · fix/…)
안 지워지는 것  main · 아직 병합 안 한 브랜치 · 남의 브랜치
언제           PR 이 ★병합된 직후에만. 직접 push 로 합친 브랜치는 안 건드립니다
```

★**커밋은 하나도 안 사라집니다.** 브랜치는 커밋을 가리키는 **이름표**일 뿐이고,
그 커밋들은 이미 `main` 안에 들어가 있습니다. 이름표만 치우는 것입니다.

★**되살릴 수도 있습니다.** GitHub 설정 화면 안내 그대로입니다 —
*"Deleted branches will still be able to be restored"*. PR 화면 아래에
**[Restore branch]** 버튼이 계속 남아 있습니다.

★**왜 켜나** — 안 켜면 병합된 브랜치가 계속 쌓입니다. 지금 저장소마다 브랜치가
9~14개인데, 그중 상당수가 **이미 병합이 끝난 것**입니다. 그대로 두면 몇 달 뒤에
지금 같은 정리를 또 하게 됩니다.

⚠️**로컬에 남은 브랜치는 자동으로 안 지워집니다.** 내 컴퓨터에서는 이렇게 치웁니다.

```bash
git fetch --prune          # 원격에서 사라진 브랜치 정보 정리
git branch -d fix/payment-refund   # 로컬 브랜치 삭제 (병합 안 됐으면 거부합니다)
```

**Q. 옛날 코드를 다시 봐야 하면?**
`catchap-legacy` 에 `<출처>/<원래이름>` 으로 있습니다. `git log`·`git show` 그대로 됩니다.

**Q. 저장소 이름이 바뀌면 지금 clone 이 깨지나요?**
바로는 안 깨집니다(GitHub 이 넘겨 줍니다). 그래도 `git remote set-url` 로 고쳐 두세요.

**Q. `main` 에 직접 못 올리면 급할 때는요?**
`hotfix/<요약>` 브랜치로 PR 을 열면 됩니다. **승인이 필요 없어서** CI 만 통과하면 바로 병합됩니다.
`gh pr merge --auto --squash` 를 걸어 두면 CI 가 끝나는 대로 저절로 나갑니다.

**Q. 화면이 깨졌는지는 누가 보나요?**
★**사람이 봅니다.** 프론트 CI 는 `lint + 타입검사 + 빌드`까지만 봅니다 — **동작 시험이 없습니다.**
버튼이 안 눌려도·화면이 비어도 초록불이 뜹니다. 배포 뒤에 한 번 열어 봐 주세요.

**Q. squash merge 면 제 커밋이 하나로 합쳐지나요?**
`main` 이력에서는 하나로 보입니다. **PR 안에는 중간 커밋이 그대로 다 있습니다** —
`main` 커밋 제목에 PR 번호가 붙어서, 클릭 한 번으로 원래 커밋을 볼 수 있습니다.

```
main 이력   "무엇이 언제 나갔나"     — 한 기능 = 한 커밋
PR         "어떻게·왜 만들어졌나"   — 중간 커밋 · CI 결과 · 그때의 대화
```

**Q. ★squash 하면 「누가 했는지」가 사라지나요?**
아니요. **작성자는 그대로 남습니다.**

```
작업할 때   커밋 5개 (오타 고침 · 되돌림 · 다시 고침 …)
병합되면    main 에 커밋 ★1개
            작성자 = ★PR 을 낸 사람 — GitHub 이 그대로 넣습니다
            둘이 같이 했으면 ★Co-authored-by 로 ★둘 다 남습니다
```

★**GitHub 기여 그래프(잔디)에도 그대로 반영됩니다.** 커밋 수가 줄어 보이는 대신
**「한 기능 = 한 커밋」이 되어 무엇을 했는지가 오히려 또렷해집니다.**

★**되돌릴 때 편합니다** — `git revert <커밋 1개>` 로 그 작업만 통째로 빠집니다.
커밋 5개를 하나씩 되돌릴 필요가 없습니다.

**Q. 언제 바뀌나요?**
저장소를 만들고 이름을 바꾸는 것부터 시작합니다. **작업 중인 브랜치는 그 전에 올려 두시면**
헷갈릴 일이 없습니다.
