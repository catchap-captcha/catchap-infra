받는 사람: **ms님** (캡차 담당) · 참고: sw님

## 요약

새 환경으로 옮기려고 캡차 서비스(`drag-captcha`)의 Dockerfile을 만들고 실제로 띄워 봤습니다.
그 과정에서 **DB 계정 권한을 하나 바꿔야 했고**, 그 이유를 공유합니다.

**바꾼 것** — `catchap_captcha_app` 계정에 `CREATE`·`ALTER`·`INDEX`·`REFERENCES` 추가
**왜** — 캡차 서비스가 기동할 때마다 스키마를 만들기 때문
**ms님이 하실 일** — 없습니다. 알고만 계시면 됩니다.

## 1. 무슨 일이 있었나

새 관리형 MySQL(`catchap_captcha`)에 붙여 서비스를 띄웠더니 **기동이 실패했습니다.**

```
(1142, "CREATE command denied to user 'catchap_captcha_app' for table 'captcha_questions'")
```

원인을 찾아보니 `app/db.py`의 `initialize()`가 기동할 때마다 이걸 합니다.

```python
def initialize(self):
    GET_LOCK('security_captcha_v2_schema', 20)
    for statement in SCHEMA: cur.execute(statement)    # CREATE TABLE IF NOT EXISTS × 14
    # 기존 DB용 멱등 마이그레이션(컬럼 이미 있으면 무시)
    for alter in (...6개...):
        try: cur.execute(alter); conn.commit()
        except Exception: conn.rollback()
    RELEASE_LOCK(...)
```

새 환경에서 만든 DB 계정은 **DML(SELECT·INSERT·UPDATE·DELETE)만** 갖고 있었습니다.
DB를 바꾸는 권한은 배포 전용 계정에만 주는 구성이었는데, 이 서비스는 앱이 직접 하니 안 맞았습니다.

### 그래서 권한을 맞췄습니다

```
전  GRANT SELECT, INSERT, UPDATE, DELETE ON `catchap_captcha`.*
후  GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, REFERENCES, INDEX, ALTER ON `catchap_captcha`.*
```

- **`catchap_captcha` 이 DB 하나에만** 줬습니다. 다른 DB는 여전히 목록에도 안 보입니다.
- **`DROP`은 안 줬습니다.** 표를 지울 이유가 없어서입니다.
- `REFERENCES`는 스키마에 외래키가 있어서 필요했습니다.

**코드는 하나도 안 고쳤습니다.** 서비스 쪽 설계를 존중하고 권한을 맞추는 쪽을 택했습니다.

### 확인

권한을 준 뒤 새 DB에 붙여 실제로 요청을 받았습니다.

```
/health/live   200  {"status":"ok"}
/health/ready  200  {"status":"ok","database_ready":true,"approved_questions":true,...}
/api/config    200  {"siteKey":"public-demo-key","embedOrigins":[]}
```

★`approved_questions: true` — 새 DB에 활성 문항이 옮겨져 있고 앱이 찾았습니다.

## 2. 두 방식이 다릅니다 — 알아 두시면 좋을 것

CatChap 안에서 스키마를 관리하는 방식이 서비스마다 다릅니다.
둘 다 흔한 방식이고 **어느 쪽이 틀린 게 아니라 트레이드오프가 다릅니다.**

| | **캡차 — 앱이 직접** | **백엔드 — alembic** |
|---|---|---|
| 언제 도나 | 앱 기동할 때마다 | 배포 절차에서 `alembic upgrade head` 한 번 |
| 무엇을 | `CREATE TABLE IF NOT EXISTS` + 멱등 `ALTER` | 버전 파일을 순서대로 |
| **지금 어느 스키마인지** | 알 방법 없음 | `alembic_version` 표에 기록 |
| **되돌리기** | 없음 (손으로) | `downgrade()` 가 파일마다 |
| 순서 보장 | 코드에 적힌 순서 | `down_revision` 사슬로 강제 |
| **필요 권한** | **앱 계정에 DDL** | 배포 계정만 DDL |
| 실패하면 | `CREATE`=기동 실패 / **`ALTER`=조용히 넘어감** | 배포가 멈추고 원인이 보임 |
| 파드 여러 개 동시 기동 | ✅ `GET_LOCK`으로 안전 | 해당 없음 |

### 캡차 방식이 나은 점

- **배포가 한 단계입니다.** 앱만 띄우면 끝이라 마이그레이션 실행을 잊을 수가 없습니다.
  백엔드는 `alembic upgrade head`를 잊으면 없는 컬럼을 찾다 터집니다.
- **도구를 안 배워도 됩니다.** alembic은 버전 사슬·head 관리를 알아야 합니다.
  (실제로 오늘 저도 head를 찾다 한 번 오판했습니다)
- **개발이 빠릅니다.** DB 지우고 다시 띄우면 스키마가 알아서 생깁니다.

### alembic 쪽이 나은 점

- **이력이 남습니다.** 지금 DB가 어느 스키마인지 한 줄로 압니다.
- **되돌릴 수 있습니다.**
- **앱 계정에 DDL이 필요 없습니다.**

★**`GET_LOCK`을 쓴 건 잘 되어 있습니다.** 쿠버네티스에서 파드를 2벌 띄우면 둘이 동시에
기동하는데, 락이 없으면 같은 `CREATE`/`ALTER`가 겹쳐 이상하게 실패할 수 있습니다.
이 부분은 그대로 두면 됩니다.

## 3. 한 가지만 제안드립니다 — 급하지 않습니다

```python
try: cur.execute(alter); conn.commit()
except Exception: conn.rollback()      # ← 여기
```

이 `except Exception`이 **"컬럼이 이미 있음"과 "권한 없음"과 "문법 오류"를 똑같이 삼킵니다.**

오늘 우리 경우가 정확히 갈렸습니다.

- `CREATE`는 예외를 안 잡아서 **기동이 실패** → 무엇이 문제인지 바로 알았습니다
- `ALTER`는 삼킵니다 → 만약 **`ALTER` 권한만 없었다면 앱이 정상으로 뜨고**,
  컬럼이 없는 채로 돌다가 나중에 쿼리에서 터졌을 겁니다

시끄럽게 실패한 게 오히려 다행이었습니다.

**제안** — 컬럼 중복(에러 1060)일 때만 넘어가고 나머지는 그대로 터뜨리는 것입니다.
방식은 그대로 두고 조용한 실패만 없앱니다.

```python
import pymysql
try:
    cur.execute(alter); conn.commit()
except pymysql.err.OperationalError as e:
    conn.rollback()
    if e.args[0] != 1060:   # 1060 = Duplicate column name (이미 있으면 정상)
        raise
```

**지금 하실 필요는 없습니다.** 이전 중에 동작을 바꾸면 문제가 생겼을 때
"옮겨서 그런지 고쳐서 그런지"를 못 가립니다. 이전이 끝난 뒤에 보시면 됩니다.

## 4. 이전하면 달라지는 것

| | 지금 (옛 GPU) | 이전 후 |
|---|---|---|
| 어떻게 뜨나 | `ms` 계정이 손으로 `uvicorn` 실행 | 쿠버네티스가 띄우고 유지 |
| 서버 재부팅하면 | ★**안 올라옵니다** (systemd 유닛 없음) | 자동으로 다시 뜸 |
| 몇 벌 | 1벌 | 2벌 (서로 다른 건물의 서버에) |
| 죽으면 | 아무도 모름 | 자동 재시작 + 다른 벌이 받음 |
| 주소 | `61.109.239.231:8000` (인터넷에 그대로 열림) | `captcha.catchap5.com` (HTTPS) |
| DB | 옛 DB 서버 `captcha_ms` | 관리형 MySQL `catchap_captcha` |
| 문항 이미지 | 서버 디스크 `data/final` | 우선 이미지에 담고, 나중에 Object Storage |

### 이미지에 담는 자산은 349MB만입니다

서버의 `data/final`은 **3.5GB · 69,111개**인데, DB가 실제로 가리키는 건 이만큼입니다.

```
문항 이미지 (status='active')   151 MB · 1,796개
조각        (piece_path)        198 MB · 6,442개
─────────────────────────────────────────
합계                            349 MB · 8,238개
```

나머지는 비활성 문항(4,900개)·원본·라벨링 중간산물이라 서비스가 열지 않습니다.
`scripts/collect_active_assets.sh`가 DB를 조회해 그 목록만 뽑습니다(읽기만 합니다).

★**문항을 추가하거나 비활성을 활성으로 바꾸면 이미지를 다시 구워야 합니다.**
그게 불편해지면 Object Storage에서 읽도록 바꾸겠습니다(백엔드가 이미 그렇게 합니다).

### 런타임 이미지에서 뺀 것

`requirements.txt`의 `ultralytics`·`opencv`·`numpy`·`pandas`는 **`app/`에서 import가 0건**이고
전부 `scripts/`의 문항 생성·라벨링 도구가 쓰는 것이라 런타임 이미지에서 뺐습니다.

```
서버의 venv        5.6 GB
런타임 의존성만     55 MB
```

`scripts/`를 돌리실 때는 지금처럼 개발 환경에서 하시면 됩니다.
**틀렸으면 알려 주세요** — 제가 못 본 경로가 있을 수 있습니다.
