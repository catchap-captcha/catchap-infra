# 앞으로 이렇게 작업합니다 — 커밋 · 푸시 · PR

이 문서는 **손으로 무엇을 치는지**만 적었습니다. 위에서 아래로 따라가면 한 바퀴가 끝납니다.

```
왜 이렇게 바뀌나          → 04-깃허브-재설계-팀원설명.md
★실무에서는 어떻게 쓰나   → 04 의 ★5-2장 (GitHub Flow · 우리가 뺀 것 · 규모가 커지면)
```

## 0. 딱 한 번만 하는 준비

### 저장소 주소 고치기 (이름이 바뀐 저장소만)

```bash
# ai-service 를 쓰시던 분
git remote set-url origin https://github.com/catchap-captcha/catchap-captcha.git

# catchap-service 를 쓰시던 분
git remote set-url origin https://github.com/catchap-captcha/catchap-legacy.git

```

### GitHub CLI 설치·로그인 (PR 을 명령으로 열려면)

```bash
gh auth login
```

★화면에서 눌러도 됩니다. `gh` 는 **빠르게 하려는 분만** 쓰시면 됩니다.

### ★내 로컬을 최신으로 — 이건 꼭 해 주세요

```bash
git fetch --all --prune
git switch main
```

⚠️★**기본 브랜치가 `develop` → `main` 으로 바뀌었습니다(0806).**
**이미 clone 해 두신 분은 자동으로 안 바뀝니다.** 위 두 줄을 한 번 실행해 주세요.

★`main` 에는 **여러분 커밋이 전부 들어가 있습니다** — `develop` 에 있던 것도, 각자 이름
브랜치에 있던 것도 그대로입니다. 새로 받으실 필요 없습니다.

## 1. 한 바퀴 — 이게 전부입니다

```bash
# ① main 최신으로
git switch main
git pull

# ② 작업 브랜치 만들기
git switch -c fix/payment-refund

# ③ 작업 · 커밋
git add -A
git commit -m "fix(payments): 환불 금액을 정수 연산으로"

# ④ 올리기
git push -u origin HEAD

# ⑤ PR 열고 자동 병합 걸기
gh pr create --fill
gh pr merge --auto --squash
```

여기까지가 **사람 몫**입니다. 그 뒤는 저절로 굴러갑니다.

```
⑥ CI 가 돎        백엔드 pytest 437개 5~7분 · 프론트 lint+타입검사+빌드 2~3분
⑦ 초록이면        ★저절로 main 에 병합 · ★작업 브랜치 자동 삭제
⑧ 배포            main 이 바뀌면 이미지 빌드 → 쿠버네티스에 반영
```

★**⑤ 다음은 손댈 게 없습니다.** 자고 일어나면 배포돼 있습니다.

⚠️**⑧ 자동 배포는 아직 안 붙었습니다.** 인프라 쪽 마지막 단계(ArgoCD)입니다.
그때까지는 **병합까지만 자동**이고, 실서버 반영은 인프라 담당이 손으로 합니다.

★**그래서 GitHub 이 이런 곳이 됩니다**

```
main       ★지금 서비스되는 코드 — 여기와 실서버가 항상 같습니다
브랜치      ★지금 누가 무엇을 만들고 있는지가 목록 그대로 보입니다
PR         ★무엇을 왜 바꿨나 · CI 결과 · 나중에 되짚을 대화
```

`jy`·`ms`·`sw` 는 봐도 **무슨 작업인지 알 수 없고, 그 사람이 없으면 아무도 못 건드립니다.**
`fix/lecture-gate` 는 **이름만 보고 알고, 누구든 이어받을 수 있습니다.**

## 2. 브랜치 이름 규칙 — ★실무 표준 그대로입니다

```
feature/<요약>     새 기능        feature/portone-refund
fix/<요약>         버그 수정      fix/lecture-gate
hotfix/<요약>      급한 수정      hotfix/login-500
chore/<요약>       빌드·설정      chore/update-deps
docs/<요약>        문서만         docs/api-guide
```

★요약은 **영문 소문자·하이픈**으로 씁니다(도구가 한글 브랜치 이름에서 자주 걸립니다).
**커밋 메시지는 한국어**로 씁니다.

★**앞의 `feature/`·`fix/` 를 왜 붙이나** — GitHub 이 `/` 를 **폴더처럼 접어서** 보여 줍니다.
가지가 30개여도 **네 덩어리로 접혀** 목록이 안 지저분해집니다.

### ★왜 사람 이름을 안 쓰나 — 네 가지

지금 우리 저장소는 `jy`·`sw`·`ms`·`my` 입니다. **실무에서 이렇게 쓰는 곳은 사실상 없습니다.**

```
① 이름만 봐선 무슨 작업인지 모릅니다
   "jy 에 지금 뭐가 있나?"  →  ★열어 봐야 압니다

② 한 사람이 두 가지를 동시에 못 합니다
   결제를 고치는 중에 급한 로그인 버그가 오면 → ★한 브랜치에 섞입니다
   기능별이면 fix/login-500 을 따로 따서 ★그것만 먼저 내보냅니다

③ 그 사람이 없으면 아무도 못 건드립니다
   "jy 브랜치를 내가 이어서 해도 되나?" 를 ★물어봐야 합니다

④ 영원히 안 없어집니다
   기능 브랜치는 병합되면 ★사라집니다. 사람 브랜치는 계속 남습니다
   → 지금 저장소마다 가지가 ★9~14개인 이유가 이것입니다
```

### 그러면 「누가 했는지」는 어디서 보나

★**브랜치 이름이 아니라 커밋과 PR 에서 봅니다. 이게 원래 자리입니다.**

```bash
git log --author=leqsss           # leqsss 님이 한 커밋 전부
git blame src/pages/Login.tsx     # ★이 줄을 누가·언제·왜 바꿨나
git shortlog -sn                  # 사람별 커밋 수
```

```
GitHub 화면
  Pull requests        누가 무엇을 열고 병합했나
  Insights → Contributors   사람별 기여량 그래프
  파일 화면 → Blame     ★줄 단위로 작성자와 그때의 커밋
```

★**브랜치 이름으로 사람을 구분하는 건 오히려 정보가 적습니다.**
`jy` 는 「jy님이 뭔가 했다」까지만 알려 줍니다.
커밋 이력은 **누가·언제·어느 줄을·왜** 를 전부 알려 줍니다.

### 실무에서 더 하는 것 · 우리가 안 하는 것

```
★티켓 번호를 붙이는 곳이 많습니다
   feature/CAT-142-portone-refund
   → Jira·Linear 같은 걸 쓰면 ★PR 이 티켓에 자동으로 연결됩니다
   ⬜우리는 아직 티켓 도구가 없어서 안 넣었습니다

⚠️<이름>/<기능> 형태는 실무에서도 씁니다
   jy/portone-refund     ← 개인 실험 브랜치를 구분하려는 목적
   ★우리는 안 씁니다 — 기능만 봐도 충분하고,
     접히는 덩어리가 ★사람 수만큼 늘어납니다
```

⚠️`jy`·`sw`·`ms`·`my` 같은 **사람 이름은 더 이상 만들지 않습니다.**
**이미 있는 것은 지우지 않고 `catchap-legacy` 로 옮깁니다** — 커밋 하나도 안 잃습니다.

## 3. 커밋 메시지 — 지금 쓰는 방식 그대로입니다

```
<종류>(<범위>): <무엇을 했나>

종류   feat 새 기능 · fix 버그 · docs 문서 · chore 설정 · refactor 정리 · test 시험
범위   payments · lectures · ops · captcha · alerts …
```

**보기**

```
feat(alerts): Alertmanager 경보를 운영자 콘솔 벨·메일로 전달
fix(payments): 비율 환불 금액 정수 연산(2/3 곱 float 1원 내림 방지)
docs(dba): 코스 썸네일 컬럼 추가 요청 SQL
```

★**「왜」를 본문에 적어 두면 6개월 뒤 자기 코드를 볼 때 도움이 됩니다.**

```bash
git commit -m "fix(payments): 환불 금액을 정수 연산으로" -m "float 곱셈이 3만원에서 19,999원으로 1원 내려갔다. 정수 연산으로 바꿔 막는다."
```

## 4. PR — 무엇이고 왜 쓰나

**PR(Pull Request) = 「내가 만든 것을 `main` 에 넣어 달라」는 요청서**입니다.

```
담기는 것   어느 브랜치를 → 어디로 · 무엇이 바뀌었나 · 왜 바꿨나
           ★CI 결과(시험 통과 여부) · 나중에 되짚을 대화
```

### 명령으로 여는 법

```bash
gh pr create --fill                 # 커밋 메시지로 제목·본문을 채움
gh pr create --web                  # 브라우저에서 직접 쓰고 싶을 때
gh pr merge --auto --squash         # CI 통과하면 저절로 병합
gh pr status                        # 내 PR 상태 보기
gh pr checks                        # CI 결과만 보기
```

### 화면으로 여는 법

```
push 하면 GitHub 저장소 첫 화면에 ★노란 띠가 뜹니다
  "<브랜치> had recent pushes"  →  [Compare & pull request]
제목·설명 쓰고  →  [Create pull request]
CI 초록이 되면  →  [Squash and merge]
```

### ★승인은 필요 없습니다

```
· 직접 push 금지 — PR 로만
· ★리뷰 승인 0명 — 본인이 열고 ★본인이 병합할 수 있습니다
· ★CI 통과가 유일한 관문
· force push·삭제 금지
```

★**왜 승인 0명인가** — 5명 팀에서 **자기 PR 은 자기가 승인할 수 없어**(GitHub 규칙)
새벽에 급한 수정이 아침까지 막힙니다. CI 관문은 그대로 두고 사람은 안 기다립니다.

## 5. CI — 무엇을 검사하나

```
백엔드   pytest ★437개 — 실제로 돌려서 동작을 봅니다. 5~7분
프론트   npm ci → lint → 타입검사 + 빌드. 2~3분
         ⚠️동작 시험이 ★없습니다 — 빌드가 되면 초록입니다
```

⚠️★**「CI 초록」은 「우리가 시험으로 적어 둔 것만 괜찮다」는 뜻**입니다.
**프론트는 배포 뒤에 화면을 한 번 열어 봐 주세요.** 버튼이 안 눌려도 CI 는 초록입니다.

### 빨간불이 뜨면

```bash
gh pr checks                        # 무엇이 실패했나
gh run view --log-failed            # 실패한 줄만 보기
```

로컬에서 미리 돌려 보는 것이 제일 빠릅니다.

```bash
# 백엔드
pytest -q

# 프론트
npm run lint && npm run build
```

## 6. 병합 뒤 — 내 로컬 정리

원격 브랜치는 **자동으로 지워집니다.** 내 컴퓨터는 자동이 아닙니다.

```bash
git switch main
git pull
git fetch --prune                       # 원격에서 사라진 브랜치 정보 정리
git branch -d fix/payment-refund        # 로컬 브랜치 삭제
```

★`-d`(소문자)는 **병합이 안 된 브랜치면 거부**합니다 — 실수로 작업을 날리지 않게 해 줍니다.

## 7. 자주 막히는 자리

**Q. `main` 에 직접 push 했더니 거부당했습니다**
정상입니다. 브랜치를 따서 PR 로 올리세요.

```bash
git switch -c fix/<요약>
git push -u origin HEAD
```

**Q. 작업 중에 `main` 이 앞서 나갔습니다**

```bash
git fetch origin
git rebase origin/main          # 내 커밋을 최신 main 위로 옮김
# 충돌이 나면 고치고
git add -A && git rebase --continue
git push --force-with-lease     # 내 브랜치에만 씁니다. main 에는 절대 안 씁니다
```

⚠️`--force-with-lease` 는 **남이 그 사이에 올린 게 있으면 거부**합니다. 그냥 `--force` 는 쓰지 마세요.

**Q. 커밋 메시지를 잘못 썼습니다 (아직 push 전)**

```bash
git commit --amend -m "올바른 메시지"
```

**Q. 실수로 커밋했습니다 (아직 push 전)**

```bash
git reset --soft HEAD~1     # 커밋만 취소, 변경 내용은 남김
```

**Q. 배포된 것을 되돌려야 합니다**

```bash
git switch -c hotfix/revert-<요약> main
git revert <커밋해시>          # squash 병합이라 커밋 하나만 되돌리면 됩니다
git push -u origin HEAD
gh pr create --fill && gh pr merge --auto --squash
```

**Q. 내 브랜치가 legacy 로 갔는데 다시 봐야 합니다**

```bash
git remote add legacy https://github.com/catchap-captcha/catchap-legacy.git
git fetch legacy
git switch -c 되살리기 legacy/catchap-backend/th-before
```

                                 (지운다고 이력에서 사라지지 않습니다 — 키를 바꿔야 합니다)
