## 1장 — 인프라 기초

한 문장 정의: "우리 코드가 실제로 돌아가는 남의 컴퓨터들, 그리고 그것들을 잇는 배선".

사용자 요청이 지나가는 길 4단계를 도식으로:
사용자 → 입구(로드밸런서) → 앱(프론트·백엔드) → 데이터(데이터베이스)

용어를 설명하는 작은 사전을 만들어 주세요. **본문에서 이 말들이 계속 나옵니다.
여기서 뜻을 모르면 뒤를 못 읽습니다.**

**★사전은 순서가 중요합니다.** 앞의 말로 뒤의 말을 설명할 수 있게 이 차례로 놓아 주세요.

| 말 | 뜻 |
|---|---|
| **이미지** | 앱과 실행에 필요한 것(파이썬·라이브러리·설정)을 통째로 담아 굳혀 둔 **한 덩어리 파일**. 요리로 치면 **밀키트** |
| **컨테이너** | 그 이미지를 실제로 **실행한 것**. 밀키트를 뜯어 조리한 상태. 같은 이미지로 몇 개든 똑같이 만들 수 있음 |
| **레지스트리** | 이미지를 올려 두고 서버들이 받아 가는 **창고**. GitHub이 코드 창고라면 레지스트리는 이미지 창고 |
| **쿠버네티스** | 컨테이너를 대신 돌봐 주는 **관리인**. 죽으면 자동으로 다시 띄우고, 몇 개를 띄울지 지켜 줌 |
| **파드** | 쿠버네티스가 앱을 띄우는 단위. **컨테이너 한 개**라고 생각하면 됨 |
| **네임스페이스** | 쿠버네티스 안을 나누는 ★**칸막이**. 건물 하나에 층이 여럿인 것과 같음. 우리 앱은 전부 `catchap` 이라는 구역에 있음. ⚠️**칸막이지 벽은 아님** — 구역이 달라도 서로 부를 수 있어서, 막으려면 따로 설정해야 함 |
| **PDB** (중단 허용치) | ★**"정비하더라도 최소 몇 벌은 살아 있어야 한다"** 는 규칙. 당직 규칙과 같음. 서버를 정비하려고 비울 때 앱이 **한꺼번에 다 내려가는 것을 막음**. ⚠️서버가 **고장 나서** 죽는 건 못 막음 — 그건 건물(가용 영역)을 나눠 둔 것이 맡음 |
| **노드 · 워커** | 쿠버네티스가 파드를 올려 두는 **서버**. 우리 VM과 같은 가상 서버인데 부르는 이름만 다름. 실제로 앱이 도는 노드를 **워커**라고 부름 — 본문에서 "워커 2대"는 **서버 2대**라는 뜻 |
| **인그레스** | **어느 주소가 어느 앱으로 갈지** 정하는 쿠버네티스 설정. `api.catchap5.com`은 백엔드로, 나머지는 프론트로. ★**규칙을 적어 둔 「종이」일 뿐** |
| **인그레스 컨트롤러** | ★**그 종이를 읽고 실제로 보내 주는 프로그램.** 규칙만 있고 이게 없으면 **아무 일도 안 일어남**. 우리는 `ingress-nginx` 를 씀 |
| **로드밸런서** | 바깥에서 들어오는 요청을 받아 **살아 있는 서버에 나눠 주는 입구**. 죽은 서버에는 안 보냄. **건물 하나 안에서만** 나눠 줌 |
| **리스너** | 로드밸런서에 달린 **접수 창구**. *"80번 포트로 온 것은 여기로"* 를 정함. **HTTPS 인증서가 붙는 자리** |

| **관리형 서비스** | 잃으면 안 되는 것을 **카카오클라우드가 대신 운영**. 백업·이중화가 자동으로 됨 |
| **컷오버(전환)** | 옛 환경에서 새 환경으로 **실제로 넘어가는 순간**. 우리 경우엔 **주소가 가리키는 곳을 바꾸는 일** 하나 |

### 용어 ② — 네트워크

**★`10.0.0.0/16` 같은 표기가 문서에 계속 나옵니다. 이것부터 설명해 주세요.**

| 말 | 한 줄 설명 |
|---|---|
| **VPC** | **우리만 쓰는 사설 네트워크.** 클라우드 안에 울타리를 치고 그 안에 서버를 놓는 것. 다른 조는 다른 VPC 라 우리 서버가 안 보입니다 |
| **CIDR (`10.0.0.0/16`)** | **주소 범위를 적는 방법.** `/16` 은 앞 16자리가 고정이라는 뜻이라 `10.0.0.0` ~ `10.0.255.255` 를 가리킵니다. `/24` 면 앞 24자리 고정이라 `10.0.2.0` ~ `10.0.2.255` — **256개짜리 한 칸** |
| **서브넷** | VPC 를 **더 작게 자른 칸.** 우리는 4칸(`10.0.1~2·5~6.0/24`). ★칸마다 **어느 건물(가용 영역)에 있는지**가 정해집니다 |
| **라우팅 테이블** | *"어디로 가려면 어느 길로 나가라"* 를 적어 둔 표. ★**퍼블릭이냐 프라이빗이냐를 가르는 것이 이름이 아니라 이 표**입니다 |
| **인터넷 게이트웨이** | 네트워크와 인터넷을 잇는 문. 라우팅 표에 이 문이 적혀 있으면 그 서브넷은 **퍼블릭 서브넷** |
| **보안 그룹** | 서버 앞에 붙는 **방화벽.** *"어디서 오는 몇 번 포트를 받을지"* 를 정합니다. 안 적힌 건 전부 막힙니다 |
| **포트** | 한 서버 안에서 **어느 프로그램에게 갈지** 정하는 번호. 웹은 `80`(평문)·`443`(암호화), 데이터베이스는 `3306` |
| **공인 IP / 사설 IP** | 공인은 **인터넷에서 닿는 주소**, 사설은 **우리 네트워크 안에서만** 쓰는 주소. ★공인 IP 가 없으면 밖에서 못 들어옵니다 |

### 용어 ③ — 비밀값 보관

| 말 | 한 줄 설명 |
|---|---|
| **시크릿(secret)** | 비밀번호·API 키처럼 **남이 보면 안 되는 값** |
| **Secrets Manager** | 그 값들을 **암호화해서 보관하는 금고.** 코드나 설정 파일에 적지 않고 여기서 꺼내 씁니다 |
| **KMS (암호화 키 관리)** | ★**금고를 잠그는 열쇠를 만들고 관리하는 곳.** 금고(Secrets Manager)와 열쇠(KMS)가 **따로 있습니다** |
| **액세스 키** | 프로그램이 자기를 밝힐 때 쓰는 **아이디와 비밀번호 한 쌍.** 사람의 로그인에 해당 |

### ★★왜 금고와 열쇠가 따로 있나 — 이 대목을 꼭 넣어 주세요

**처음 보면 「비밀값을 넣는 곳이 왜 두 개지」 싶습니다.**

```
Secrets Manager   값을 넣어 두는 금고
KMS               ★그 금고를 잠그는 열쇠
```

**이유는 「열쇠를 따로 관리해야 통제가 생기기」 때문입니다.**

```
열쇠가 금고 안에 있으면    금고에 접근하는 사람은 전부 값을 봄
열쇠를 따로 두면          ★금고에 닿아도 열쇠가 없으면 못 품
```

★**우리는 `kms11` 이라는 우리 전용 열쇠를 따로 만들었습니다.** 안 만들면 카카오가 주는
**기본 열쇠**를 쓰는데, 그건 **누가 쓸 수 있는지 우리가 못 정합니다.**

★**실제로 이걸로 한 번 걸렸습니다.** `catchap-ops` 계정으로 비밀값이 읽히길래
*"명단 추가가 필요 없다"* 고 적었는데, 알고 보니 **그 값이 기본 열쇠로 잠겨 있어서**였습니다.
`kms11` 로 다시 잠그니 **같은 계정이 거절당했습니다.**
→ **`kms11` 값을 읽으려면 `catchap-backend` 계정을 써야 합니다.**

★**이름이 `kms11` 인 이유** — 강사님이 만들어 두신 키가 `kms1`~`kms10` 까지 있어서
**겹치지 않는 다음 번호**를 골랐습니다. 뜻이 있는 이름은 아닙니다.

### 용어 ④ — 도메인

| 말 | 한 줄 설명 |
|---|---|
| **DNS** | **이름 → 주소** 변환표. `catchap5.com` 을 치면 어느 IP 로 갈지 알려 줍니다 |
| **A 레코드** | 이름에 **IP 를 직접** 적는 것. `catchap5.com → 210.109.55.233` |
| **CNAME** | 이름에 **다른 이름**을 적는 것. `www → 고가용성그룹주소`. ★IP 가 바뀌어도 우리가 안 고쳐도 됩니다 |
| **TTL** | *"이 답을 몇 초 동안 기억해도 되나"*. 우리는 **600초(10분)** — 바꾸면 늦어도 10분 안에 퍼집니다 |
| **MX 레코드** | **메일을 어디로 보낼지.** ★루트 도메인에 CNAME 을 못 붙이는 이유가 이것과 같이 못 있어서입니다 |
| **상태 확인 (헬스체크)** | 로드밸런서가 **몇 초마다 「살았니」 물어보는 것.** 죽은 서버를 명단에서 빼기 위해 |
| **리다이렉트 (301·308)** | *"여기 말고 저기로 가세요"* 라고 돌려보내는 응답. **308 은 방식과 본문을 그대로 유지**해서 301 보다 안전합니다 |
| **인증서 (TLS/SSL)** | *"이 사이트가 진짜 catchap5.com 이 맞다"* 를 증명하는 것. 주소창의 자물쇠. ★**2026년 10월 20일 만료** |

★**"이전"과 "컷오버"를 꼭 구분해서 써 주세요.** 자주 헷갈립니다.

```
이전     몇 주에 걸쳐 옮기는 일        지금까지 한 것이 전부 이것
컷오버   그 마지막에 한 번에 넘기는 순간  ★아직 안 했습니다
```

**컷오버는 도메인 레코드 3~4줄을 바꾸는 일**입니다. 그래서 **되돌리기도 그만큼**이고,
TTL 이 600초라 **10분이면 원래대로 돌아갑니다.**
문서 전체에서 이 말을 **"컷오버"로 통일**해 주세요 — "전환"과 섞어 쓰면 같은 것이
다른 것처럼 읽힙니다.

**이미지 → 컨테이너 관계는 그림으로도 보여 주세요.** 이 문서에서 가장 많이 나오는 말이라
여기서 확실히 잡아야 뒤가 편합니다.

```
   이미지 1개                        컨테이너 여러 개
   catchap-backend:5fb2b5d9   ──►   백엔드 파드 ①
   (한 번 구우면 안 바뀜)       ──►   백엔드 파드 ②
                                     같은 이미지 = 완전히 같은 앱
```

이 장의 결론 한 줄: **죽어도 되는 것(앱)은 쿠버네티스에, 죽으면 안 되는 것(데이터)은
관리형에 맡긴다. 그러면 서버 한 대가 꺼져도 서비스는 산다.**

## 2장 — 카카오클라우드에서 무엇을 빌려 쓰나

**설명 방식이 중요합니다.** 서비스 이름만 나열하지 말고,
**"이걸 안 쓰면 우리가 직접 해야 하는 일"**을 같이 적어 주세요.

먼저 한 문단: 우리는 서버실을 갖고 있지 않습니다. 카카오클라우드에서 필요한 만큼 빌려 쓰고,
어려운 부분(백업·이중화·보안)은 맡깁니다.

**★그리고 반드시 넣을 것 — "쓰는 중"과 "받아만 둔 것"을 구분하세요.**
신청은 했는데 아직 앱이 안 쓰는 서비스가 셋 있습니다. 그게 이번 이전의 큰 부분입니다.

| 서비스 | 우리가 받은 것 | 상태 | 안 쓰면 우리가 해야 할 일 |
|---|---|---|---|
| **Virtual Machine** | 서버 5대 (VM1~VM4, GPU) | 쓰는 중 | 컴퓨터를 사서 두고 전기·인터넷·고장까지 직접 관리 |
| **Kubernetes Engine** | `catchap-cluster-prod` 워커 2대 | **아직 안 씀** | 앱이 죽을 때마다 사람이 붙어서 다시 띄우기 |
| **MySQL (관리형)** | `mysql-team1` 서버 2대 이중화 | **아직 안 씀** | DB를 직접 설치·백업·이중화. 서버가 죽으면 밤에도 일어나야 함 |
| **MemStore (Valkey)** | `catchap-redis-prod` 2노드 | **안 씀 — 이유는 5장** | (지금은 없어도 됨. 트래픽이 늘면 쓸 자리가 있음) |
| **Object Storage** | `catchap-storage-prod-team1` | **아직 안 씀** | 영상·이미지를 서버 디스크에 저장 |
| **Container Registry** | `kc-sfacspace05.kr-central-2.kcr.dev` | 준비됨 | 만든 이미지를 서버마다 직접 복사 |
| **Load Balancer** | `210.109.55.233` | **아직 안 씀** | 사용자를 어느 서버로 보낼지 직접 나눠야 함 |
| **Secrets Manager** | 비밀값 5건 | 쓰는 중 | 비밀번호·API 키를 설정 파일에 평문으로 두게 됨 |
| **KMS (암호화 키)** | `kms11` | 쓰는 중 | 비밀값을 무엇으로 잠글지 직접 관리 |
| **IAM (계정·권한)** | 사람 5명, 기계 계정 3개 | 쓰는 중 | 누가 무엇을 할 수 있는지 관리할 방법이 없음 |
| **VPC (네트워크)** | `Team1-VPC` 서브넷 4개 (8/4 정리) | 쓰는 중 | 서버 연결과 방화벽을 직접 설계 |
| **Monitoring** | 서버·DB 지표 수집 | 쓰는 중 | 문제가 생겨도 사용자가 알려 줄 때까지 모름 |

이어서 왜 이 조합인지 한 문단:

> 규칙은 하나입니다. **직접 만들면 계속 돌봐야 하는 것은 빌려 씁니다.**
> 데이터베이스 이중화나 백업은 잘 만들기도 어렵고, 잘못되면 데이터를 잃습니다.
> 우리가 잘할 수 있는 건 서비스 코드지 데이터베이스 운영이 아닙니다.

**대가도 적어 주세요** — 관리형 데이터베이스는 서버 안에 들어가 볼 수 없고, 설정도 정해진
방법으로만 바꿉니다. **자유를 조금 내주고 안정을 받는 거래**입니다.

```
주소      console.kakaocloud.com
```

  비어 있으면 고장이 아니라 **아직 안 깐 것**입니다.
- ★**콘솔 홈의 숫자는 프로젝트 전체입니다.** `Instance 26` 같은 숫자에 **다른 조 것도
  포함**돼 있습니다. 우리 것만 보려면 각 서비스 메뉴로 들어가야 합니다.

## 4장 — 무엇이 문제인가 (5가지)

각각 "무엇이 문제인가" + **"왜 이렇게 됐나"**를 같이 씁니다. 뒤쪽이 중요합니다.

1. **서버 한 대가 죽으면 서비스가 멈춘다**
   백엔드가 한 대에만 있어서, 그 서버가 재부팅되면 사람이 살릴 때까지 서비스가 안 됨.
   *왜* — 서비스가 작을 땐 서버 하나에 하나씩 올리는 게 가장 빠른 선택이었음. 이제 기준이 달라짐.

2. **★앱이 서버 디스크에 파일을 쌓고 있다** ← 이번 이전의 핵심
   강의 영상·이미지 **3.3GB**가 백엔드 서버 안(`/app/media`)에 그냥 들어 있음.
   *왜 문제인가* — 이 상태로는 **쿠버네티스로 못 갑니다.**
   앱을 2벌 띄우면 각자 다른 디스크를 보게 되어,
   **한쪽에 올린 영상이 다른 쪽에서 안 보입니다.** 파드가 죽으면 파일도 같이 사라집니다.
   *왜 이렇게 됐나* — 서버 한 대만 쓸 땐 디스크에 두는 게 가장 간단하고 잘 동작함.
   서버가 여러 대가 되는 순간 그 전제가 깨짐.

3. **실험할 곳이 없어서 프로덕션 서버에 올리고 있다**
   GPU 서버에서 개인 작업 폴더 코드가 `0.0.0.0:8000`으로 떠 있음.
   프로덕션 데이터베이스 안에 개인 스키마도 있음.
   *왜* — **실험용 서버를 아무도 안 줬기 때문.** 접속 가능한 서버가 GPU밖에 없었음.
   사람 문제가 아니라 배치 문제입니다.

   ★★**이 문제는 「서버를 하나 더 주는」 방식이 아니라 「그 경로를 없애는」 방식으로
   풀렸습니다.** 이 대목을 꼭 정확히 써 주세요 — 전에는 전용 서버를 두겠다고 적었는데
   **2026-08-06 에 방향이 바뀌었습니다.**

   ```
   전에 생각한 방법   실험용 서버를 한 대 주고 거기서 돌리게 한다
   ★실제로 된 것     앱이 전부 쿠버네티스로 올라가면서
                    ★프로덕션 서버에 사람이 들어갈 일 자체가 없어졌습니다
   ```

   ★**왜 이쪽이 나은가** — 서버를 하나 더 주면 **거기서도 같은 일이 반복될 수 있습니다.**
   그 서버가 프로덕션 데이터베이스에 닿으면 개인 스키마가 또 생깁니다.
   ★**경로를 없애는 쪽이 근본입니다.**

   ★**그래서 앞으로 실험은 이렇게 합니다.**

   ```
   각자 PC 에서       도커로 띄웁니다. 프로덕션과 같은 이미지를 씁니다
   인프라가 필요하면   ⬜나중에 쿠버네티스에 ★스테이징 네임스페이스를 하나 둡니다
                     프로덕션과 같은 방식으로 뜨므로 "여기선 됐는데" 가 안 생깁니다
   ```

   ⚠️**빈 서버 두 대(VM3·VM4)는 반납합니다.** 6일 동안 아무도 안 썼고,
   **필요해지면 그때 만드는 편**이 낫습니다.

4. **이름과 실제가 안 맞아 아무도 확신할 수 없다**
   AI 서버는 비어 있고 AI는 백엔드에 있음. GPU에는 데이터베이스가 있음.
   새로 온 사람이 서버 이름으로 추측하면 반드시 틀림.
   **데이터베이스 이름도 마찬가지**입니다 — 프로덕션 데이터베이스 이름이
   `catchap_dev_db`입니다. `dev`가 붙어 있지만 실제 서비스 데이터가 들어 있습니다.
   캡차 데이터베이스는 `captcha_ms`인데, `ms`는 만든 사람의 이니셜입니다.
   *왜 문제인가* — 장애 때 어디를 볼지 모름. 문서를 써도 실제가 어긋나면 문서도 못 믿음.
   **이번에 데이터베이스 이름도 같이 바로잡습니다**(아래 5장).

5. **데이터베이스 계정 하나가 모든 권한을 갖고 인터넷에 열려 있다**
   관리자 계정이 어디서든 접속 가능하고 계정 생성·전체 삭제가 다 됨.
   비밀번호 하나가 새면 데이터 전체를 잃음.
   *왜* — 급할 땐 전권 계정 하나로 다 하는 게 빠름. 흔한 일이고 흔한 만큼 사고도 흔함.

## 5장 — 새 설계

원칙 4개를 먼저:
1. 죽어도 되는 것과 안 되는 것을 나눈다
2. 한 서버는 한 가지 일만 한다
3. 실험할 곳을 따로 준다
4. 계정마다 닿는 범위를 정해 둔다

### ★먼저 할 일 — 앱이 자기 서버를 기억하지 않게 만들기

이 부분을 **가장 공들여** 설명해 주세요. 나머지 설계가 전부 여기에 딸려 있습니다.

앱을 여러 대로 늘리려면, 앱이 **자기가 어느 서버에 있는지를 기억하지 않아야** 합니다.
어느 서버에서 실행되든 똑같이 동작해야 요청을 아무 데나 보낼 수 있습니다.

| 지금 어디에 | 옮길 곳 | 안 옮기면 |
|---|---|---|
| 강의 영상·이미지 **3.3GB**가 백엔드 서버 디스크 | Object Storage | 앱을 2벌 띄우면 한쪽에 올린 영상이 다른 쪽에서 안 보임 |
| 데이터가 서버에 직접 설치한 MySQL | 관리형 MySQL | 서버가 죽으면 데이터도 같이 위험 |

### ★확인해 보니 나머지는 이미 돼 있었습니다

이 부분을 **꼭 넣어 주세요.** 처음에 저(인프라 담당)는 "로그인 정보가 앱 메모리에 있어서
앱을 재시작하면 전원 로그아웃될 것"이라고 적었는데, **코드를 열어 보니 틀렸습니다.**
흔한 문제라서 확인 없이 그렇게 적었던 겁니다.

| 서버에 남을 법한 것 | 실제로 어디에 있나 |
|---|---|
| 로그인 세션 | 토큰(JWT) + 데이터베이스 `refresh_tokens` 표 |
| 캡차 문제와 정답 | 암호화해서 토큰 안에 넣음 — 서버에 안 남음 |
| 캡차 토큰 재사용 차단 | 데이터베이스 `captcha_consumed_tokens` 표 |
| 로그인 시도 횟수 제한 | 데이터베이스 `login_throttle` 표 |
| 문항 생성 작업 상태 | 데이터베이스 `lecture_question_gen_jobs` 표 |

코드에 이유까지 적혀 있었습니다.

> "무상태 서명 토큰의 리플레이 차단은 인메모리로는 멀티워커/재시작에 무효 →
>  (kind, token_id) UNIQUE로 원자적 소비"

★**이 인용문 바로 아래에 쉬운 말 풀이를 한 줄 붙여 주세요.** 인프라를 모르는 사람에게는
이 문장이 안 읽힙니다. 이런 뜻입니다 — **"쓴 토큰을 앱 메모리에 기억해 두면 앱이 여러 개일
때 서로 모르고, 재시작하면 잊어버린다. 그래서 데이터베이스에 적어 둔다."**

**앱을 만들 때 이미 여러 대로 늘릴 것을 염두에 두고 만들어져 있었습니다.**
그래서 이번에 실제로 옮길 것은 **파일 3.3GB와 데이터베이스, 두 가지뿐**입니다.

### 그래서 MemStore(Valkey)는 이번에 쓰지 않습니다

받아 둔 서비스지만 **지금 붙일 자리가 없습니다.** 위 표대로 전부 데이터베이스에
들어 있고, 그걸로 충분합니다. 필요 없는 걸 붙이면 **고장 날 곳과 관리할 비밀번호만**
하나씩 늘어납니다.

★**나중에 쓸 자리는 분명히 있습니다.** `login_throttle`·`captcha_store`는 수명이 몇 분이고
쓰기가 잦은 데이터라, 사용자가 많아지면 데이터베이스가 아니라 캐시 서버에 두는 게 맞습니다.
지금 규모에서는 데이터베이스로 충분해서 미뤄 둔 것이지, 안 쓰기로 못 박은 게 아닙니다.

**여기가 이번 작업의 절반입니다.** 서버를 옮기는 것보다 이게 더 중요합니다.

### 데이터베이스 이름도 바로잡습니다

| 지금 | 새 이름 | 왜 |
|---|---|---|
| `catchap_dev_db` | **`catchap`** | `dev`인데 프로덕션이라 거짓말이었습니다. 개발·운영 구분은 어느 서버에 붙느냐로 이미 갈립니다 |
| `captcha_ms` | **`catchap_captcha`** | 만든 사람 이니셜이 들어 있어, 사람이 바뀌면 이름이 거짓말이 됩니다 |
| `catchap_ai` | `catchap_ai` (그대로) | 이미 정확합니다 |

**지금이 아니면 못 바꿉니다.** 데이터가 들어간 뒤에 바꾸려면 서비스를 멈춰야 합니다.
새 데이터베이스가 아직 비어 있는 지금이 가장 싼 시점입니다.

### 앱은 쿠버네티스로

워커 2대에 **전체 2벌씩**(노드당 1벌씩) 나눠 띄웁니다.
**★"한 대는 예비"가 아닙니다. 두 대 모두 동시에 일합니다.**

⚠️★**데이터베이스는 이것과 반대입니다.** DB 도 두 대인데, 거기서는 **한 대만 일하고
한 대는 대비**합니다. **같은 "2대"인데 이유가 정반대**라서, 이 대비를 뒤의 DB 절에서
따로 설명합니다. ★**여기에 "DB 는 왜 다른지는 뒤에 나옵니다" 한 줄을 꼭 걸어 주세요.**
안 걸면 뒤에서 읽을 때 앞과 어긋난 것처럼 읽힙니다.

| 워크로드 | 벌 수 | 지금 어디에 | 왜 옮기나 |
|---|---|---|---|
| backend-api | 2 | 백엔드 서버 | 한 대 죽으면 서비스 정지 → 자동 복구되게 |
| frontend-web | 2 | 프론트 서버 | 같은 이유 |
| behavior-ai | 1~2 | 백엔드 서버 | 백엔드와 자원을 다툼. 떼어냄 |
| captcha-api | 2 | GPU 서버 | GPU는 자막 전용이어야 함. 떼어냄 |

**두 노드는 서로 다른 "가용 영역"에 있습니다** — `kr-central-2-a`와 `kr-central-2-b`.
물리적으로 다른 건물·전력·네트워크입니다. 같은 건물에 두 대를 두면 정전 한 번에 둘 다 죽지만,
영역을 나눠 두면 한 영역이 통째로 사고가 나도 다른 쪽이 삽니다.

한 대가 죽었을 때 무슨 일이 일어나는지 순서대로 보여 주세요:

```
평소      워커1  backend×1 · frontend×1      요청의 절반
         워커2  backend×1 · frontend×1      요청의 절반

워커1 사망
  1  입구가 워커1로 안 보냄  →  워커2가 전부 받음     서비스는 계속
  2  쿠버네티스가 없어진 몫을 워커2에 다시 띄움
  3  워커2  backend×2 · frontend×2            자원은 2배로 씀
```

### ★★하나가 죽으면 어떻게 되나 — 전체를 한 표로

**이 표가 이 문서에서 가장 실용적인 한 장입니다.** 인프라를 왜 이렇게 짜는지가
여기서 한 번에 보입니다. **크게, 눈에 띄게** 배치해 주세요.

★**"자동으로 살아나는 것"과 "사람이 가야 하는 것"을 색으로 갈라 주세요.**

| 무엇 | 몇 벌인가 | 하나가 죽으면 | 사람이 할 일 |
|---|---|---|---|
| **backend / frontend / captcha / behavior-ai** | **2벌** · 다른 건물 | 남은 벌이 전부 받고, 쿠버네티스가 죽은 몫을 다시 띄움 | **없음** |
| **쿠버네티스 워커** | **2대** · 다른 건물 | 파드가 살아 있는 노드로 옮겨 뜸 | **없음** |
| **로드밸런서** | **2대** · 다른 건물<br>**고가용성 그룹**으로 묶음 | 대표 주소가 살아 있는 쪽으로 보냄 | **없음** |
| **관리형 MySQL** | **2대** (주 · 예비) | **예비가 주가 됨.** 앱이 아는 주소는 그대로 | **없음** |
| **Object Storage** | 카카오가 알아서 여러 벌 | 우리가 모르는 사이에 처리됨 | **없음** |
| **MemStore** | 2노드 | 자동 (지금은 앱이 안 씀) | **없음** |
| ★**프로메테우스 (지표 저장)** | ★**1벌** · 디스크가 **한 건물에 묶임** | ★**그래프가 멈춤**. 서비스는 계속 돎 | ★**사람이** |
| ★**그라파나 (화면)** | ★**1벌** | ★**화면이 안 뜸**. 숫자는 계속 쌓임 | ★**사람이** |
| ★**GPU (자막 생성)** | ★**1대뿐** | ★**자막 생성이 멈춤** | ★**사람이 살려야 함** |
| ★**VM1 (점프서버)** | ★**1대뿐** | ★**서버에 못 들어감** (서비스는 계속 돎) | ★**사람이 살려야 함** |
| ★**HTTPS 인증서** | — | ★**만료되면 브라우저가 경고를 띄움** | ★**만료 전에 사람이 갱신** |
| ★**루트 도메인 첫 연결** | — | ★고가용성 보호를 못 받는 구간이 남음 | ★**나중에 DNS 이전** |

★★**자동이 아닌 것이 여섯입니다. 숨기지 말고 그대로 적어 주세요.**
*"전부 자동으로 복구됩니다"* 라고 쓰면 그건 거짓말이고, 나중에 사고가 났을 때
문서를 아무도 안 믿게 됩니다.

### ★★건물 하나가 통째로 죽으면 — 순서대로 따라가 주세요

★**이 절을 꼭 넣어 주세요.** 위 표는 "무엇이 어떻게 되나"만 보여 줍니다.
**실제로는 여러 개가 동시에 영향을 받고, 순서가 있습니다.** 그걸 한 번 따라가 봐야
*"그래서 서비스는 되는 건가"* 에 답이 됩니다.

**상황 — 건물 A(`kr-central-2-a`)가 정전되었다고 가정합니다.**

```
0초    건물 A 의 모든 것이 한꺼번에 사라집니다
       · 워커 노드 1대           · 로드밸런서 1대
       · 각 서비스의 파드 1벌씩   · 그라파나 · Alertmanager
       · 관리형 MySQL 의 주 서버

수 초   ★대표 주소(고가용성 그룹)가 건물 B 쪽으로만 보내기 시작합니다
       → 사용자 요청은 계속 처리됩니다. 남아 있는 파드가 받습니다

수십 초 ★관리형 MySQL 이 예비를 주로 승격합니다
       → 앱이 아는 접속 주소는 그대로입니다. 앱은 아무것도 모릅니다
       ⚠️승격되는 동안 잠깐 끊깁니다. 앱이 다시 붙습니다

1~2분   쿠버네티스가 "노드가 응답이 없다"고 판단하고, 없어진 파드를
       ★건물 B 의 노드에 다시 띄웁니다
       ⚠️그동안은 각 서비스가 1벌로 버팁니다. 트래픽이 많으면 느려집니다
```

★**결론 — 사용자 입장에서는 몇 초 느려졌다가 계속됩니다.** 이게 두 건물에 나눠 둔 값입니다.

⚠️**같이 죽는 것도 정확히 적어 주세요.**

```
그라파나가 건물 A 에 있었다면    ★화면이 안 뜹니다
프로메테우스가 건물 A 에 있었다면 ★지표 수집이 멈춥니다
                               → ★장애가 났는데 그래프를 못 보는 상황이 됩니다
GPU 서버                       ★1대뿐이라 그 건물이면 자막 생성이 멈춥니다
점프서버(VM1)                  ★1대뿐이라 서버에 들어갈 길이 막힙니다
```

★★**"장애가 났는데 그래프를 못 본다"가 가장 아픈 대목입니다.** 정직하게 적어 주세요.

### ★★왜 앱은 2벌인데 모니터링은 1벌인가 — 이 질문에 답해 주세요

★**읽는 사람이 반드시 물을 질문입니다.** *"그럼 모니터링도 2벌로 하면 되잖아요"* 에
답이 없으면 앞의 설명이 다 흔들립니다.

```
앱          ★아무것도 안 들고 있습니다
            어느 노드에 뜨든 똑같이 동작하고, 요청을 아무나 받아도 됩니다
            → 여러 벌로 만들기 쉽습니다

프로메테우스 ★자기 디스크에 숫자를 쌓습니다
            2벌로 만들면 각자 다른 디스크에 각자 쌓습니다.
            둘의 내용이 서로 다르고, 어느 쪽을 봐야 할지 알 수 없게 됩니다
            → 여러 벌로 만들려면 ★그 둘을 맞추는 장치가 또 필요합니다
```

★**이것이 「상태를 갖는 것」과 「안 갖는 것」의 차이입니다.** 5장에서 무상태화를 설명한
이유가 여기서 다시 나옵니다. **상태가 없으면 여러 벌로 만들기가 쉽고, 있으면 어렵습니다.**

★**그래서 우리 선택은 이렇습니다.**

```
앱          ★2벌 · 두 건물     — 사용자가 직접 겪는 것이라 끊기면 안 됩니다
모니터링     ★1벌              — 잠깐 안 보여도 서비스는 계속 돕니다
                              지금 규모에서 2벌로 만드는 비용이 얻는 것보다 큽니다
```

⚠️**다만 이건 "지금 규모에서" 라는 단서가 붙은 판단입니다.** 서비스가 커지면 다시 봐야 합니다.

### ★정비할 때는 어떻게 되나 — 고장과 다릅니다

**고장은 예고 없이 오지만, 정비는 우리가 시점을 압니다.** 쿠버네티스는 노드를 정비할 때
그 노드의 파드를 **먼저 다른 곳으로 옮기고** 나서 비웁니다.

⚠️**그런데 그냥 두면 위험한 구간이 생깁니다.**

```
우리 파드는 ★같은 노드에 두 벌이 못 앉게 해 뒀습니다(한 노드가 죽어도 0벌이 안 되게).
그래서 노드 하나를 비우면 그 서비스는 ★1벌로 떨어진 채 버팁니다.
이때 두 번째 노드까지 비우면 ★0벌이 됩니다.
```

★**그래서 「최소 1벌은 남겨라」는 규칙(PodDisruptionBudget)을 걸어 뒀습니다.**
이게 있으면 쿠버네티스가 **노드를 한 대씩만** 비웁니다.

⚠️**이 규칙은 정비 같은 계획된 중단만 막습니다.** 서버가 고장 나서 죽는 것은 못 막습니다.
그건 위의 「건물 두 개」가 맡습니다. **둘은 서로 다른 문제를 막는 장치입니다.**

★**관리형 클러스터라 카카오가 우리에게 안 물어보고 노드를 업데이트할 수 있습니다.**
우리가 안 보고 있을 때 이 규칙이 대신 지켜 줍니다.

---

### ★★★데이터베이스는 따로 한 절을 써 주세요 — 유일하게 되돌릴 수 없는 것

★**이 절을 반드시 넣어 주세요.** 앱은 죽어도 다시 띄우면 그만입니다.
**데이터는 잃으면 끝입니다.** 그래서 이중화와 복구를 따로 봐야 합니다.

#### ① ★왜 두 대인가 — 앱과는 이유가 다릅니다

★**이 질문에 먼저 답해 주세요.** 앱도 2벌이고 DB 도 2대라 같아 보이는데, **두는 이유가
정반대입니다.**

```
앱이 2벌인 이유    ★일을 나눠 하려고
```

★★**DB 는 앱처럼 그냥 여러 벌로 늘릴 수 없습니다.** 이유가 있습니다.

#### ② 무엇이 주이고 무엇이 예비인가


⚠️**지금 앱은 주(3306)만 씁니다.** 예비는 **대기 중인 복사본**이고 평소에 트래픽을 안 받습니다.

★**다만 길은 열어 뒀습니다.** 보안 그룹에서 `3307` 을 허용해 둔 것이 그것입니다(12장 ⑥ 표).

```
            앱 ──▶ 3307(예비) 읽기   ★길은 이미 열려 있습니다
```

⚠️**바로 하지 않는 이유** — 예비는 주를 **따라 복사하는 중**이라 아주 짧은 시간 뒤처집니다.

| 부품 | 하는 일 | 비유 |
|---|---|---|

**우리 실제 구성을 그대로 보여 주세요.** 숫자가 있으면 훨씬 잘 읽힙니다.

```
   사용자
     │
     ▼
   로드 밸런서  catchap-lb-2a        공인 IP 210.109.55.233   (건물 A)
     │
     ├─ 리스너  HTTP  : 80   ──┐
     └─ 리스너  HTTPS : 443  ──┤     ★인증서는 여기 붙는다
```

★**하나씩 짚어 주세요.**

### ★로드밸런서 하나는 자기 건물 밖으로 못 나갑니다

공식 문서 원문입니다.

> 로드 밸런서 노드는 **단일 가용 영역 내** 트래픽을 분산 및 배포하지만,
> **고가용성 그룹에 연결하여 사용함으로써 여러 가용 영역에 걸쳐** 고가용성 보장 가능

```
   로드밸런서만 있을 때              고가용성 그룹으로 묶었을 때
   사용자                            사용자
     ↓                                 ↓
   LB (건물A) ─▶ 앱(건물A)            고가용성 그룹
                 앱(건물B) ✗            ├─▶ LB(건물A) ─▶ 앱(건물A)
   ★건물A 가 죽으면 끝                  └─▶ LB(건물B) ─▶ 앱(건물B)
```

★**고가용성 그룹은 로드밸런서를 대체하지 않고 품습니다.** 기존 것을 그대로 넣을 수
있다는 걸 콘솔에서 확인했습니다. 그래서 **인증서와 설정을 다시 만들 필요가 없습니다.**

★**지금 상태를 정직하게 쓰면 이렇습니다** — **파드가 죽는 것 · 워커 한 대가 죽는 것 ·
건물 하나가 통째로 죽는 것까지 견딥니다.** 남은 것은 배포뿐입니다.

**왜 GPU 는 2대로 안 만드나** — 비쌉니다. 그리고 자막 생성은 **잠깐 멈춰도 서비스가
안 죽습니다.** 사용자가 강의를 보는 데는 지장이 없고, 새 영상의 자막이 늦어질 뿐입니다.
**"멈춰도 되는 것"과 "멈추면 안 되는 것"을 나눠서 돈을 쓰는 것**이 설계입니다.

**인증서는 오히려 나빠집니다** — 지금은 Caddy 가 알아서 갱신해 주는데, 새 구조에서는
사람이 챙겨야 합니다(5장 Caddy 절). **2026년 10월 20일 만료**입니다.

### ★관리형 MySQL 은 실제로 시험해 봤습니다

표에 *"예비가 주가 됨"* 이라고 적은 것은 **읽어서 안 게 아니라 해 봐서 안 것**입니다.

```
   앱이 아는 주소 하나  →  주 서버 A
                        ↓ 콘솔에서 일부러 전환
   앱이 아는 주소 하나  →  주 서버 B      ★주소는 그대로, 가리키는 곳만 바뀜
```

**끊긴 시간은 10초 남짓**이었습니다. 앱에는 끊겼을 때 다시 잡게 하는 설정
(`pool_pre_ping`)을 켭니다. **그러면 사람이 아무것도 안 해도 됩니다.**

★**해 보기 전에는 "주소를 두 개 알아야 하나?" 를 몰랐습니다.** 문서만 읽고 넘어갔으면
전환하는 날 처음 겪었을 일입니다. 이런 건 **미리 일부러 고장 내 보는 게** 답입니다.

### 서버 5대는 역할 고정

| 서버 | 역할 | 왜 서버여야 하나 |
|---|---|---|
| VM1 | 점프 서버 · 배포 실행 | 나머지로 들어가는 유일한 문. 외부 접속 가능한 유일한 서버 |
| VM2 | **이미지 굽는 곳** | 코드를 이미지로 만들어 레지스트리에 올림. **프로덕션 서버에서 빌드하지 않으려고 따로 둠**(8장) |
| VM3 | **스테이징 · 팀 실험실** | 여기서 마음껏 돌려도 됨. 프로덕션과 완전 분리 |
| VM4 | 모니터링 · 로그 · 배치 | 지표 수집과 정기 작업 |
| GPU | 자막 생성 전용 | 쿠버네티스 워커에 GPU가 없어 여기서만 가능. **다른 건 안 올림** |

강조: **VM3가 이번 설계에서 가장 중요하다.** 실험할 곳을 안 주면 프로덕션에 올릴 수밖에 없다.
지금 벌어진 일이 정확히 그것이고, 서버 한 대로 구조적으로 막을 수 있는 문제다.

### 없어지는 것 — Caddy (꼭 넣어 주세요)

지금 백엔드·프론트 서버에는 **Caddy**라는 웹서버가 한 대씩 떠 있습니다. 설정은 이렇습니다.

백엔드:
```
api.catchap5.com {
    reverse_proxy api:8000
    encode gzip
}
```

프론트:
```
www.catchap5.com {
    reverse_proxy web:80
    encode gzip
}
catchap5.com {
    redir https://www.catchap5.com{uri} permanent
}
```

**Caddy가 하는 일 네 가지**가 새 구조에서는 다른 곳으로 갑니다.

| Caddy가 하던 일 | 새 구조에서는 | 설명 |
|---|---|---|
| **HTTPS 인증서** | 로드밸런서 | 자물쇠 아이콘을 만드는 인증서. 로드밸런서에 이미 붙어 있음 |
| **도메인 → 앱 연결** | 쿠버네티스 인그레스 | `api.catchap5.com`이 어느 앱으로 갈지 |
| **압축(gzip)** | 인그레스 | 전송량을 줄이는 일 |
| **주소 정리** | 인그레스 | `catchap5.com` → `www.catchap5.com` |

결론: **Caddy 컨테이너는 사라지고 Caddyfile도 없어집니다.**

**★솔직하게 적을 것** — 이 변화에는 **불편해지는 점이 있습니다.**
Caddy는 HTTPS 인증서를 **알아서 자동 갱신**해 줬습니다(지금 인증서도 Let's Encrypt에서
Caddy 가 자동으로 받아 쓰던 것입니다). 새 구조의 로드밸런서에는 **따로 발급받아 등록한**
**인증서**가 붙어 있습니다 — `catchap5.com` + `*.catchap5.com` · **2026년 10월 20일 만료**.
★**자동 갱신이 아닙니다.** 갱신하려면 재발급 → 인증서 관리에 다시 등록 →
로드밸런서 리스너에 다시 붙이기까지 **사람이** 해야 합니다.
새 구조에서는 로드밸런서에 붙은 인증서를 **만료 전에 사람이 갱신**해야 합니다.
자동을 하나 잃는 대신 서버마다 흩어진 웹서버 설정을 한 곳으로 모읍니다.

## 6장 — 계정을 나눈다

목적 한 줄: **계정 하나가 새거나 실수했을 때 잃는 범위를 미리 정해 두는 것.**

★**계정이 두 종류라는 것부터 알려 주세요.** 이름이 비슷해서 계속 헷갈리는 지점입니다.

```
클라우드 계정      카카오클라우드에 무엇을 시킬 때      "이미지를 올려라" "비밀값을 꺼내라"
데이터베이스 계정   MySQL 안에서 자료를 읽고 쓸 때       "회원 표를 조회해라"
```

**서로 아무 관계가 없습니다.** 하나가 새도 다른 쪽은 멀쩡합니다.

### 6-A. 클라우드 계정 — 사람 말고 프로그램이 쓰는 계정

**"서비스 계정"이 무엇인지부터 한 줄로** 설명해 주세요.

> 사람이 콘솔에 로그인하듯, **프로그램도 클라우드에 자기를 밝혀야** 합니다.
> 그때 쓰라고 만드는 것이 서비스 계정입니다. **비밀번호 대신 키를 씁니다.**

우리 서비스 계정은 **셋**입니다. **하나가 한 가지 일만** 하게 나눴습니다.

| 계정 | 무슨 일을 하나 | 클라우드 권한 | 쿠버네티스 권한 |
|---|---|---|---|
| **`catchap-backend`** | 앱이 기동할 때 **비밀값을 꺼내 풀고**, 영상·이미지를 넣고 뺌 | Object Storage 매니저 · KMS 사용자 · Secrets Manager 매니저 | 없음 |
| **`catchap-ops`** | 우리(인프라)가 **조회**할 때 | 프로젝트 리더 + 매니저 5 (실효 11) | 없음 |
| **`catchap-ci`** | 이미지를 **구워서 올리고**, **쿠버네티스에 배포**할 때 | 프로젝트 멤버 하나 | ★**cluster-admin** (0804 부여) |

★**`catchap-ci` 가 하는 일이 8월 4일에 늘었습니다.** 원래 이미지만 올렸는데
**쿠버네티스 배포까지** 하게 됐습니다. 그래서 키 이름도 `catchap-ci-registry` 에서
`catchap-ci-deploy` 로 바꿨습니다.

### ★★클라우드 권한과 쿠버네티스 권한은 별개입니다 — 이 대목을 꼭 넣어 주세요

**이걸 몰라서 닷새를 헛기다렸습니다.**

```
클라우드 권한(IAM)     서버·DB·네트워크를 만들고 지우는 권한. 콘솔에서 줍니다
쿠버네티스 권한(RBAC)   ★클러스터 안에서 무엇을 할 수 있는지. 콘솔에 없습니다
```

★**둘은 따로 놉니다.** `프로젝트 관리자` 를 받아도 **쿠버네티스는 여전히 거절**합니다.
반대로 쿠버네티스 관리자여도 **서버를 못 만듭니다.**

**우리가 한 것**

```
catchap-ci 에게   클라우드는 ★프로젝트 멤버 하나만 (제일 낮은 축)
                 쿠버네티스는 ★cluster-admin (제일 높음)
```

★**왜 이렇게 나눴나** — 배포하려면 **쿠버네티스 안에서는 뭐든 할 수 있어야** 합니다
(인그레스 컨트롤러가 클러스터 범위 자원을 만듭니다). 하지만 **클라우드 쪽까지 세게 주면
그 계정이 서버·DB·네트워크를 지울 수 있게** 됩니다.
**「필요한 곳에서만 세게」** 가 원칙입니다.

★**이미지 받아오기(pull)도 `catchap-ci` 로 합니다.** 쿠버네티스에
`catchap-registry` 라는 자격증명을 넣어 뒀습니다. 저장소가 **비공개**라
이게 없으면 파드가 `ImagePullBackOff` 로 멈춥니다 — 실제로 겪었습니다.

### ★IAM 키와 S3 키는 다릅니다 (꼭 넣어 주세요)

계정 하나가 **키를 두 종류** 가질 수 있는데, **쓰는 곳이 완전히 다릅니다.**
이름이 비슷해서 가장 많이 틀리는 지점입니다.

| | IAM 액세스 키 | S3 액세스 키 |
|---|---|---|
| 무엇에 쓰나 | **카카오클라우드 전반**에 명령할 때 | **Object Storage(파일 창고)에만** |
| 예 | 이미지 올리기 · 비밀값 꺼내기 · 쿠버네티스 명령 | 영상 파일 넣고 빼기 |
| 개수 | 계정당 최대 2개 | 계정당 최대 2개 |

★**실제로 겪은 일로 설명해 주세요** — 이미지를 올리려고 `docker login` 할 때
**S3 키를 넣으면 거부(401)** 당합니다. **IAM 키여야 됩니다.**
이름만 보면 둘 다 "액세스 키"라 구분이 안 됩니다.

★**키는 2개까지 만들 수 있다는 게 실무에서 중요합니다.** 키를 바꿀 때
**새 키를 먼저 만들고 → 바꿔 끼우고 → 옛 키를 지우면** 서비스가 안 끊깁니다.

### ★역할(Role)이 권한을 정합니다

키 자체에는 권한이 없습니다. **계정에 붙은 역할이 권한을 정하고, 키는 발급 시점의
역할을 물려받습니다.**

| 역할 | 무엇을 할 수 있나 |
|---|---|
| 프로젝트 관리자 | 전부. 다른 조 자원까지 지울 수 있음 |
| **프로젝트 멤버** | 자원을 만들고 지울 수 있음. **단 IAM(계정·권한)은 못 건드림** |
| **프로젝트 리더** | **조회만** |
| 서비스별 역할 24종 | Object Storage 매니저, KMS 사용자 처럼 **그 서비스만** |

★★**역할은 계정을 만들 때만 정할 수 있고 나중에 못 바꿉니다.**
잘못 고르면 계정을 지우고 다시 만드는 수밖에 없습니다. 그래서 만들기 전에 확인이 필요합니다.

★**하나 더 — 고른 역할 1개가 실제로는 여러 개로 펼쳐집니다.**
`catchap-ci` 에 `프로젝트 멤버` **하나만** 줬는데, 실제 권한을 조회하니
`member` + `reader` + `load-balancer_member` **셋**이었습니다.
상위 역할이 하위를 포함하기 때문입니다. **"역할 1개"와 "권한 1개"는 다릅니다.**

### 6-B. 데이터베이스 계정

| 계정 | 닿는 곳 | 할 수 있는 일 | 쓰는 곳 |
|---|---|---|---|
| team_one | 전부 | 전부 | **앱 사용 금지.** 사람이 계정 만들 때만 |
| catchap_backend | catchap | 읽기·쓰기 | 백엔드 앱. **표 구조는 못 바꿈** |
| catchap_migrate | DB 3개 | 전부 | 스키마 변경. 배포할 때 잠깐만 |
| catchap_captcha_app | catchap_captcha | 읽기·쓰기 | 캡차 서비스 |
| catchap_ai_app | catchap_ai | 읽기·쓰기 | AI 워커 |
| **jy · sw · ms · my** | DB 3개 | **읽기만** | **팀원 각자의 조회 계정.** 서버 계정과 이름이 같음 |

핵심 두 문장:
- **백엔드 앱이 표를 지울 수 없다.** 코드에 문제가 생기거나 공격을 받아도 데이터를 읽고 쓸 뿐
  구조는 못 건드린다.
- 팀원에게는 **각자 이름의 읽기 전용 계정**을 준다. 무슨 쿼리를 날려도 데이터가 안 변하니
  마음 놓고 조회해도 된다.

**★이미 다 만들어서 동작을 확인했습니다.** 그 사실도 적어 주세요 — 계획이 아니라 완료입니다.
각 계정으로 실제 접속해 보니, **자기 데이터베이스만 보이고 다른 것은 목록에도 안 나옵니다.**
앱 계정으로 표를 만들려고 하면 거부당하고, `catchap_migrate`만 됩니다.

**★공유 계정을 안 쓰는 이유도 적어 주세요.**
읽기 전용이라 데이터는 안 망가지지만, **읽기가 무해한 것은 아닙니다.**
우리 데이터베이스에는 회원 실명·이메일·학습 기록이 들어 있습니다.
계정을 하나로 같이 쓰면 **누가 언제 회원 정보를 조회했는지 구분이 안 됩니다.**
그리고 한 명이 팀을 떠나면 비밀번호를 바꿔야 하고 나머지도 전부 다시 받아야 합니다.
**SSH 키를 사람마다 다르게 주는 것과 같은 이유**로 데이터베이스 계정도 나눕니다.

## 7장 — 서비스별로 무엇이 어디로 가나

여기까지가 "왜 바꾸나"였고, 이 장은 **"그래서 무엇이 어디로 가나"**입니다.
표 하나로 한눈에 들어오게 해 주세요.

| 서비스 | 하는 일 | 지금 있는 곳 | 이후 |
|---|---|---|---|
| **backend-api** | 서비스의 본체. API 전부 | 백엔드 서버 | 쿠버네티스 **2벌** |
| **frontend-web** | 사용자가 보는 화면 | 프론트 서버 | 쿠버네티스 **2벌** |
| **behavior-ai** | 사람인지 봇인지 행동으로 판별 | 백엔드 서버 (**AI 서버가 아니라**) | 쿠버네티스 |
| **captcha** | 사람 확인 문제 출제·채점 | 옛 GPU 서버 | 쿠버네티스 **2벌** |
| **STT 워커** | 강의 영상에서 자막 생성 | 옛 GPU 서버 | ✅ **새 GPU로 이전 완료** |
| Caddy ×2 | 웹서버 (5장 참고) | 백엔드·프론트 서버 | ❌ **없어짐** — 로드밸런서와 인그레스가 나눠 맡음 |

### ★캡차 하나만 사정이 다릅니다 — 이 대목은 꼭 넣어 주세요

나머지 서비스는 전부 **컨테이너**로 떠 있는데, 캡차만 **서버에 직접 설치돼** 있습니다.

★**오해가 없게 먼저 적어 주세요 — 캡차도 자동으로 뜨고 자동으로 되살아납니다.**
`Restart=always` 가 걸려 있어 죽으면 3초 뒤에 다시 뜨고, 서버를 껐다 켜도 자동으로
올라옵니다. **7월 21일 재부팅 때 49초 만에 스스로 돌아왔습니다.** 관리가 안 되고 있다는
이야기가 아닙니다.

**그런데도 옮기는 이유는 다른 데 있습니다.** 세 가지입니다.

| | 왜 문제인가 |
|---|---|
| **한 사람 계정에 매달려 있다** | 팀원 개인 계정의 설정으로 돌아갑니다. **그 계정이 없어지면 서비스도 같이 멈춥니다** |
| ★**설정 파일이 두 벌 있다** | 서로 **다른 폴더를 가리키는 설정이 두 개** 남아 있습니다. 지금 도는 건 한쪽인데, 모르는 사람이 다른 쪽을 고치면 아무 일도 안 일어납니다 |
| **똑같이 다시 만들 수가 없다** | 이미지가 없어서, 다른 서버에 같은 것을 띄우려면 **설치를 처음부터 손으로** 해야 합니다 |

★**두 번째가 가장 위험합니다.** "고쳤는데 왜 안 바뀌지?"가 나오는 전형적인 상황입니다.

### ★★그리고 이 서비스는 찾기가 어려웠습니다 (이 이야기를 꼭 넣어 주세요)

**서버에 무엇이 돌고 있는지 조사할 때 캡차를 두 번 놓쳤습니다.**

```
① docker ps          → 안 나온다. 컨테이너가 아니니까
② 시스템 서비스 목록   → 안 나온다. 개인 계정 설정으로 등록돼 있어서
③ 열린 포트 목록      → ★여기서 겨우 찾았다
```

세 번째 방법이 없었으면 **캡차를 통째로 빠뜨린 채 이전을 끝냈을 것**입니다.

**이게 컨테이너를 쓰는 진짜 이유입니다.** 컨테이너로 떠 있으면 `docker ps` 한 줄에
전부 나옵니다. 쿠버네티스면 목록에 다 뜹니다. **"서버에 뭐가 도는지 아무도 확신 못 하는
상태"가 없어집니다.** 4장 4번(이름과 실제가 안 맞는다)과 같은 이야기입니다.

★이 대목을 **찾기 어려웠다는 사실 그대로** 써 주세요. 누구의 잘못도 아니고,
**구조가 그렇게 만든 것**입니다.

### ★코드가 GitHub에 다 있는지 먼저 확인했습니다 (꼭 넣어 주세요)

**왜 이걸 확인해야 하나부터 설명해 주세요.** 이 장에서 가장 중요한 대목입니다.

새 방식은 **GitHub에 올라온 코드로 이미지를 굽습니다.** 서버에 있는 파일을 쓰지 않습니다.
그래서 만약 **서버에서 직접 고치고 GitHub에는 안 올린 수정**이 하나라도 있으면,
**그 기능이 빠진 채로 새 환경이 뜹니다.** 그리고 그건 배포한 다음에야 알게 됩니다.

```
   서버에만 있는 수정이 있으면
   GitHub 코드 ──► 이미지 ──► 새 환경    ← 그 수정이 통째로 빠진다
```

그래서 **지금 실제로 돌고 있는 파일과 GitHub의 파일을 하나씩 대조**했습니다.
"있겠지"가 아니라 내용을 비교했습니다.

| 서비스 | 무엇과 비교했나 | GitHub의 어디 | 결과 |
|---|---|---|---|
| 백엔드 | 지금 도는 **컨테이너 안의 파일 127개** | `jy` | **127개 전부 같음** |
| 프론트 | 서버의 소스 **200개** | `jy` | **200개 전부 같음** |
| 캡차 | 서버에서 실행 중인 **6개** | `sw-captcha` | **6개 전부 같음** |
| behavior-ai | 컨테이너 안의 **38개** | `sw` | 32개 같음 · **6개는 GitHub이 더 새것** |

**결론: 서버에만 있는 코드는 없습니다.** 안심하고 GitHub에서 구우면 됩니다.

behavior-ai의 6개가 다른 건 **빠진 게 아니라 반대**입니다. 지금 도는 컨테이너가 6일 전에
구워진 것이라, 그 뒤에 올라온 수정이 아직 안 들어간 상태입니다. **GitHub 쪽이 최신**이므로
새로 구우면 그 수정까지 들어갑니다.

### ★브랜치 이름 이야기 (짧게, 그러나 꼭)

지금 프로덕션 코드는 **사람 이름 브랜치**에 있습니다 — `jy`, `sw`, `sw-captcha`.
누구를 탓하는 이야기가 아니라, **다음 사람이 반드시 헷갈릴 지점**이라 적어 둡니다.

**`th` 브랜치는 어느 서비스의 프로덕션도 아닙니다.** 이름만 보면 대표 브랜치처럼
보이지만 아닙니다. 실제로 확인해서 알아낸 것이고, 안 확인했으면 틀린 코드를 구울 뻔했습니다.

이건 **4장 4번(이름과 실제가 안 맞는다)과 같은 문제**입니다. 서버 이름이 거짓말을 하듯
브랜치 이름도 거짓말을 합니다. 이번 이전에서 브랜치까지 정리하지는 않지만,
**어느 브랜치가 프로덕션인지는 문서로 남깁니다.**

## 8장 — 팀원에게 달라지는 것 (가장 중요한 장)

전/후를 나란히 비교해서 보여 주세요.

**뭔가 돌려 보고 싶을 때**
- 지금: 접속 가능한 서버가 GPU뿐이라 거기 올림. 프로덕션과 섞임
- 앞으로: **VM3에 각자 계정.** 여기선 뭘 해도 프로덕션에 영향 없음

**★배포할 때 — 이 장에서 가장 크게 다뤄 주세요. 팀원이 매주 겪는 일입니다.**

먼저 **지금 방식이 왜 서비스를 멈추게 하는지**를 설명해 주세요. 이걸 안 짚으면
"바꿔서 뭐가 좋은데?"에 답이 안 됩니다.

지금은 **프로덕션 서버 안에서 이미지를 굽습니다.** 그러면 두 가지가 동시에 일어납니다.

1. 굽는 동안 그 서버의 CPU와 메모리를 빌드가 씁니다. **사용자 요청을 처리하던 그 서버입니다.**
2. 다 구워지면 옛 컨테이너를 **먼저 내리고** 새것을 띄웁니다. **그 사이는 아무도 없습니다.**

```
지금
  코드 수정 → 서버에 접속 → 코드 올림 → 서버에서 빌드 → 옛것 내림 → 새것 띄움
                                        └─ 서버가 느려짐 ─┘   └ 아무도 없음 ┘
                                                              여기서 접속이 끊긴다
```

새 방식은 **굽는 곳과 도는 곳을 떼어 놓습니다.**

```
이후
  코드 수정 → GitHub에 push        ← ★팀원이 하는 건 여기까지입니다
                  │
             ① VM2(빌드 전용 서버)가 이미지를 굽는다     프로덕션은 아무 영향 없음
             ② 레지스트리(이미지 창고)에 올린다
             ③ 쿠버네티스에게 "이 이미지로 바꿔라"
                  │
             파드를 하나씩 교체한다
             새 파드가 정상인 걸 확인한 다음에 옛 파드를 내린다
             ★비는 순간이 없다
```

**"하나씩 교체"가 핵심입니다.** 백엔드가 2벌 떠 있으므로, 한 벌을 새것으로 바꾸는 동안
**나머지 한 벌이 요청을 받습니다.** 그게 끝나면 반대쪽을 바꿉니다. 그래서 안 끊깁니다.

### ★단계마다 누가 하는지 — 6장의 계정과 이어서 보여 주세요

★**올리는 계정과 받아오는 계정이 다릅니다.** 받아오기만 하면 되는 쪽에 올릴 권한을

### ★이 흐름은 이미 돌려서 확인했습니다 (사실로 적어 주세요)

그러면 **떠 있는 이미지 이름만 보고 GitHub 에서 그 커밋을 찾아** 정확히 어떤 코드인지

```
                 ★그 서버에 git 저장소가 없습니다 (tarball 로 배포합니다)

  캡차           ★위젯 빌드 결과물이 git 에 없습니다
```

★★**즉 「지금 도는 코드」를 GitHub 에서 재현할 수 없습니다.** 이건 인프라 문제가 아니라

| | 전 (옛 VPC) | 후 (새 VPC) |
|---|---|---|
| **앱이 죽으면** | ★사람이 서버에 들어가 다시 켬 | 쿠버네티스가 **알아서 다시 켬** |
| **서버 한 대가 죽으면** | 그 서버의 앱이 통째로 사라짐 | **다른 서버에 옮겨 켬** |
| **건물(가용영역)이 죽으면** | ★전부 중단 | 앱·DB·캐시·입구가 **양쪽 건물에** 있어 반대쪽이 받음 |
| **DB가 죽으면** | ★수동 복구 | 예비가 **10초 남짓 만에** 자동으로 대신 받음 (실제로 시험함) |
| **DB 백업** | 사람이 챙김 | **매일 자동 · 14일 보관** |
| **비밀번호** | ★설정 파일에 글자 그대로 | 금고(Secrets Manager)에서 꺼내 씀 · **누가 언제 꺼냈는지 기록** |
| **영상·이미지** | 서버 디스크 (서버 죽으면 같이 사라짐) | **파일 창고**에 분리 · 서버와 무관 |
| **로그인 상태** | ★서버 메모리 (서버를 늘리면 로그인이 풀림) | 밖으로 빼서 **몇 벌을 늘려도 안 풀림** |
| **무엇이 떠 있는지** | ★"아마 최신일 것" | 이미지 태그가 **커밋 해시** — 그 해시로 코드를 정확히 찾음 |
| **팀원 DB 조회** | 공용 계정 (누가 했는지 모름) | **각자 이름의 읽기 전용 계정** |
| **누가 무엇을 했나** | 기록 없음 | Cloud Trail 에 **전부 기록** |

### 8.5-B. ★나빠진 것 · 불편해진 것 — 숨기지 말고 적어 주세요

| | 전 | 후 | 어떻게 대처하나 |
|---|---|---|---|
| **인증서 갱신** | Caddy 가 **자동으로** 갱신 | ★**사람이 챙겨야 함.** 2026년 10월 20일 만료 | 달력에 넣고 만료 2주 전에 알림 |

★**「배포 절차가 길어진 것」이 가장 체감되는 변화**입니다. 대신 **무엇이 떠 있는지 정확히

## 8.6장 — ★GitHub 저장소와 브랜치가 바뀝니다 (개발 방식이 달라지는 장)

★**이 장은 「인프라」가 아니라 「우리가 코드를 어떻게 올리고 배포하나」 이야기입니다.**
지금까지와 가장 크게 달라지는 부분이라 따로 뺐습니다.

### 왜 바꾸나 — 지금 구조가 자동배포를 막습니다

**앞으로 하려는 것은 이겁니다.**

```
팀원이 GitHub 에 코드를 올린다  →  자동으로 검사  →  자동으로 배포
```

★**그런데 지금 구조로는 안 됩니다.** 이유를 하나씩 봅니다.

#### 문제 ① — 저장소 하나에 서로 다른 세 가지가 들어 있습니다

`ai-service` 저장소를 열어 보면 **브랜치마다 다른 서비스**가 들어 있습니다.

```
sw-captcha 브랜치   →  캡차
sw 브랜치           →  행동 판별 AI
main · th 브랜치    →  ★이미지 분류 AI (지금 어디서도 안 돕니다)
```

★★**「main 에 올리면 배포」 규칙을 만들 수가 없습니다.** `main` 하나가 **세 서비스를
동시에 가리킬 수 없기 때문**입니다.

#### 문제 ② — `main` 이 6월 29일 상태입니다

```
catchap-backend   main 2026-06-29 「초기 세팅」   ← ★한 달 반 전
                  jy   2026-08-05                ← ★진짜 프로덕션
```

★**지금 `main` 을 배포하면 6월 코드가 뜹니다.** 세 저장소가 다 그렇습니다.

#### 문제 ③ — 브랜치 이름이 사람 이름입니다

```
jy · sw · ms · my · th
```

★**이름만 봐서는 무엇을 하는 브랜치인지 모릅니다.** 그리고 **그 사람이 빠지면 아무도
손대지 못합니다.** 실제로 오늘 **`sw-captcha` 브랜치를 `ms` 님이 서버에서 돌리고 있는
것**을 알아내는 데 시간이 걸렸습니다.

### 새 브랜치 규칙 — 이게 가장 크게 달라집니다

★**요약은 영문 소문자와 하이픈**으로 씁니다. 커밋 메시지는 **지금처럼 한국어**로 씁니다.

```
나쁜 예   jy · sw · ms · my · th
```

★★**개인 이름 브랜치는 없어집니다.** 대신 **「무엇을 하는 브랜치인지」가 이름에 들어갑니다.**

```
① main 에서 새 브랜치를 딴다        feature/무엇무엇

⑥ main 으로 합친다  →  ★자동 배포
⑦ 브랜치는 지운다
```

★**⑤가 왜 필요한가** — 지금은 사람이 배포 명령을 직접 쳐서 **한 번 걸러집니다.**
자동배포가 붙으면 **그 단계가 사라집니다.** `main` 에 합치는 순간 사용자에게 나갑니다.
**리뷰가 유일한 안전장치가 됩니다.**


★**「내 브랜치가 지워지나」 걱정되실 수 있습니다.** ★**남은 작업이 있는 브랜치는 안 지웁니다.**
전부 커밋 하나하나 확인했고, **이미 프로덕션에 들어간 것만** 지웁니다.

## 9장 — 컷오버는 어떻게 하고, 잘못되면 되돌릴 수 있나

불안 해소를 위한 장입니다. 먼저 **되돌릴 수 있다**는 세 가지부터.

- **옛 환경을 바로 안 지웁니다.** 새 환경이 자리를 잡을 때까지 그대로 둡니다
- **컷오버는 주소가 가리키는 곳을 바꾸는 일**입니다. 지금 `catchap5.com`은 옛 서버를
  직접 가리키고 있고, 컷오버는 그 주소가 **새 입구**를 보게 하는 것입니다.
  **문제가 생기면 되돌리면 옛 환경으로 돌아갑니다**
- **데이터는 옮기는 것이 아니라 복사하는 것**입니다. 옛 데이터베이스는 그대로 남습니다

### 실제로 무엇을 바꾸나 — 가비아에서 3~4줄

**도메인을 산 곳(가비아)의 DNS 관리 화면에서 레코드를 고칩니다.** 서버에는 손을 안 댑니다.

```
① catchap5.com   A       210.109.14.25  →  210.109.55.233     (입구 A)
①-2 catchap5.com A       61.109.239.102 를 한 줄 더 추가        (입구 B)
② www            A 지우고 →  CNAME  catchap-lb-2ab-….kakaocloud.com
③ api            A 지우고 →  CNAME  같은 주소
```

★**`www`와 `api`는 CNAME 입니다.** 고가용성 그룹이 **IP 가 아니라 DNS 이름**을 주기 때문입니다.
이름을 가리키면 **카카오가 알아서 살아 있는 입구로 보내 줍니다.**

### ★★루트 도메인만 다릅니다 — 이걸 꼭 넣어 주세요

**`www.catchap5.com`은 CNAME 을 붙일 수 있는데, `catchap5.com`은 못 붙입니다.**

**인터넷 규격에 그렇게 정해져 있습니다.** 루트 도메인에는 메일 주소를 찾는 `MX` 레코드처럼
**반드시 같이 있어야 하는 레코드들**이 있는데, CNAME 은 *"이 이름의 모든 것을 저쪽으로
넘겨라"* 라는 뜻이라 **둘이 같이 있을 수 없습니다.** CNAME 을 붙이면 **메일이 죽습니다.**

```
www.catchap5.com   CNAME  가능      다른 레코드가 없어도 되는 이름
catchap5.com       CNAME  ★불가능   MX·SPF 같은 게 같이 있어야 하는 이름
```

**AWS·Cloudflare 같은 곳은 이걸 우회하는 기능(ALIAS/ANAME)이 있는데, 가비아와
카카오클라우드 DNS 에는 없습니다.** 공식 문서에서 확인했습니다.

**그래서 루트는 IP 를 직접 적습니다.** 입구가 둘이니 **두 줄을 적습니다.**

```
catchap5.com   A   210.109.55.233      (입구 A)
catchap5.com   A   61.109.239.102      (입구 B)
```

★**이건 완화지 해결이 아닙니다. 정직하게 적어 주세요.**
**DNS 는 건강검진을 하지 않습니다.** 두 줄을 적으면 브라우저가 **번갈아 아무 쪽이나**
갑니다. 입구 A 가 죽어도 DNS 는 그걸 모르고 계속 A 를 알려 줍니다.

```
입구 둘 다 정상   →  절반씩 나눠 들어옴
입구 A 가 죽음    →  ★절반은 실패한다 (브라우저가 재시도하면 붙기도 함)
```

### 막혀 있는 곳은 하나입니다

이것도 숨기지 말고 적어 주세요. **막힌 걸 적어야 나머지가 믿깁니다.**

쿠버네티스에 앱을 올리려면 쿠버네티스에게 명령을 보내야 하는데,

| `401` | **당신이 누군지 모르겠습니다** | 아님 |
| `403` | 당신인 건 알겠는데 **그럴 권한이 없습니다** | ★**이쪽** |

**계정과 연결은 정상이고 권한만 없다**는 뜻입니다.

### ★★그런데 이 진단이 틀렸습니다 — 8월 4일에 풀렸습니다. 이 대목을 꼭 넣어 주세요


> `User "catchap-ops-…@kc.serviceaccount.com" cannot list resource "namespaces"`

**그 한 줄을 8월 4일에야 열어 봤습니다.** 계정을 바꿔서 재니 **바로 통과**했습니다.
받아야 할 권한이 없었고, **처음부터 잘못된 계정으로 재고 있었습니다.**

★**교훈으로 크게 넣어 주세요.**

> **`403` 은 「권한이 없다」가 아니라 「이 신원에 권한이 없다」입니다.**
> **무엇이 실패했나 못지않게 「누구로 시도했나」를 봐야 합니다.**

**그리고 지금은 이렇게 되어 있습니다** — 사람 계정으로 한 번 들어가서 **배포 전용 계정을

## 12장 — 카카오클라우드 서비스별로 무엇을 했나 (기록)

★**이 장이 이 문서에서 가장 긴 장이 돼도 됩니다.** 앞 장들이 "왜·무엇이 달라지나"였다면
여기는 **"실제로 무엇을 만졌고 어떻게 확인했나"** 입니다.

**서비스 하나에 한 덩어리씩** 카드나 아코디언으로 만들어 주세요. 각 덩어리는
**① 이 서비스가 하는 일 ② 우리가 한 일 ③ 어떻게 확인했나 ④ 화면 자리** 순서로.

★**"확인했나"를 반드시 넣어 주세요.** "했습니다"만 있으면 못 믿습니다.
무엇을 보고 됐다고 판단했는지가 같이 있어야 합니다.

### ★★이 장은 발표 자료(PPT)로도 씁니다 — 그 전제로 만들어 주세요

**보는 사람이 클라우드를 하나도 모른다고 가정**합니다. 그래서 서비스마다
**「이게 뭔가」를 먼저** 두고, 그다음에 「우리가 한 일」을 둡니다.

```
한 서비스 = 슬라이드 1~2장

슬라이드 앞면   ① 이게 뭔가        비유 한 줄 + 안 쓰면 어떻게 되는지
                                 ★전문 용어를 쓰기 전에 우리말로 먼저
슬라이드 뒷면   ② 우리가 한 일      표
                ③ 어떻게 확인했나   숫자·응답 코드
                ④ ★콘솔 화면       실제 캡처
```

★**「이게 뭔가」에 반드시 「안 쓰면 어떻게 되는지」를 같이 두세요.**
*"Object Storage 는 파일 창고입니다"* 만으로는 왜 필요한지 모릅니다.
*"서버에 넣으면 서버가 죽을 때 파일도 사라집니다"* 가 있어야 이해됩니다.

★**슬라이드마다 콘솔 캡처를 한 장씩** 넣습니다. 자리와 파일은 뒤쪽
「실제 콘솔 화면을 붙일 자리」에 정리돼 있습니다.

★**용어는 앞의 용어집 ①~④를 먼저 보게 하세요.** 발표에서는 **처음 나오는 말마다
한 번씩 풀어 주고** 넘어가는 것이 낫습니다.

### ① Virtual Machine — 서버 5대

**이게 뭔가** — **빌려 쓰는 컴퓨터**입니다. 사무실에 컴퓨터를 사다 놓는 대신,
카카오 데이터센터에 있는 컴퓨터를 **필요한 만큼 빌려** 씁니다.

```
지금 옛 서버    설정 파일에 비밀번호가 ★글자 그대로 적혀 있음
                → 그 파일을 볼 수 있는 사람은 전부 비밀번호를 앎
금고로 옮기면    ★누가 언제 꺼냈는지 기록이 남음 · 바꿀 때 한 곳만 고치면 됨
```


| 한 일 | 확인한 것 |
|---|---|
| 비밀값 **5건**을 우리 전용 암호화 키(`kms11`)로 다시 만듦 | 설명을 한국어로 · 콘솔에서 값은 안 보임 |
| 앱이 이 값을 읽어 오는 코드 작성 | 아직 배포 전 |
| 쓰지 않는 시크릿 정리 | 7건 → **6건** |

★**왜 이걸 하나**를 꼭 적어 주세요. 지금은 데이터베이스 비밀번호가 **설정 파일에

Secrets Manager로 옮기면 **누가 언제 꺼냈는지 기록이 남고**, 바꿀 때 한 곳만 고치면 됩니다.

★**주의로 적을 것** — 시크릿은 **이름과 설명을 만든 뒤에 못 고칩니다.** 그래서 만들기 전에
이름 규칙을 먼저 정해야 했습니다. 이런 "생성할 때만 정할 수 있는 것"이 여러 서비스에
있습니다.

### ★★"프라이빗 서브넷"이 사실은 퍼블릭입니다 — 꼭 넣어 주세요

**우리 서버들이 있는 자리를 정확히 알아야** 합니다. 여기서 오해가 생기기 쉽습니다.

**퍼블릭이냐 프라이빗이냐를 가르는 것은 이름이 아니라 「라우팅 테이블」입니다.**
라우팅 테이블은 **"어디로 가려면 어느 길로 나가라"를 적어 둔 표**입니다.

카카오클라우드 공식 정의입니다.

> **인터넷 게이트웨이를 포함한 라우팅 테이블에 연결된 서브넷을 퍼블릭 서브넷이라고 합니다.**

**우리 라우팅 테이블은 두 개인데, 둘 다 이렇게 적혀 있습니다.**

```
   10.0.0.0/16   →   Local              내부끼리는 바로
   0.0.0.0/0     →   Internet Gateway   ★그 밖 전부는 인터넷 게이트웨이로
                                          = 이 한 줄이 "퍼블릭 서브넷" 판정 근거
```

★**화면 자리 16번**을 여기에 넣어 주세요. **라우팅 테이블 화면에 이 두 줄이 실제로
찍혀 있습니다.** 글로만 읽으면 *"정말?"* 이 되는 대목이라 **화면이 있어야 믿깁니다.**
캡션에 `0.0.0.0/0 → Internet Gateway` 줄을 **화살표로 짚어 주세요.**

**우리 `Team1-VPC`의 서브넷이 전부 여기에 해당합니다.** 원래 이름이
`private_sn1`~`sn6` 이었는데 **정의상 전부 퍼블릭 서브넷**이었습니다.

★**이름이 거짓말을 하고 있었습니다.** 이것 때문에 저희가 하루에 **판단을 네 번 뒤집었습니다.**
그래서 **8월 4일에 이름을 전부 고쳤습니다.**

```
전                          후                 안에 있는 것
Team1-VPC_public_sn1   →   catchap-jump-2a    VM1 점프서버 · 입구 A
Team1-VPC_private_sn1  →   catchap-core-2a    서버 3대 · 워커1 · DB · 캐시   ┐ 이중화 짝
Team1-VPC_private_sn6  →   catchap-core-2b    워커2 · 입구 B · DB · 캐시     ┘
Team1-VPC_private_sn4  →   catchap-gpu-2a     GPU 서버(자막 생성)
Team1-VPC_private_sn2  →   ★삭제 (비어 있었음)
Team1-VPC_private_sn3  →   ★삭제 (비어 있었음)
```

★**`역할-건물` 순서로 지은 이유가 있습니다.** 이름순으로 정렬하면 **`core-2a`와 `core-2b`가
위아래로 붙어서 이중화 짝이 눈에 보입니다.** `건물-역할` 순서(`sn-2a-core`)로 지으면
짝이 맨 위와 맨 아래로 떨어집니다. **이름은 정렬됐을 때를 생각하고 지어야 합니다.**

★**비어 있던 둘은 지웠습니다.** 강사님이 7월 23일에 **뭐가 들어갈지 정하기 전에 칸부터
그어 두신 것**이고(5개가 2분 안에 30초 간격으로 만들어졌습니다), 그 뒤로 아무도 안 썼습니다.
**서브넷은 프로젝트당 30개를 3개 조가 같이 쓰기 때문에** 2개를 돌려준 셈입니다.

★**지우기 전에 다섯 군데를 따로 확인했습니다** — 네트워크 인터페이스 전수 · 쿠버네티스
클러스터 · 노드 풀 · 관리형 MySQL · MemStore. **한 곳만 보고 "안 쓴다"고 판단하면 안 됩니다.**
실제로 **관리형 MySQL 과 MemStore 는 네트워크 인터페이스 목록에 아예 안 나옵니다.**

### 이름을 고쳤어도 "전부 퍼블릭 서브넷" 인 건 그대로입니다

★**이름을 바꾼 것이지 성질을 바꾼 게 아닙니다.** 여섯 개가 넷이 됐을 뿐,
**넷 다 여전히 인터넷 경로를 가진 퍼블릭 서브넷**입니다.

**그런데도 밖에서 못 들어옵니다.** 이유는 방화벽이 아니라 **공인 IP가 없어서**입니다.

```
   VM2~4 · 워커들       →  ★공인 IP 없음. 밖에서 못 들어옴
```

★**나갈 때는 됩니다.** 공인 IP가 없는 서버도 인터넷에 나갑니다. 실제로 재 봤습니다.

```
VM1 (공인 IP 있음)  →  나갈 때 210.109.82.148   자기 IP
VM2 (공인 IP 없음)  →  나갈 때 210.109.82.130   ★카카오가 주는 공용 출구
```

**카카오클라우드의 인터넷 게이트웨이가 나가는 길의 주소 변환을 대신 해 줍니다.**
그래서 이미지를 받아오고 업데이트를 할 수 있습니다.

★★**그래서 이 규칙이 중요합니다 — 굵게 써 주세요.**

> **서버에 공인 IP를 함부로 붙이지 마세요.**
> 라우팅은 이미 인터넷으로 열려 있습니다. 공인 IP를 붙이는 순간 **그 서버가 바로
> 인터넷에 노출**됩니다. 지금 안전한 이유는 막아 뒀기 때문이 아니라 **공인 IP가
> 없기 때문**입니다.

### ★"그럼 NAT 을 만들어야 하지 않나요" — 안 만듭니다. 이유를 적어 주세요

**반드시 나올 질문입니다.** 보통 클라우드 교재는 *"사설 서버가 인터넷에 나가려면
NAT 이 필요하다"* 고 가르치는데, **우리는 NAT 없이 이미 나가고 있습니다.**

**카카오클라우드에는 관리형 NAT 게이트웨이가 아예 없습니다.** 문서에는 **NAT 인스턴스**
— **VM 한 대를 사서 직접 NAT 장비로 만드는 방법**만 나옵니다.

**만들면 오히려 나빠집니다.**

| 만들면 생기는 일 | 왜 나쁜가 |
|---|---|
| 사설 서버 **전부의 출구가 VM 한 대**로 모임 | 그 한 대가 죽으면 **GPU·쿠버네티스·DB 가 전부 인터넷에서 끊깁니다.** 지금은 어느 한 대가 죽어도 나가는 길이 멀쩡합니다 |
| 대역폭도 그 한 대 | 영상 올리기·이미지 내려받기가 전부 통과 |
| 라우팅 표를 갈라야 함 | 건물 B 서브넷이 **점프서버·입구 A 와 같은 표를 씁니다.** 잘못 고치면 점프서버가 끊깁니다 |

**얻는 것은** *"라우팅 표에도 진짜 사설로 보인다"* 는 **서류상 성질 하나**입니다.
**들어오는 문은 지금도 이미 닫혀 있습니다**(공인 IP 가 없으면 밖에서 못 들어옵니다).

★**교훈으로 적어 주세요** — **교재의 정답이 이 클라우드의 정답은 아닙니다.**
AWS 는 공인 IP 가 없으면 인터넷 게이트웨이로 못 나가서 NAT 이 꼭 필요한데,
**카카오클라우드는 게이트웨이가 주소 변환까지 해 줍니다.** 문서를 읽고 **실제로 재 봐야**
압니다. 저희는 서버 안에서 나가는 IP 를 찍어 보고 알았습니다.

점프 서버에서 돌립니다. 이런 맞바꿈이 인프라에는 계속 나옵니다.

## ★★13장 — 무엇이 얼마나 바쁜지 보는 법 (2026-08-05·06 신설)

★**이 장은 통째로 새 내용입니다.** 이전 작업이 끝나갈 무렵에 만든 것이라 앞 장에는 없습니다.
**한 장을 온전히 쓰고, 아래 순서 그대로 가 주세요.**

### 13-1. 왜 필요한가 — 문제부터

서비스가 느려졌다는 말이 나왔을 때 답할 수 있어야 하는 질문은 이것입니다.

```
지금 느린 게 맞나        아니면 그 사람 인터넷이 느린 건가
느리다면 어디가 느린가    앱인가 · 데이터베이스인가 · 네트워크인가
언제부터 그런가          오늘 오후부터인가 · 지난주부터 조금씩인가
```

★**이 셋에 답하려면 「그때의 숫자」가 남아 있어야 합니다.** 지금 서버에 들어가서 보는 것으로는
"지금"밖에 모릅니다. 어제 오후가 어땠는지는 아무도 모릅니다.

그래서 **숫자를 계속 모아서 쌓아 두는 장치**가 따로 필요합니다. 그게 모니터링입니다.

### 13-2. 모니터링은 두 층입니다

```
① 재서 모으는 층    누가 CPU·메모리를 재고, 어디에 쌓는가
② 보여주는 층       그 값을 어떤 화면에서 보는가
```

★**이 둘을 나눠서 보면 뒤에 나오는 이야기가 전부 정리됩니다.** 부품 이름이 여럿 나오는데,
각각이 두 층 중 어디에 속하는지만 잡으면 됩니다.

### 13-3. 재는 방식에는 두 가지가 있습니다

```
★밀어넣기(push)   재는 쪽이 먼저 말을 겁니다
                  "나 지금 CPU 40%야" 하고 중앙 서버로 보냅니다

★걷어가기(pull)   중앙이 주기적으로 찾아가서 읽습니다
                  "너 지금 어때?" 하고 물으러 갑니다
```

★**밀어넣기는 재는 쪽마다 프로그램을 깔아야 합니다.** 서버가 5대면 5군데에 깝니다.

⚠️**그런데 쿠버네티스에서는 이 방식이 잘 안 맞습니다.** 파드는 배포할 때마다 이름이 바뀌고
노드를 옮겨 다닙니다. **프로그램을 깔아 둘 고정된 대상이 없습니다.**

★**그래서 새 환경에서는 걷어가기로 바꿨습니다.**

### 13-4. 부품 이름 셋

**프로메테우스(Prometheus)** — 지표를 걷어와서 저장하는 서버입니다.
30초마다 클러스터 안의 모든 노드와 파드를 돌면서 숫자를 읽고, 시간과 함께 쌓아 둡니다.
*"어제 오후 3시에 CPU 가 몇 %였나"* 에 답할 수 있는 것은 이것이 쌓아 뒀기 때문입니다.

**그라파나(Grafana)** — 그 숫자를 그래프로 그려 주는 화면입니다.
프로메테우스는 숫자만 갖고 있고 화면이 없습니다. 그라파나가 프로메테우스에 물어서 그립니다.

**node-exporter** — 서버 한 대의 CPU·메모리·디스크를 읽어서 내놓는 작은 프로그램입니다.
노드마다 한 벌씩 떠 있고, 프로메테우스가 여기에 물으러 옵니다.

```
node-exporter (노드마다) ──걷어감──▶ 프로메테우스 (저장) ──질의──▶ 그라파나 (화면)
```

### 13-4-1. ★GPU 서버 한 대만은 「밀어넣기」입니다 — 왜 그런지

★**앞에서 걷어가기로 바꿨다고 했는데, 딱 한 대는 밀어넣기를 씁니다.** 이유가 있습니다.

```
GPU 서버(음성→자막 변환을 돌리는 기계)는 ★쿠버네티스 밖에 있습니다.
프로메테우스는 클러스터 ★안을 도는 물건이라, 밖에 있는 이 서버를 걷어갈 수가 없습니다.
```

그래서 이 서버에는 **작은 프로그램 하나를 깔아 두고, 30초마다 스스로 백엔드에 보냅니다.**
보내는 값은 CPU·메모리·디스크에 더해 **GPU 사용률과 VRAM**(그래픽카드 전용 메모리)입니다.

```
GPU 서버 ──30초마다 밀어넣기──▶ 백엔드 ──저장──▶ ★운영 콘솔 화면
```

**왜 이걸 굳이 하느냐** — 예전에 문항 생성이 두 번 실패한 적이 있는데,
원인이 **GPU 서버의 디스크가 0바이트**였습니다. 그때는 **볼 화면이 없어서** 원인을 찾는 데
오래 걸렸습니다. 지금은 `디스크 24.7%` 처럼 **숫자로 먼저 보입니다.**

★**카카오클라우드가 만든 에이전트를 먼저 써 봤습니다.** 문서상 GPU 지표를 지원합니다
(`nvidia_smi_utilization_gpu` 등). 그런데 설치해서 돌리니 **전송할 때마다 400 오류**가 나고
값이 안 들어갔습니다. 시계·설정·주기를 바꿔 가며 세 가지를 시험했는데 전부 같은 오류라,
**우리 프로그램으로 돌아왔습니다.** 카카오 쪽은 따로 문의할 항목으로 남겨 뒀습니다.

⚠️**여기서 얻은 교훈 하나** — 보내는 쪽 로그에 *"보냈다"* 가 찍혀도 **도착했다는 증거가 아닙니다.**

### 13-7. ★디스크를 붙이는 데서 한 번 막혔습니다 — 이 이야기를 꼭 넣어 주세요

프로메테우스는 숫자를 **디스크에 쌓아야** 합니다. 파드는 죽으면 안에 있던 파일이 사라지므로,
**밖에 있는 디스크**를 붙여야 합니다.

★**그런데 클러스터에 「디스크를 달라」고 적을 창구 자체가 없었습니다.**

```
kubectl get storageclass  →  ★아무것도 없음
```

**CSI** 라는 규격이 있습니다. `Container Storage Interface` 의 줄임말이고,
**컨테이너에 디스크를 붙여 주는 표준 규격**입니다.

```
디스크를 만드는 방법은 클라우드 회사마다 다릅니다.
쿠버네티스가 회사마다 코드를 품을 수는 없으니 ★규격을 정했습니다.
클라우드 회사가 그 규격에 맞는 프로그램(드라이버)을 만들어 두면,
쿠버네티스는 그 드라이버를 통해 디스크를 다룹니다.
```

**프린터 드라이버와 같은 구조입니다.** 윈도우가 세상 모든 프린터를 알 수는 없으니
제조사가 드라이버를 주고, 윈도우는 그걸 통해 인쇄합니다.

★**카카오가 그 드라이버를 주는데, 클러스터를 만들 때 같이 깔아 주지는 않습니다.**
우리가 깔았습니다.

### 13-8. ★★그리고 디스크가 엉뚱한 곳에 생겼습니다 — 이 대목이 이 장의 핵심입니다

깔고 나서 시험 삼아 디스크를 하나 만들어 봤더니, **파드가 앉을 자리와 다른 건물에 생겼습니다.**

```
디스크가 생긴 곳   ★kr-central-2-b (건물 B)
파드가 앉을 자리   아직 안 정해짐
```

⚠️**블록 디스크는 건물을 넘지 못합니다.** B 건물에 있는 디스크는 A 건물 서버에 못 붙습니다.
파드가 A 건물에 앉으면 **디스크를 못 붙여서 뜨지 못합니다.**

★**원인은 만드는 시점이었습니다.**

```
Immediate               "디스크 달라" 는 말이 나오는 ★즉시 만든다
                        → 그때는 파드가 어느 건물에 앉을지 ★아직 모른다
★WaitForFirstConsumer   파드가 자리를 잡을 때까지 ★기다렸다가 그 건물에 만든다
```

**뒤쪽으로 바꾸고 다시 시험했습니다.**

```
 6초   디스크 대기 · 파드 대기        ← 자리가 정해지기 전
12초   디스크 ★생김 · 파드 대기       ← 자리가 정해지자 그 건물에 만듦
18초   디스크 붙음 · 파드 ★동작

파드가 앉은 건물 A  →  ★디스크도 건물 A. 따라갔습니다.
```

★**우리 서버가 두 건물에 나뉘어 있어서 생긴 문제입니다.** 한 건물에만 있었으면 안 겪었을
일이고, 대신 그 건물에 문제가 생기면 서비스가 통째로 멈춥니다. **나눠 둔 값입니다.**

### 13-9. ★운영 콘솔에서도 같은 숫자를 봅니다

우리 운영 콘솔에는 원래 **서버 상태 화면**이 있었습니다. 옛 환경에서는 서버 5대에 각각

**화면과 그래프 코드는 하나도 안 바뀌었고, 값의 출처만 바뀌었습니다.**

```

```

### 13-10. ★파드의 메모리 백분율은 무엇을 나눈 값인가 — 짧게, 그러나 꼭


⚠️**CPU 는 다르게 잽니다.** 파드에는 CPU 한도를 안 걸어 뒀습니다. 그래서 "CPU 한도 대비"
라는 개념이 없고, **클러스터 전체 코어 대비 점유율**로 냅니다.

### ㉮ 앱을 담는 것

**도커(Docker)** — 앱과 그 앱이 돌아가는 데 필요한 것(파이썬 버전·라이브러리·설정)을
**한 덩어리로 묶는 도구**입니다. 묶은 결과물을 **이미지**라고 부릅니다.
필요한 이유는 *"제 컴퓨터에서는 되는데요"* 를 없애기 위해서입니다. 이미지에는 필요한 것이
전부 들어 있어서, **어느 서버에 올려도 같은 모양으로 뜹니다.**
없으면 서버마다 파이썬 버전과 라이브러리를 사람이 맞춰야 하고, 하나만 어긋나도 안 뜹니다.

**이미지(Image)와 컨테이너(Container)** — 이미지는 **찍어 둔 것**이고, 컨테이너는
**그 이미지를 실제로 돌린 것**입니다. 같은 이미지로 컨테이너를 여러 개 띄울 수 있습니다.
빵틀과 빵의 관계입니다.

**태그(Tag)** — 이미지에 붙이는 이름표입니다. `catchap-backend:824e7c4` 에서 `824e7c4` 가
태그입니다. ★**우리는 태그에 깃 커밋 해시를 씁니다.** 그래야 *"지금 떠 있는 게 어느 코드냐"* 에
`git show 824e7c4` 로 정확히 답할 수 있습니다.
★`latest` 라는 태그는 안 씁니다 — 같은 이름인데 내용이 계속 바뀌어서, 무엇이 떠 있는지
알 수 없게 됩니다.

**컨테이너 레지스트리(Container Registry)** — 이미지를 올려 두는 창고입니다.
빌드한 서버와 실행할 서버가 다르기 때문에, 중간에 창고가 필요합니다.

### ㉯ 앱을 굴리는 것

**쿠버네티스(Kubernetes)** — 컨테이너를 **여러 서버에 나눠서 돌리고, 죽으면 다시 띄우고,
서버 한 대가 고장 나면 다른 서버로 옮겨 주는** 관리자입니다.
없으면 사람이 서버에 들어가서 컨테이너를 띄우고, 죽었는지 지켜보고, 죽으면 다시 띄워야 합니다.

**노드(Node)** — 쿠버네티스가 쓰는 서버 한 대입니다. 우리는 2대입니다.

**파드(Pod)** — 컨테이너를 담는 단위입니다. 쿠버네티스는 컨테이너를 직접 다루지 않고
**항상 파드 단위로** 다룹니다. 우리 파드는 대부분 컨테이너 하나만 담고 있습니다.

**디플로이먼트(Deployment)** — *"이 이미지를 2벌 띄워 두고, 죽으면 다시 띄워라"* 를 적어 둔
문서입니다. 우리가 `2벌` 이라고 적으면 쿠버네티스가 계속 2벌을 유지합니다.
배포는 이 문서의 이미지 태그를 바꾸는 일입니다.

**데몬셋(DaemonSet)** — 디플로이먼트와 비슷한데 **"모든 노드에 한 벌씩"** 이 규칙입니다.
노드가 3대로 늘면 자동으로 3벌이 됩니다.
★**노드 자체를 재는 프로그램은 노드마다 있어야 하므로 데몬셋으로 띄웁니다.**

**네임스페이스(Namespace)** — 클러스터 안을 나누는 칸막이입니다. 우리 앱은 `catchap` 칸에,
모니터링은 `monitoring` 칸에 있습니다. 이름이 겹쳐도 칸이 다르면 서로 안 부딪힙니다.

**PodDisruptionBudget (PDB)** — *"정비 때문에 파드를 내리더라도 최소 몇 벌은 살려 둬라"* 를
적어 둔 규칙입니다. 우리는 **최소 1벌**로 걸어 뒀습니다.
필요한 이유는, 쿠버네티스가 노드를 정비할 때 그 노드의 파드를 내리기 때문입니다.
★**막는 것이 없으면 두 노드를 잇달아 비울 때 파드가 0벌이 되는 순간이 생깁니다.**
⚠️이 규칙은 **정비 같은 계획된 중단만** 막습니다. 서버가 고장 나서 죽는 것은 못 막습니다.

---

### ㉰ 디스크를 붙이는 것

**CSI** — 컨테이너에 디스크를 붙여 주는 **표준 규격**입니다(13-7 참조).

**StorageClass** — *"어떤 종류의 디스크를 어떻게 만들지"* 를 적어 둔 설정입니다.
디스크를 달라고 할 때 이 이름을 대면, 그 방식대로 만들어집니다.
★우리는 세 가지가 있고, 그중 **파드가 앉은 건물에 만드는 것**을 씁니다(13-8 참조).

**PVC / PV** — `PVC`(PersistentVolumeClaim)는 **"10GB 짜리 디스크 하나 주세요" 라는 신청서**
이고, `PV`(PersistentVolume)는 **그래서 실제로 만들어진 디스크**입니다.
신청서와 실물을 나눠 둔 이유는, 앱 쪽은 *"10GB 필요하다"* 만 적고 **어느 클라우드의 어떤
디스크인지는 몰라도 되게** 하려는 것입니다.

### ㉱ 재고 보는 것 — 모니터링 부품

**프로메테우스(Prometheus)** — 지표를 걷어와 시간과 함께 쌓아 두는 서버입니다.
30초마다 클러스터를 돌면서 숫자를 읽습니다.
없으면 *"어제 오후 3시에 어땠나"* 에 아무도 답할 수 없습니다.

**PromQL** — 프로메테우스에 질문할 때 쓰는 **질의어**입니다. SQL 이 데이터베이스에 묻는
말이라면, PromQL 은 지표에 묻는 말입니다.

```
node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
   → 노드마다 "남은 메모리 비율" 이 숫자로 돌아옵니다

rate(container_cpu_usage_seconds_total[5m])
   → 파드마다 "최근 5분 평균 CPU 사용률"
```

★**이게 표준이라는 점이 중요합니다.** 나중에 다른 도구로 바꾸더라도 같은 말로 묻습니다.

**그라파나(Grafana)** — 프로메테우스가 갖고 있는 숫자를 **그래프로 그려 주는 화면**입니다.
프로메테우스에는 화면이 거의 없습니다. 숫자를 보관하는 일만 합니다.
그라파나는 화면만 담당하고 자기 데이터는 없습니다. **둘이 붙어야 쓸 수 있습니다.**
우리 그라파나에는 **기본 대시보드 25개**가 들어 있습니다 — 노드별·파드별·네임스페이스별
사용량 화면이 만들어 둔 채로 옵니다.

**node-exporter** — 서버 한 대의 CPU·메모리·디스크·네트워크를 읽어서 내놓는 작은
프로그램입니다. **노드마다 한 벌씩**(데몬셋) 떠 있고, 프로메테우스가 여기로 물으러 옵니다.
★재는 일만 하고 저장은 안 합니다. *"지금 이 순간의 값"* 만 내놓습니다.

**kube-state-metrics** — node-exporter 가 **하드웨어**를 잰다면, 이쪽은 **쿠버네티스의 상태**를
숫자로 바꿔 줍니다.

```
파드가 몇 벌 떠 있나 · 재시작이 몇 번 났나 · 메모리 한도가 얼마로 걸려 있나
```

★**node-exporter 는 이걸 모릅니다.** 그쪽은 리눅스만 볼 뿐 쿠버네티스를 모릅니다.
파드 메모리를 한도 대비 백분율로 낼 수 있는 것은 이 부품이 한도를 알려 주기 때문입니다.

**Alertmanager** — *"CPU 가 90% 를 넘겼다"* 같은 상황이 생기면 **알리는 일만** 하는 부품입니다.
판단은 프로메테우스가 하고, 알림은 이쪽이 보냅니다. 나눠 둔 이유는 **같은 경보가 여러 번
겹칠 때 묶어서 한 번만 보내거나, 밤에는 참았다가 아침에 보내는 규칙**을 여기서 정하기
위해서입니다.
⚠️**지금은 받는 곳을 아직 안 정했습니다.** 화면에는 뜨는데 메일이나 메신저로는 안 갑니다.

★**경보 중에 `Watchdog` 이라는 것이 항상 울리고 있습니다.** 이건 고장이 아니라
**일부러 항상 울리게 만들어 둔 것**입니다. *"알림 통로가 살아 있는가"* 를 확인하는 용도라,
이게 안 울리면 알림 체계 자체가 죽은 것입니다.

**metrics-server** — *"지금 이 파드가 CPU 를 얼마나 쓰고 있나"* 를 쿠버네티스에게 알려 주는
부품입니다. 프로메테우스와 하는 일이 비슷해 보이지만 **쓰는 곳이 다릅니다.**

```
프로메테우스     ★사람이 보는 용도. 오래 쌓아 둔다
metrics-server   ★쿠버네티스가 판단하는 용도. 최근 값만 갖고 있다
```

★**파드 자동 확장(HPA)이 이걸 봅니다.** 카카오 클러스터에는 이게 안 깔려 있어서
`kubectl top` 도 안 되고 자동 확장도 못 쓰는 상태였습니다. 어제 깔았습니다.

**HPA (Horizontal Pod Autoscaler)** — 부하에 따라 **파드 수를 자동으로 늘리고 줄이는**
장치입니다. `수평(Horizontal)` 은 *"서버를 더 크게"* 가 아니라 *"같은 것을 여러 벌로"* 라는
뜻입니다.
지금 우리는 **2벌 고정**입니다. 숫자가 문서에 박혀 있어서 사람이 고쳐 배포하기 전에는
안 바뀝니다. ⬜전제 조건은 갖췄고 아직 안 붙였습니다.

### ㉲ 깔 때 쓴 도구

**헬름(Helm)** — 쿠버네티스에 무언가를 깔 때 쓰는 **설치 도구**입니다.

```
헬름이 없으면   프로메테우스를 깔 때 설정 파일을 ★수십 개 직접 써야 합니다
헬름이 있으면   ★차트 하나를 고르고, 바꾸고 싶은 것만 적습니다
```

**차트(Chart)** 는 그 설치 꾸러미의 이름입니다. 우분투의 `apt install` 과 비슷한 자리입니다.

**kube-prometheus-stack** — 우리가 쓴 차트 이름입니다. 프로메테우스 하나만 깔아 주는 게
아니라 **그라파나·Alertmanager·kube-state-metrics·node-exporter 를 한꺼번에** 깔고,
서로 연결까지 해 줍니다. **대시보드 25개도 이 안에 들어 있습니다.**

★**그대로 깔면 안 되는 자리가 있었습니다.** 이 차트는 쿠버네티스의 **관리 부분**까지
감시하려고 하는데, 카카오가 관리하는 클러스터라 **우리가 그 부분에 접근할 수 없습니다.**
켜 둔 채로 두면 *"감시 대상에 못 닿는다"* 는 경보가 계속 뜹니다. **꺼서 깔았습니다.**

**hostNetwork** — 파드가 **자기 IP 를 갖지 않고 노드의 IP 를 그대로 쓰게** 하는 설정입니다.
보통은 파드마다 자기 IP 를 받는데, 그러면 **클러스터 밖에서는 그 IP 로 못 닿습니다.**
★`metrics-server` 를 깔았는데 안 붙어서 원인을 찾아보니, **카카오가 관리하는 부분이
우리 파드 IP 로 못 닿는 것**이었습니다. 노드 IP 를 쓰게 바꿔서 풀었습니다.
★같은 이유로 **입구(인그레스)도 이 설정으로 돌고 있습니다** — 힌트가 이미 클러스터 안에
있었던 셈입니다.

### ㉳ 카카오클라우드 쪽

**Metric Export** — 카카오클라우드가 모아 둔 지표를 **밖에서 가져갈 수 있게 열어 둔 창구**
입니다. 카카오 콘솔에서 그래프로 보는 것과 **같은 숫자**를 API 로 받아 옵니다.

★**중요한 점은 이 창구가 프로메테우스와 같은 방식이라는 것입니다.**
그래서 **그라파나에 데이터소스로 그냥 붙습니다.** 우리 프로메테우스와 카카오 지표를
**한 화면에서** 볼 수 있게 됩니다.

⚠️**질의한 양만큼 요금이 붙습니다.** 너무 자주 물으면 비용이 늘어서, 주기를 넉넉히 잡습니다.

⬜**아직 안 붙였습니다** — 조회용 계정을 하나 만들어야 합니다.

**모니터링 에이전트** — 가상 서버 안에 깔아서 **그 서버의 CPU·메모리·디스크·GPU 를 카카오로
보내는** 프로그램입니다.
★**GPU 서버에 이게 안 깔려 있어서** 지금 GPU 사용률과 VRAM 이 어디에도 안 보입니다.
깔면 카카오 쪽 창구로 들어오고, 그라파나에서 같이 보입니다.

★**이 문서에서 "이미지"라는 말이 20번 넘게 나옵니다.** 여기서 안 잡히면 배포 장을
통째로 못 읽습니다. 작아도 되니 **용어 사전 바로 아래**에 꼭 넣어 주세요.

**① 지금 구조 vs 새 구조 — 나란히 놓은 두 장**
문서 앞쪽에 배치. 왼쪽 "지금", 오른쪽 "이후".
지금 = 서버 상자 5개가 각각 따로 서 있고 그 안에 컨테이너가 박혀 있음.
이후 = 로드밸런서 → 쿠버네티스 상자 안에 파드들 → 아래로 관리형 서비스 3개.
★**이 한 장으로 문서의 절반이 전달돼야 합니다.**

**② 요청이 흐르는 길**
사용자 → 도메인 → 로드밸런서 → 인그레스 → 각 서비스로 갈라지는 화살표.
`catchap5.com` · `api.catchap5.com` · `captcha.catchap5.com` 이 각각 어디로 가는지.

**③ 서버 한 대가 죽었을 때 — 3컷**
만화처럼 3칸으로. (1) 평소: 워커1·워커2에 파드가 반씩.
(2) 워커1 사망: 입구가 워커1로 안 보냄, 워커2가 전부 받음 — **서비스는 계속**.
(3) 쿠버네티스가 없어진 몫을 워커2에 다시 띄움.
★죽은 쪽은 회색, 살아 있는 쪽은 강조색으로.

**④ 가용 영역 = 건물 두 개**
건물 아이콘 2개(`kr-central-2-a` / `-b`)에 각각 서버가 들어 있는 그림.
한쪽 건물에 번개(정전) 표시를 하고 다른 쪽은 멀쩡한 모습.
★"물리적으로 다른 건물"이라는 게 그림으로 와닿게.

**⑤ 무상태화 — 파일이 어디 있느냐**
왼쪽: 앱 2벌이 각자 자기 디스크를 안고 있고, 한쪽에만 파일이 있어 **다른 쪽에서 ✗**.
오른쪽: 앱 2벌이 **같은 창고(Object Storage)** 를 보고 있어 둘 다 ✓.
★이 문서에서 가장 이해가 어려운 개념이라 그림이 꼭 필요합니다.

**⑥ 배포가 어떻게 바뀌나 — 두 줄 비교**
지금: `코드 → 서버 SSH → tarball → 서버에서 빌드` (중간에 **서비스 멈춤** 표시)
이후: `코드 → GitHub → 이미지 빌드 → 레지스트리 → 쿠버네티스` (**안 멈춤** 표시)
★팀원이 가장 궁금해할 부분입니다. 크게 그려 주세요.

**⑦ GitHub 과 레지스트리는 다르다**
GitHub = 레시피(종이), 레지스트리 = 조리된 도시락(상자)로 비유해 그리세요.
쿠버네티스는 요리를 안 하고 **도시락을 받아 데울 뿐**이라는 게 보이게.
★둘 다 "저장소"라 불려서 가장 많이 헷갈리는 지점입니다.

**⑧ 데이터베이스 계정 경계**
계정 5종이 각각 어느 DB 를 볼 수 있는지 선으로 연결.
★**서로 다른 DB 는 목록에도 안 뜬다**는 것이 보이게 — 안 보이는 쪽은 자물쇠·점선으로.

**⑨ 없어지는 Caddy — 하던 일이 어디로 갔나**
Caddy 상자에서 화살표 4개가 뻗어 나가 각각 로드밸런서·인그레스·인증서 관리로
옮겨 가는 그림.

**⑩ 컷오버 = 화살표 하나 옮기기**
도메인에서 옛 서버로 가던 화살표를 로드밸런서로 옮기는 그림.
★"큰 공사가 아니라 DNS 한 줄"이라는 게 보이게.

**⑪ 지표가 흐르는 길 — 13장**
왼쪽에 노드 2개(각각 안에 `node-exporter` 작은 상자)와 파드들.
가운데 **프로메테우스** 상자로 **화살표가 프로메테우스 쪽에서 뻗어 나가** 각 대상을
찍는 모양(★걷어가는 방향입니다 — 화살표를 거꾸로 그리면 뜻이 반대가 됩니다).
오른쪽에 **그라파나**(화면)와 **운영 콘솔** 두 개가 프로메테우스를 보고 있는 그림.
★**프로메테우스에는 화면이 없고, 그라파나에는 데이터가 없다**는 게 보이게 그려 주세요.

**⑫ 밀어넣기 vs 걷어가기 — 13장, 작게**
왼쪽: 서버 5개가 각각 중앙으로 화살표를 쏘는 그림(밀어넣기·옛 방식).
오른쪽: 가운데 하나가 여러 대상으로 화살표를 뻗는 그림(걷어가기·새 방식).
★오른쪽 대상들에는 **점선 테두리**를 둘러 *"생겼다 사라지는 것"* 을 표현해 주세요.
그게 방식을 바꾼 이유입니다.

**⑬ ★디스크가 건물을 못 넘습니다 — 13장, 3컷**
(1) 건물 B 에 디스크가 먼저 생김. 파드는 아직 자리 미정(물음표).
(2) 파드가 **건물 A** 에 앉음 → 디스크와 파드 사이에 **✗ 표시**. 파드가 못 뜸.
(3) 방식을 바꾼 뒤: 파드가 **먼저** 건물 A 에 앉고, 디스크가 **그 건물에** 생김 → ✓.
★**이 문서에서 두 번째로 이해가 어려운 대목입니다.** ⑤(무상태화) 다음으로 공들여 주세요.

**⑭ ★★데이터베이스가 두 대인 이유 — 5장 DB 절, 나란히 두 장**
왼쪽 「앱」: 파드 2벌이 **둘 다 화살표를 받는** 그림(둘 다 일함).
오른쪽 「DB」: 주 한 대만 화살표를 받고, 예비는 **주에서 예비 쪽으로 가는 복사 화살표**만
받는 그림. ★예비 쪽에는 바깥에서 오는 화살표가 **없어야** 합니다.
그 아래 한 줄: **"앱은 일을 나누려고 둘, DB 는 대비하려고 둘"**.
★**두 대를 서로 다른 건물 아이콘 안에** 그려 주세요.

**⑮ 데이터베이스 접속 주소 — 포트와 호스트가 가리키는 것이 다릅니다**
가운데 서버 두 대(주·예비)를 놓고, 왼쪽에 건물 A 입구·건물 B 입구를 둡니다.
**두 입구에서 나온 `:3306` 선이 모두 「주」로**, **`:3307` 선이 모두 「예비」로** 갑니다.
★**포트가 역할을 고르고, 호스트는 들어가는 문을 고른다**는 것이 선으로 보이게.
★장애 조치가 나면 「주」 딱지가 다른 서버로 옮겨 가고 **선은 그대로**라는 것을
작은 화살표로 덧붙여 주세요.

## ★★실제 콘솔 화면을 붙일 자리를 만들어 주세요

그림(SVG)과 별개로, **실제 카카오클라우드 콘솔 화면을 나중에 끼워 넣을 것**입니다.
**빈 자리를 미리 만들어 주세요.**

### 자리를 만드는 방법

각 자리는 이렇게 만들어 주세요.

- `<figure>` 안에 **점선 테두리의 빈 상자**를 두고, 가운데에 `[화면 1]` 같은 번호와
  **무슨 화면인지** 를 적어 둡니다
- 그 아래 `<figcaption>` 에 **"이 화면에서 무엇을 봐야 하는지"** 를 한 줄로 씁니다
- 상자는 `aspect-ratio` 로 가로가 긴 비율(16:10 정도)을 잡아 두세요.
  나중에 그림을 넣어도 배치가 안 흔들립니다

★**설명을 캡션에 꼭 써 주세요.** 콘솔 화면은 정보가 빽빽해서, 그냥 붙여 두면
**어디를 봐야 할지 모릅니다.** "왼쪽 위 상태가 `Available` 인 것을 보세요" 같은
안내가 화면보다 중요합니다.

## 활자와 색

- **서버 이름·포트·계정명·주소는 전부 고정폭 글꼴**로. 설명글과 기계 이름이 눈으로 구분되게.
  인프라 문서에서 가장 헷갈리는 지점입니다.
- 흔한 AI 문서 팔레트(따뜻한 크림+세리프+테라코타, 보라-파랑 그라데이션,
  검정 바탕에 형광 초록)는 피하세요.
- 한글 웹폰트는 외부에서 못 불러오니 **시스템 글꼴 스택**을 쓰세요
  (`-apple-system, "Segoe UI", "Malgun Gothic", "Apple SD Gothic Neo", sans-serif`).

## 기술

- **라이트·다크 두 테마 모두** 제대로 되게. CSS 변수로 토큰을 잡고
  `prefers-color-scheme` 과 `:root[data-theme="dark"]` 둘 다 대응.
  ★**SVG 그림도 다크 모드에서 보이는지 확인하세요** — 검은 선이 검은 배경에 묻히지 않게.
- 표·코드 블록·넓은 그림은 각자 `overflow-x:auto` 컨테이너 안에.
- 외부 리소스(폰트 CDN, 이미지 URL) 없이 **자체 완결**로.
- 휴대폰에서도 읽히게. 표는 가로 스크롤, 2단 비교는 1단으로 접히게.
