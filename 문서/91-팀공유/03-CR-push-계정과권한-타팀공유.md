# Container Registry 에 이미지 올리려면 — 계정과 권한

카카오클라우드에서 이미지를 push 하려고 서비스 계정을 만들 때 무엇을 골라야 하는지
정리했습니다. **전부 저희가 직접 해 보고 확인한 것**이고, 확인 못 한 것은 그렇게 적었습니다.

---

## 한 줄 답

**서비스 계정을 만들고 역할은 `프로젝트 멤버` 하나만 줍니다. 그리고 IAM 액세스 키를 발급해
`docker login` 에 씁니다.**

---

## 1. 왜 `프로젝트 멤버` 인가

★**Container Registry 전용 IAM 역할이 없습니다.** 콘솔의 서비스 역할 목록을 전수로 확인했는데
CR 이 아예 없습니다. 대신 공식 문서가 이렇게 말합니다.

> IAM 역할이 **프로젝트 관리자 또는 프로젝트 멤버**인 경우, 자동으로 Container Registry 관리자
> 역할이 부여됩니다. … 이미지 Push와 Pull을 할 수 있습니다.
> — 리포지토리 생성 및 관리 문서

**저희가 실제로 재 본 결과입니다.**

| 계정에 준 역할 | CR 토큰이 돌려준 권한 | push |
|---|---|---|
| `프로젝트 리더` (조회 전용) | `actions: ["pull"]` | ✗ |
| **`프로젝트 멤버`** | push 성공 (이미지 3종 업로드) | **○** |

★`push,pull` 을 요청해도 **`pull` 만** 돌아옵니다. 로그인은 되는데 push 만 막히므로
*"키가 잘못됐나"* 로 헤매기 쉽습니다. **인증(login)과 권한(push)을 나눠서 보십시오.**

---

## 2. ⚠️먼저 알아야 할 함정

### ⓐ 서비스 계정의 역할은 만든 뒤에 못 바꿉니다

잘못 고르면 **계정을 새로 만들어야** 합니다. 키도 다시 발급하고 검증도 다시 합니다.
저희는 이것 때문에 계정을 한 번 다시 만들었습니다.

### ⓑ 저장소별로 권한을 좁히는 길은 서비스 계정에 안 먹습니다

저장소 상세의 `[권한 설정] → 리포지토리 멤버` 로 좁히려 했는데 **서비스 계정은 후보에
들어가지 않습니다.**

```
catchap-ops                                        → "추가할 수 없는 계정입니다."
catchap-ops-kc-sfacspace05@kc.serviceaccount.com   → 같은 문구
```

**사람 계정만 됩니다.** 그래서 서비스 계정으로 push 하려면 **프로젝트 전체 권한 말고는
선택지가 없습니다.**

### ⓒ `프로젝트 멤버` 는 생각보다 넓습니다

그 키를 가진 사람은 **같은 프로젝트의 VM · 로드밸런서 · MySQL 도 지울 수 있습니다.**

★★**「관리자 말고 멤버니까 안전하다」는 착각입니다.** 공식 문서를 그대로 옮기면
**둘의 차이는 IAM 리소스 하나뿐**입니다.

```
프로젝트 관리자   서비스 리소스 CRUD  +  ★IAM 리소스(계정·역할·키) 제어
프로젝트 멤버     서비스 리소스 CRUD  ·  ★"IAM 리소스는 설정할 수 없음"
```

**서비스 자원(VM·LB·MySQL·클러스터·레지스트리)은 둘 다 똑같이 지웁니다.**
멤버로 주는 것이 막아 주는 것은 딱 하나 — **키가 스스로 번식하는 것**입니다.

```
관리자 키가 새면   ★새 서비스 계정과 새 키를 만들어 영구 발판을 남길 수 있다
멤버 키가 새면     자원은 지울 수 있지만 ★새 계정·새 키는 못 만든다
```

CI 용 키는 서버 파일로 저장되므로, 저희는 이렇게 했습니다.

```
· 역할은 프로젝트 멤버 하나만        (권한 상승만 막힘 — 자원 삭제는 못 막습니다)
· 키는 빌드 서버 한 곳에만 · 0600
· 빌드 서버는 인바운드가 없는 사설 VM
```

### ⓓ ★그 계정으로 Secrets Manager 시크릿 목록이 다 보입니다

**2026-08-05 에 저희가 직접 잰 것입니다.** 배포용으로만 쓰려고 만든 계정인데,

```
IAM 토큰 발급     → 201
시크릿 목록 조회   → 200 · 5건 전부 보임
ID 마스킹         → 전부 「아니오」 = 막는 것이 없음
```

★**비밀값을 Secrets Manager 에 두신다면 항목마다 「접근 제어」를 켜 두십시오.**
켜면 명단 밖 계정에는 **목록에서부터 안 보입니다**(저희 프로젝트의 다른 분 시크릿이
실제로 그렇게 안 보였습니다). 안 켜면 **배포용 키로 로그인 서명 키·결제 키까지 닿습니다.**

## 3. 실제 순서

### ① 저장소(리포지토리) 만들기

```
콘솔 > Container Pack > Container Registry > 리포지토리 > 우측 상단 [리포지토리 생성]
```

⚠️**저장소 이름은 만든 뒤에 못 고칩니다.** 수정 가능한 것은 **공개 여부 · 설명 ·
태그 덮어쓰기 · 이미지 스캔** 네 가지뿐입니다.

⚠️**이름은 4~20자입니다.** 저희는 `catchap-frontend-repo`(21자)가 거절돼
`catchap-front-repo` 로 줄였습니다. 그전에 만든 오타본(`chatchap-frtend-repo`)은
이름을 못 고쳐서 **새로 만들고 옛것을 지웠습니다.**

⚠️**클러스터나 리포지토리를 같은 이름으로 재생성하면 기존 앱이 엉뚱한 곳에 붙을 수
있습니다**(카카오 문서 주의사항).

★**저희는 항상 콘솔에서 먼저 만들고 push 했습니다. push 가 저장소를 자동으로 만들어
주는지는 시험해 보지 않았습니다.** 미리 만드시는 쪽을 권합니다.

### ② 서비스 계정 만들기

```
콘솔 > IAM > 서비스 계정 > [생성] > 역할 [프로젝트 멤버] 하나
```

### ③ IAM 액세스 키 발급

```
⚠️계정당 최대 2개
⚠️이름·설명은 생성 후 수정 불가
⚠️IAM 키는 이름 재사용 불가 (S3 액세스 키는 재사용 됨 — 종류가 다릅니다)
⚠️발급 시점의 권한을 상속. 나중에 역할이 바뀌면 겹치는 권한만 남습니다
```

### ④ 빌드 서버에서 로그인

```bash
docker login kc-sfacspace05.kr-central-2.kcr.dev \
  --username '{IAM 액세스 키 ID}' \
  --password '{IAM 보안 액세스 키}'
```

★★**여기 쓰는 것은 IAM 액세스 키입니다. S3 액세스 키로는 `401 login failed` 입니다.**
(2026-07-29 실측 — 두 종류를 헷갈려 한참 헤맸습니다.)

`kc-sfacspace05` 자리에는 **그 팀의 프로젝트 이름**이 들어갑니다.

### ⑤ 태그와 push — ★경로가 2단입니다

```
{프로젝트}.kr-central-2.kcr.dev/{저장소}/{이미지}:{태그}
```

```bash
docker tag  myapp:local  {프로젝트}.kr-central-2.kcr.dev/{저장소}/{이미지}:{커밋해시12자}
docker push             {프로젝트}.kr-central-2.kcr.dev/{저장소}/{이미지}:{커밋해시12자}
```

★**저장소 이름 뒤에 이미지 이름이 한 단 더 붙습니다.** 저장소만 쓰면 레지스트리가
**`is wrong name`** 으로 거절합니다. 저희가 이것 때문에 한참 못 찾았습니다.

★**태그에 `latest` 를 쓰지 마십시오.** 커밋 해시를 쓰면 **지금 무엇이 떠 있는지**
나중에 추적됩니다. 저희는 12자리 커밋 해시를 씁니다.

### ⑥ 쿠버네티스에서 받으려면 — imagePullSecret

**저장소가 비공개면 이게 없을 때 파드가 `ImagePullBackOff` 로 멈춥니다.**
저희가 실제로 겪었습니다.

```bash
kubectl -n {네임스페이스} create secret docker-registry {이름} \
  --docker-server=kc-sfacspace05.kr-central-2.kcr.dev \
  --docker-username='{IAM 액세스 키 ID}' \
  --docker-password='{IAM 보안 액세스 키}'
```

만들어진 시크릿은 `kubernetes.io/dockerconfigjson` 형식입니다.

```yaml
spec:
  template:
    spec:
      imagePullSecrets:
        - name: {이름}
```

★**pull 에는 pull 만 되는 계정을 쓰는 편이 낫습니다.** push 계정을 그대로 넣으면
**클러스터를 볼 수 있는 사람이 push 권한까지 얻습니다.** `프로젝트 리더`(조회) 계정이
`actions:["pull"]` 을 받는 것을 저희가 확인했으니 그런 계정을 따로 쓰실 수 있습니다.

## 4. 한눈에

```
서비스 계정 역할        프로젝트 멤버 하나          ★생성 후 수정 불가
docker login 자격증명   IAM 액세스 키              ★S3 키는 401
이미지 경로            {저장소}/{이미지}:{태그}    ★2단
저장소 이름            4~20자                    ★생성 후 수정 불가
저장소별 권한 좁히기     ★서비스 계정에는 불가       사람 계정만 됨
K8s 에서 받을 때        imagePullSecret 필수       없으면 ImagePullBackOff
같이 점검할 것          ★Secrets Manager 접근 제어  안 켜면 이 키로 비밀값까지 닿음
```
