## 한 장 요약

**지금 서비스는 서버 5대에 손으로 얹혀 있습니다. 이걸 쿠버네티스로 옮깁니다.**

바뀌는 것을 한 줄로 하면 이렇습니다.

```
지금   서버에 직접 들어가서 배포한다        → 배포하는 동안 서비스가 멈춘다
이후   이미지를 만들어 올리면 알아서 교체된다  → 안 멈춘다 · 되돌리기 한 줄
```

**여러분이 실제로 겪을 변화는 배포 방식 하나**입니다. 코드 쓰는 방식은 그대로입니다.

# 1부 — 큰 그림

## 1. 지금 어떻게 돼 있나

서버 5대에 도커 컨테이너가 얹혀 있습니다.

```
210.109.52.124   백엔드      backend-api · behavior-ai · caddy
210.109.14.25    프론트      frontend-web · caddy
210.109.52.114   DB         MySQL (직접 설치)
210.109.53.16    "AI 서버"   ★아무것도 없음 (이름만 AI)
61.109.239.231   GPU        STT 워커 · 캡차 서비스 · MySQL
```

배포는 이렇게 합니다.

```
코드 수정 → 서버에 SSH → tarball 올림 → docker compose up -d --build
                                          ↑ 서버에서 직접 빌드
```

## 2. 무엇이 문제인가

### ① 배포하는 동안 서비스가 멈춥니다

`--build`가 서버에서 돌기 때문입니다. 빌드가 끝날 때까지 그 서버는 요청을 못 받습니다.

### ② 서버가 죽으면 아무도 모릅니다

지금은 컨테이너가 죽으면 **사람이 알아채고 다시 띄워야** 합니다.
특히 **옛 GPU의 캡차 서비스는 `ms` 계정이 손으로 띄운 프로세스**라,
그 서버를 재부팅하면 **조용히 안 올라옵니다**(systemd 등록이 없습니다).

### ③ 무엇이 떠 있는지 모릅니다

배포 서버 홈 디렉터리에 이런 게 쌓여 있습니다.

```
backend.tgz · be.tgz · be-batch.tgz · be-committed.tgz · be-graded.tgz
be-mathchap.tgz · be-playback.tgz · be-purge.tgz · be-scratch.tgz · be-widget.tgz
```

**어느 게 지금 도는 것인지 아무도 모릅니다.** 되돌리려 해도 무엇으로 되돌릴지 모릅니다.

### ④ 서버를 늘릴 수 없습니다

앱을 2벌 띄우면 **한쪽에 올린 영상이 다른 쪽에서 안 보입니다.**
파일을 서버 디스크에 쌓기 때문입니다.

### ⑤ 데이터베이스가 인터넷에 열려 있습니다

DB 서버의 MySQL이 `0.0.0.0:3306`으로 듣고 있습니다. 비밀번호 하나가 새면 끝입니다.

## 3. 어떻게 바뀌나

```
                        인터넷
                          │
                  catchap5.com (도메인)
                          │
            ┌─────────────▼─────────────┐
            │      로드밸런서             │  들어온 요청을 나눠 준다
            └─────────────┬─────────────┘
                          │
   ┌──────────────────────────────────────────────────┐
   │  쿠버네티스 (서버 2대)                              │
   │                                                  │
   │   backend      2벌     서로 다른 건물의 서버에      │
   │   frontend     2벌                                │
   │   behavior-ai  1~2벌                              │
   │   captcha      2벌                                │
   │                                                  │
   │   ★한 대가 죽으면 나머지가 받고, 죽은 몫을 다시 띄운다  │
   └───────┬──────────────┬──────────────┬────────────┘
           │              │              │
      관리형 MySQL     Object Storage   Valkey(캐시)
      (백업·이중화)     (영상·이미지)     ※지금은 안 씀
```

**핵심은 "앱이 자기 서버를 기억하지 않게" 만드는 것**입니다.
그래야 아무 서버에서나 똑같이 돌고, 몇 벌을 띄우든 상관없어집니다.

### 확인해 보니 대부분 이미 돼 있었습니다

처음에 저는 *"로그인 정보가 앱 메모리에 있어서 서버를 늘리면 로그인이 풀릴 것"*이라고
적었는데, **코드를 열어 보니 틀렸습니다.**

| 서버에 남을 법한 것 | 실제 위치 |
|---|---|
| 로그인 세션 | 토큰(JWT) + DB `refresh_tokens` |
| 캡차 문제·정답 | **암호화해서 토큰 안에** — 서버에 안 남음 |
| 캡차 토큰 재사용 차단 | DB `captcha_consumed_tokens` |
| 로그인 시도 횟수 | DB `login_throttle` |
| 문항 생성 작업 상태 | DB `lecture_question_gen_jobs` |

코드에 이유까지 적혀 있었습니다.

> *"무상태 서명 토큰의 리플레이 차단은 인메모리로는 멀티워커/재시작에 무효
>  → (kind, token_id) UNIQUE로 원자적 소비"*

**앱을 만들 때 이미 여러 대로 늘릴 것을 염두에 두고 만들어져 있었습니다.**
그래서 실제로 옮긴 것은 **영상·이미지 3.3GB와 데이터베이스 둘뿐**입니다.

# 2부 — 자세히

## 4. ★여러분에게 실제로 달라지는 것 — 배포

### 지금

```
코드 수정 → 서버 SSH → tarball 올림 → docker compose up -d --build
```

### 이후

```
코드 수정 → GitHub 에 push          ← 여러분이 하는 건 여기까지
              │
         ① 이미지 빌드   코드를 실행 가능한 꾸러미로 만든다
         ② 레지스트리에 올림
         ③ 배포          쿠버네티스에 "이 이미지로 바꿔라"
              │
         파드를 하나씩 교체 — 새것이 준비되면 옛것을 내린다
```

**①②③은 처음엔 인프라(저)가 합니다.** 나중에 명령 하나로 자동화할 예정입니다.

### 무엇이 좋아지나

| | 지금 | 이후 |
|---|---|---|
| 배포 중 | ★**서비스 끊김** | **안 끊김** |
| 되돌리기 | 옛 tarball 찾아 재빌드 | `kubectl rollout undo` **한 줄** |
| 무엇이 떠 있나 | 모름 | **이미지 태그 = 커밋 해시** |

★**이미지 태그에 커밋 해시를 박습니다.** 예를 들어 지금 구워 둔 백엔드 이미지는
`catchap-backend:5fb2b5d965d5` 입니다. **그 해시로 GitHub 을 찾으면 정확히 그 코드**입니다.
`be-widget.tgz` 가 뭔지 모르는 문제가 없어집니다.

### 주의할 것 — 프론트는 빌드할 때 값이 박힙니다

Vite 가 `VITE_*` 를 **번들 안에 넣어 버립니다.** 런타임에 못 바꿉니다.

```
VITE_API_BASE_URL            https://api.catchap5.com
VITE_CATCHAP_EDU_SITE_KEY    (사이트 키)
```

**이 값을 바꾸려면 이미지를 다시 구워야 합니다.** 지금도 그랬지만, 앞으로도 같습니다.


## 부록 — 용어

| 말 | 뜻 |
|---|---|
| **컨테이너** | 프로그램 + 그게 돌아가는 데 필요한 것을 통째로 담은 꾸러미 |
| **이미지** | 그 꾸러미의 설계도. 이걸로 컨테이너를 몇 개든 찍어낸다 |
| **레지스트리(CR)** | 이미지를 두는 창고. ★GitHub 과 다르다 — GitHub 은 레시피, 여기는 조리된 도시락 |
| **쿠버네티스** | 컨테이너를 어느 서버에 몇 개 띄울지 관리하는 것. 죽으면 알아서 다시 띄운다 |
| **파드** | 쿠버네티스가 띄우는 컨테이너 한 덩어리 |
| **노드** | 파드가 실제로 도는 서버 |
| **로드밸런서** | 들어온 요청을 여러 서버에 나눠 주는 것 |
| **가용 영역** | 같은 지역의 물리적으로 분리된 데이터센터. 한쪽이 정전돼도 다른 쪽은 산다 |
| **Object Storage** | 파일을 두는 창고. 서버 디스크와 달리 서버가 몇 대든 같은 파일을 본다 |
| **무상태(stateless)** | 앱이 자기 서버에 아무것도 안 쌓는 상태. 그래야 몇 벌이든 띄울 수 있다 |
| **컷오버** | 도메인이 새 서버를 가리키게 바꾸는 순간. 실제로는 DNS 한 줄 |
