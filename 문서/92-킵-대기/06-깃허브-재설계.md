## 2. 브랜치 설계

### 2-A. 어떤 방식을 쓸까 — GitHub Flow

```
★GitHub Flow    main + 작업 브랜치.  단순. ★배포가 잦고 staging 이 없을 때 맞습니다
 Git Flow       main + develop + release + hotfix.  릴리스 주기가 있을 때. ★우리에겐 과합니다
 Trunk-based    main 에 아주 자주 작게.  자동 테스트가 촘촘해야 합니다
```

★**우리는 5명이고 배포가 잦고 staging 이 없습니다. GitHub Flow 가 맞습니다.**

### 2-B. 브랜치 종류와 이름

| 이름 | 무엇 | 수명 |
|---|---|---|
| **`main`** | ★프로덕션. **항상 배포 가능한 상태** | 영구 |
| `feature/<요약>` | 새 기능 | PR 병합 후 삭제 |
| `fix/<요약>` | 버그 수정 | 〃 |
| `hotfix/<요약>` | ★프로덕션 급한 수정 | 〃 |
| `chore/<요약>` | 빌드·설정·문서 | 〃 |
| `archive/<원래이름>-<날짜>` | 보관 | 영구 (읽기용) |

★**요약은 영문 소문자·하이픈**으로 씁니다 — 도구가 한글 브랜치 이름에서 자주 걸립니다.
커밋 메시지는 지금처럼 한국어로 씁니다.

```
좋음   feature/portone-refund · fix/lecture-gate · hotfix/login-500
나쁨   jy · sw · ms · my · th        ← ★사람 이름은 "무엇을 하는지" 를 안 알려 줍니다
       th-after · th-before          ← 시간 순서만 있고 내용이 없습니다
```

### 2-C. 흐름

```
main 에서 분기
  ↓  작업 · 커밋
PR 열기
  ↓  ★CI 통과 (빌드·테스트)
리뷰 1명 승인
  ↓  ★squash merge  →  main 에 커밋 1개로 들어감
브랜치 삭제 · 자동배포
```

★**`squash merge` 를 권합니다** — main 이력이 **「한 기능 = 한 커밋」** 이 되어
**되돌리기가 쉽습니다**(`git revert <커밋 하나>`).

### 2-D. `main` 보호 규칙

```
· 직접 push 금지
· PR 필수 · 승인 ★1명 이상
· ★CI 통과가 병합 조건
· force push 금지 · 삭제 금지
· ★관리자도 예외 없음 (include administrators)
```

★★**staging 이 없습니다.** `main` 병합이 곧 배포라 **PR·리뷰가 유일한 안전장치**입니다.
⬜나중에 네임스페이스를 하나 더 만들어 staging 을 둘 수 있습니다(클러스터는 그대로).

## 3. 태그 규칙

```
이미지 태그 = ★커밋 short SHA (12자)

```

★**지금 우리 태그 4개 중 3개가 이미지 ID 라 어느 커밋인지 모릅니다.**

```
backend      79d5e2d05a1e   ← 이미지 ID
frontend     488c549a0b53   ← 이미지 ID

★0805 저녁 기준 ★넷 다 이미지 ID 입니다 — 커밋으로 가리킬 수 있는 것이 하나도 없습니다

왜 그렇게 됐나
  behavior-ai   GPU 소스가 ★어느 커밋과도 일치하지 않음 (origin/sw 의 repositories.py 는 24,216)
  captcha       ★위젯 빌드 결과물(static/dist)이 git 에 없음
  backend·front  옛 서버에서 구워진 이미지를 그대로 가져옴 — 그 서버에 git 저장소가 없음
→ ★저장소를 정리하고 CI 로 구우면 자연히 커밋 해시가 됩니다
```
