**이 문서의 모든 IP·엔드포인트·포트는 콘솔과 실측으로 확인한 값입니다.** 추정은 "미확인"으로 표시했습니다.

## 0. 왜 옮기는가 — 지금 구조의 한계

```
지금 (옛 VPC)                          문제
서버마다 앱이 하나씩 통째로 떠 있음        서버를 늘리면 로그인이 풀린다 (세션이 프로세스 메모리)
미디어가 서버 로컬 디스크에 있음           서버마다 파일이 흩어진다
설정이 .env 파일로 서버에 박혀 있음        바꿀 때마다 서버에 들어가야 한다
MySQL이 서버 안에서 돌거나 단일 지점       그 서버가 죽으면 끝
```

**목표는 "앱을 상태 없이(stateless) 만들고, 상태는 전부 관리형 서비스로 뺀다"** 입니다.
그러면 파드를 몇 개로 늘려도 되고, 죽어도 다시 뜨면 됩니다. K8s는 그 결과로 필요해진 것이지
목적이 아닙니다.

## 2. 왜 이렇게 나눴나 — 요소별 근거

### 2-A. 앱 3개는 K8s 안으로

| 서비스 | 컨테이너 | 포트 | 왜 K8s |
|---|---|---|---|
| `catchap-frontend` | nginx + Vite `dist` | 80 | 정적 파일. 복제가 가장 쉽고 이득이 큼 |
| `catchap-backend` | FastAPI (uvicorn, 워커 2) | 8000 | 무상태화만 하면 수평 확장 가능 |
| `catchap-ai` | 행동 위험도 AI | 8010 | GPU 불필요. CPU 추론 |

★프론트는 **빌드 타임에 `VITE_*`가 번들에 인라인**되므로 API 주소가 이미지에 박혀 나옵니다.
주소가 바뀌면 재빌드해야 합니다(런타임 주입 불가).

### 2-B. STT 워커는 K8s 밖에 남긴다

**노드 풀이 `m2a.xlarge` CPU 인스턴스라 GPU가 없습니다.** STT는 Tesla T4에서 faster-whisper
large-v3를 돌리므로 K8s 안으로 넣으면 GPU를 못 씁니다.
→ **GPU VM(`10.0.5.57`)에 docker로 띄우고, 백엔드가 `STT_WORKER_URL`로 호출**합니다.

```
백엔드 파드 ──(영상/오디오 POST + X-Worker-Token)──▶ 10.0.5.57:8100 ──▶ T4
```

0722 실측 — 247MB mp4 → **232초 · 566 세그먼트**, OpenAI 키 없이 성사.
★강사 자막이 업로드돼 있으면 STT를 건너뜁니다.

### 2-C. 인그레스는 `hostNetwork: true`

카카오클라우드 문서의 제약입니다.

> 현재 Kubernetes Engine 서비스에서는 **Admission Webhook을 지원하지 않습니다.**
> Admission Webhook 설정된 서비스를 배포하려면 **`hostNetwork: true` 설정이 필요합니다.**

이 설정이면 컨트롤러가 **노드의 80 포트를 직접 점유**합니다. 그래서 오늘 워커 보안 그룹에
**TCP 80(출발지 `10.0.0.0/16`)** 을 열었습니다. 이게 없으면 502가 납니다.

### 2-D. 데이터는 전부 관리형 · 다중 AZ

```
MySQL    HA · 다중 AZ 사용 · 자동 백업 4건(매일 01:00 · 14일)
         앱은 Primary 엔드포인트(az-a:3306)를 씀
         Standby(az-b:3307)는 오늘 개방 → 읽기 전용 복제본으로 조회 분리 가능
Valkey   노드 2대 · 자동 장애 조치 · 클러스터 모드 미사용
         세션 · 캡차 챌린지 상태 · 레이트리밋 카운터
         ★Primary가 2-b, Read가 2-a  (MySQL과 AZ가 반대)
Object   비공개 · 역할 그룹 매핑 6건 이미 존재
Storage  Lifecycle: stt-temp/ 접두사 3일 후 삭제
```

★**Valkey Primary는 2-b, MySQL Primary는 2-a** 입니다. 파드가 두 AZ에 흩어지면 어느 쪽이든
한 번은 AZ를 건너갑니다. 같은 리전 내부라 지연은 작지만 **알고 있어야 하는 비대칭**입니다.

### 2-E. 설정은 Secrets Manager에서 읽는다

두 방식이 있습니다.

```
(가) 앱이 기동 시 Secrets Manager를 읽는다     K8s Secret은 부트스트랩 키 1개만
(나) 시크릿 4건을 K8s Secret으로 복사한다      런타임 의존이 없지만 두 곳을 동기화해야 함
```

**(가)를 택합니다.** 이유 — 시크릿을 바꿀 때 K8s를 건드리지 않아도 되고, 관리 지점이
Secrets Manager 하나로 모입니다. `catchap-backend` 계정이 이미 `kms11` 접근 명단과
버킷 권한을 갖고 동작 중이라 **그 계정을 그대로 부트스트랩 자격증명으로 씁니다.**

★`.env`는 **이미지에 굽지 않습니다** — Dockerfile 주석에도 명시돼 있습니다.
비밀값을 이미지에 넣으면 레지스트리를 볼 수 있는 사람이 다 보게 됩니다.

### 2-F. 이미지는 CR을 거친다

```
경로 형식   kc-sfacspace05.kr-central-2.kcr.dev/<저장소>/<이미지>:<태그>     ★2단
push       빌드 호스트에서. 프로젝트 멤버 이상 필요 (실측 확정)
pull       catchap-ops 로 imagePullSecret          actions:["pull"] 실측 확인
```

★**빌드는 클러스터가 하지 않습니다.** 완성된 이미지를 워커가 받아서 켜기만 합니다.

강사님의 판단을 그대로 따릅니다.

#### ★Deployflow 는 왜 못 쓰나 — 확인 결과 (0803)

```
문서   "퍼블릭 엔드포인트가 할당되고 'Provisioned' 상태인 클러스터만"  (배포 대상 조건)

       https://04c32b21-…-internal.ke.kr-central-2.kakaocloud.com:443   ← 주소에 -internal
문서   클러스터 생성 후 수정 가능 = 이름 · 설명 60자.  ★엔드포인트 변경 메뉴 없음
```

MemStore 사용자 인증·시크릿 이름·서비스 계정 역할과 **같은 패턴**입니다 —
만들 때만 정하는 값입니다.

**왜 이런 서비스가 있나 / 실무는 다 노출하나** — 팀에서 다시 나올 질문이라 적어 둡니다.

- 관리형 쿠버네티스는 **기본이 퍼블릭인 경우가 많습니다.** 대신 **허용 IP 대역을 좁힙니다**
  (GKE `Control plane authorized networks` · EKS `Public endpoint access CIDRs` ·
   AKS `API server authorized IP ranges`).
- 퍼블릭이어도 TLS·인증·RBAC 가 걸려 있어 **"누구나 들어온다"가 아니라
  "누구나 문을 두드릴 수 있다"** 에 가깝습니다. 그래도 프라이빗이 더 안전합니다 —
  **문을 두드릴 기회조차 안 주니까요.** 금융·공공이 프라이빗을 쓰는 이유입니다.
- Deployflow 가 퍼블릭을 요구하는 건 **카카오의 관리 평면이 우리 VPC 밖**에 있어서
  프라이빗이면 길 자체가 없기 때문입니다. 프라이빗용 경로(피어링·프라이빗 링크)를
  카카오가 아직 안 만든 것입니다.

**프라이빗 클러스터의 실무 배포 방식 세 가지**

```
① 배스천/점프서버에서 kubectl        ← 우리가 지금 하려는 것
② 클러스터 안에서 도는 CD (GitOps)   ← Argo CD·Flux. 요즘 표준으로 가는 쪽
③ 퍼블릭 + IP 허용목록               ← Deployflow 를 쓰려면 이것
```

★**②가 프라이빗의 정석**입니다. Argo CD 를 클러스터 안에 띄우면 그게 GitHub 을
주기적으로 확인해 **스스로 끌어다 배포**합니다. 밖에서 안으로 들어올 필요가 없어져
"배포 자동화"라는 목적을 **API 서버를 노출하지 않고** 달성합니다.

우리 규모(서비스 4개·사용자 19명)에서는 ①로 충분합니다. 배포가 잦아지면 ②를 봅니다.

### 3-B. ★로드밸런서가 단일 AZ — 워커2를 못 붙인다

> 로드 밸런서와 동일한 VPC 및 **가용 영역(kr-central-2-a)** 에 있는 인스턴스만
> 대상 그룹에 추가할 수 있습니다.

```
워커1  10.0.2.128  (2-a)   ✅ 대상 등록됨 · Active · 100%
워커2  10.0.6.202  (2-b)   ❌ 추가 불가
```

**결과** — 워커가 2대인데 **LB는 1대만 봅니다.** 워커1이 죽으면 워커2가 살아 있어도
서비스가 끊깁니다. **K8s의 AZ 이중화가 인그레스 단계에서 무력화됩니다.**

**★0731 확인 — 우리 LB가 잘못 만들어진 게 아닙니다. 단일 AZ가 정상입니다.**

공식 문서 원문:

> **"로드 밸런서 노드는 단일 가용 영역 내 트래픽을 분산 및 배포하지만,
> 고가용성 그룹에 연결하여 사용함으로써 여러 가용 영역에 걸쳐 트래픽 분산 및
> 고가용성 보장 가능"**

> 고가용성 그룹 = **"둘 이상의 서로 다른 가용 영역에 생성된 동일한 설정 및 유형의
> 로드 밸런서 노드를 하나로 묶어 고가용성을 보장하는 리소스"**

→ **LB를 "수정"해서 다중 AZ로 만들 수는 없습니다.** 카카오클라우드 방식은
**2-b에 LB 노드를 하나 더 만들고 `고가용성 그룹`으로 묶는 것**입니다.
LB는 전용 IAM 역할이 없어 `프로젝트 관리자`가 통로인데, 대상 그룹을 이미 우리가
고쳤으므로 **권한은 있습니다.**

#### ★★0804 추가 — 단계가 하나 더 있었습니다 (콘솔 생성 화면으로 확인)

고가용성 그룹 생성 화면을 열어 보니 **LB 노드를 놓을 서브넷을 고르게** 되어 있고,
안내 문구가 이렇습니다.

> **인터넷 경계** — 퍼블릭 IP가 연결되어 있어 인터넷을 통해 통신할 수 있습니다.
> **퍼블릭 서브넷에 위치한 LB 노드를 연결해야 합니다.**

**그런데 `Team1-VPC` 에 퍼블릭 서브넷이 하나뿐이고 그것도 2-a 입니다.**

| 서브넷 | CIDR | AZ |
|---|---|---|
| ★`catchap-jump-2a` | 10.0.1.0/24 | **2-a** |
| `catchap-core-2a` · `catchap-gpu-2a` | 10.0.2.0/24 · 10.0.5.0/24 | 2-a |
| `catchap-core-2b` | 10.0.6.0/24 | **2-b** |

★**2-b 에 퍼블릭 서브넷이 없어서, 지금 구성으로는 2-b 에 LB 노드를 놓을 수가 없습니다.**

**그래서 실제 순서는 4단계입니다** (기존 기록은 ③④만 있었습니다).

```
① 2-b 에 퍼블릭 서브넷 생성                  ★지금 없음
② 인터넷 게이트웨이 라우팅에 연결             ★이름이 아니라 라우팅이 퍼블릭을 정한다(문서 8번)
③ 고가용성 그룹 생성 (2-a + 2-b LB 노드)
④ 인증서 재부착 · DNS 컷오버 대상 변경        공인 IP 가 바뀔 가능성
```

★①②는 **네트워크 구조 변경**입니다. 이전 중에 건드릴 일이 아닙니다.
*"LB 하나 더 만들면 되겠지"* 로 시작하면 ①에서 막힙니다.

★**언제 하나** — 우리 규모(사용자 19명)에서는 **이전을 끝내고, 실서비스 전환 전**이 적기입니다.
이전만 해도 파드 장애·워커2 장애는 자동으로 견디게 되므로 지금보다 이미 낫습니다.
남는 위험은 **워커1(2-a) 장애 하나**이고, 그때는 2-b 에 LB 를 만들고 도메인을 돌리는
수동 대응이 가능합니다.

캡처 `08-LoadBalancer/20260804-01-고가용성그룹-0개.png` · `20260804-02-고가용성그룹-생성화면.png`

**★결정 (0731) — 지금은 하지 않습니다. 이전을 끝내고 별도로 합니다.**

```
지금   기존 LB(2-a) + 인그레스를 워커1에 고정
       앱 파드는 두 워커에 분산 → 파드 장애·워커2 장애는 이미 견딤
       남는 약점 = 입구가 워커1 하나
이후   2-b에 LB 노드 추가 → 고가용성 그룹으로 묶음
```

**이유 3가지**

1. **아직 모르는 게 있습니다** — ⓐ 기존 LB를 **나중에** 고가용성 그룹에 붙일 수 있는가
   ⓑ **퍼블릭 IP가 유지되는가**(`210.109.55.233`). 세부 문서 경로가 404라 못 읽었습니다.
   **IP가 바뀌면 인증서 재부착 + 컷오버 대상 변경**이 따라옵니다 → 강사님 문의 목록에 추가
2. **지금은 검증할 수 없습니다** — 뒤에 붙일 인그레스가 없어 만들어도 확인이 안 됩니다.
   배포 후에는 "대상 2개 모두 Healthy"로 즉시 확인됩니다
3. **이전과 이중화를 섞으면 원인이 갈립니다**

★**LB를 쓰는 이유는 부하 분산이 아니라 "유일한 안전한 입구"입니다** (0731 실측).
워커 2대 모두 **공인 IP가 없습니다**(`10.0.2.128`·`10.0.6.202`, 나갈 때만 `210.109.82.130` 공유).
그 주소로 밖에서 들어오면 무응답입니다. **LB가 없으면 인터넷에서 앱에 닿을 방법이 없고**,
워커에 공인 IP를 붙이는 것은 K8s 노드를 인터넷에 노출하는 것이라 훨씬 나쁩니다
(옛 GPU 박스가 그렇게 열려 있는 것을 0731에 확인 — 3-I 참조).
그 외에 TLS 종료·고정 진입점·상태 확인도 LB가 맡습니다.

### 3-C. MySQL 장애 조치 — ★대부분 풀렸습니다 (0731 실측)

문서는 포트를 **역할**에 묶는데(`3306(Primary)`) **엔드포인트 이름은 AZ**에 묶여 있어
두 해석이 가능했습니다.

```
해석 A  포트가 역할을 따라감   →  앱은 3306 만 보면 됨
해석 B  포트가 AZ에 고정      →  failover 후 az-b:3307 로 붙어야 함
```

**★해석 A가 맞습니다.** 4가지 조합(`az-a`/`az-b` × `3306`/`3307`)이 전부 열리는데,
`connection_id` 계열로 갈라 보니 **같은 포트면 호스트명이 달라도 같은 mysqld**였습니다.

```
az-a:3306  223740,741,742   ┐ 같은 카운터를 이어받음 = 같은 서버
az-b:3306  223743,744,745   ┘
az-a:3307  167045,046,047   ┐ 같은 서버 (위와는 다른 서버)
az-b:3307  167048,049,050   ┘
```

→ 각 노드 앞에 **포워딩 계층**이 있고 **포트가 대상을 고릅니다.**
**앱은 `3306` 하나만 보면 되고, 호스트명은 역할과 무관합니다.**

★**아직 남은 것** — `3306`이 실제로 쓰기 가능한지(`SELECT @@read_only`)와
**failover가 실제로 일어났을 때도 `3306`이 새 Primary를 따라가는지**는
자격증명·실제 failover가 있어야 확인됩니다. 구조상 따라갈 것으로 보이지만
**시험 전에는 단정하지 않습니다.** → 이전 전에 `수동 Failover`로 한 번 확인.

★호스트명은 역할과 무관하지만 **접속 가능성** 면에서는 의미가 있습니다 —

### 3-E-1. ★★컷오버는 A 레코드가 아니라 CNAME 이다 (0804 실측으로 정정)

**3-E-0 에 *"컷오버 = A 레코드 한 줄"* 이라고 적었는데 틀렸습니다.**
0804 에 고가용성 그룹을 실제로 만들어 보니 **IP 가 아니라 도메인 이름을 줍니다.**

```
catchap-lb-2ab (고가용성 그룹)
  DNS 이름   catchap-lb-2ab-4957cfb14f.blb.kr-central-2.kakaocloud.com
  공인 IP    ★없음 — 화면에 IP 칸 자체가 없다
  가용영역    kr-central-2-a, kr-central-2-b
```

★**A 레코드로 가리킬 대상이 없습니다.** 컷오버는 **CNAME** 이 됩니다.

**좋은 점** — 뒤에서 IP 가 바뀌어도 도메인은 그대로입니다. 카카오가 관리합니다.

**★그런데 루트 도메인에는 CNAME 을 못 붙입니다** (DNS 표준). 가비아도 마찬가지입니다.

가비아 공식 페이지 확인 (0804)

| | |
|---|---|
| 지원 레코드 | `A` · `MX` · `CNAME` · `SRV` · `SPF` · `TXT` |
| **ALIAS / ANAME** | ★**없음** |
| **포워딩** | ★**있음** — "고정 포워딩과 유동 포워딩을 지원합니다" |

**→ 결론: 루트는 가비아 포워딩으로 넘긴다**

```
catchap5.com       ★가비아 유동 포워딩  →  https://www.catchap5.com{경로유지}
www.catchap5.com   CNAME  →  catchap-lb-2ab-….blb.kr-central-2.kakaocloud.com
api.catchap5.com   CNAME  →  같음
```

★**유동 포워딩**이어야 합니다. 고정은 경로가 사라집니다.
지금 Caddy 가 `redir https://www.catchap5.com{uri}` 로 **경로를 유지**하고 있으므로
같은 동작을 하는 쪽을 골라야 합니다.

★**루트가 우리 인프라를 안 거칩니다** — 가비아가 넘겨 주므로 고가용성이 안 깨집니다.

⚠️**아직 확인 못 한 것** — 포워딩이 `https://catchap5.com` 을 어떻게 처리하는지.
가비아가 인증서를 제시하지 못하면 브라우저 경고가 뜹니다. **가비아 로그인이 필요**합니다.

   (STT 워커에 헬스체크를 두면 자동으로 잡힙니다)

★**GPU의 apt 148개를 안 올린 것은 이 위험 때문이 아닙니다.** 확인해 보니 그 148개에는
**커널 이미지도 nvidia도 dkms도 없고**, GPU는 이미 최신 커널(`6.8.0-136`)로 돌고 있습니다.
당시 근거로 든 "커널 1건"은 `linux-base`였습니다 — **개수만 보고 이름을 안 봤습니다.**
미룬 비용은 0(보안 0건)이므로 그대로 두되, **근거는 정정합니다.**
