# 2. ★0730 정정 — 새로 만들 계정은 **`catchap-ops` 1개**

처음엔 `catchap-app`도 신설하려 했으나 **만들 이유가 없다.**
기존 `catchap-backend`의 역할이 앱 런타임에 필요한 조합과 **정확히 일치**하고
(`Object Storage 매니저` + `KMS 사용자` + `Secrets Manager 매니저`),
게다가 **IAM 역할과 별개인 두 가지를 이미 갖고 동작 중**이다.

```
① kms11 접근 제어 허용 명단   ← 시크릿 4건 복호화
② 버킷 권한                  ← 그 계정이 버킷을 직접 만들어 생성 시점에 받음
```

★**새 계정을 만들면 이 둘을 강사님께 다시 부탁드려야 한다.** 기존 계정을 쓰면 그 요청이 0건이 된다.

★★**`kms11`을 우회하지 않는다.** 한때 "시크릿을 kms12(접근제어 미사용)로 옮겨 kms11 의존을 없애자"고
적었으나 **철회했다.** `kms11`은 설명이 **"1팀 사용자 관리형"** 인 우리 전용 키이고 강사님이 일부러
접근 제어를 걸어 둔 것이다. 부탁 한 번 줄이려고 **보안을 낮추고 남이 만든 설정을 말 없이 바꾸는 것**은
맞지 않다. 같은 문서에서 "접근 제어를 끄지 마세요"라고 하면서 우회를 제안한 것도 앞뒤가 안 맞았다.
→ 교훈=[[catchap-doc-hygiene-rule]]

## `catchap-ops` — 우리가 서버에서 쓰는 운영 계정

```
프로젝트 리더 (Reader)
Secrets Manager 매니저 (Manager)
KMS 사용자 (User)
Object Storage 매니저 (Manager)
Alert Center 프로젝트 매니저 (Manager)
Codeflow 매니저 (Manager)
```

| 역할 | 근거 |
|---|---|
| **프로젝트 리더** | VPC·VM·LB·K8s·MySQL·MemStore·CR·Monitoring **전용 역할이 없어 유일한 조회 통로** |
| Secrets Manager 매니저 | `DATABASE_URL`·LLM 키 등록. 리더는 조회만 |
| **KMS 사용자** | ★**리더만으론 시크릿 값을 못 읽음.** 등록은 되는데 확인이 안 됨 |
| Object Storage 매니저 | 미디어 2.4GB 이전 |
| Alert Center 매니저 | `catchap-monitoring` 흡수 |
| Codeflow 매니저 | CI. ★매니저만이면 PR 리뷰어를 못 고르는데 **리더가 함께 있어 해결** |

★ **`프로젝트 멤버`를 요청하지 않는 이유** — 멤버면 다른 조 자원까지 지울 수 있는데
**이 계정의 키는 서버 파일로 저장**됩니다. 변경 작업은 **사람 계정(콘솔 로그인)** 으로 하는 편이 안전합니다.
→ 대신 사장님 계정에 프로젝트 역할을 받는 쪽을 별도로 요청합니다.

# 4. 요청하지 않는 역할

| | 이유 |
|---|---|
| Cloud Trail 뷰어 · Billing | **조직 단위 역할**이라 프로젝트 서비스 계정에 못 붙음 |
| Monitoring 역할 | **없음.** `프로젝트 리더`로 열림 |
| Kubernetes 역할 | **없음.** 클러스터 내 RBAC |
| Container Registry 역할 | **없음.** 로그인은 IAM 키면 되고, push/pull은 **저장소별 `권한 설정`** — 이건 나중에 바꿀 수 있어 급하지 않음 |
| 각종 `뷰어` | 상위 역할이 자동 포함. 문서가 `리더 + 뷰어`를 중복으로 명시 |
| Kubeflow · DNS · File Storage · Pub/Sub | 안 씀 |

# 5. 검증 계획 (계정 받은 직후)

```
1. catchap-ops 키로 VPC·인스턴스·LB·K8s 조회    → 프로젝트 리더가 실제로 여는 범위
2. catchap-ops 키로 시크릿 등록 후 되읽기        → 매니저 + KMS 사용자 조합 확인
3. catchap-ops 키로 이미지 push 시도            → ★프로젝트 리더로 CR push가 되는지 (미검증)
4. catchap-deploy 키로 kubectl get pods         → clusterrolebinding 반영 확인
5. catchap-backend 키로 시크릿 4건·버킷 재확인   → 기존 계정이 여전히 동작하는지
```

★ 3번이 실패하면 **저장소별 `권한 설정`에 `catchap-ops` 추가**를 부탁드려야 한다.
문서: *"IAM 역할이 프로젝트 관리자 또는 프로젝트 멤버인 경우 자동으로 Container Registry 관리자
역할이 부여됩니다"* — **`프로젝트 리더`는 언급이 없다.**

**하나라도 실패하면 그 계정은 역할이 잘못 들어간 것이고, 재생성 요청이 필요합니다.**
그래서 기존 `catchap-backend`를 검증이 끝날 때까지 살려 둡니다.
