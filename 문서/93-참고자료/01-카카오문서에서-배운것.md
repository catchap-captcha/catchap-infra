# 1. Secrets Manager — ★뷰어는 시크릿 값을 못 읽는다

출처: [Secrets Manager 주요 개념](https://docs.kakaocloud.com/service/security/secrets-manager/secrets-manager-main)

> **Secrets Manager 뷰어(Viewer)**: 시크릿의 목록, 상태, 버전 정보 등 리소스를 조회할 수 있습니다.
> **단, 시크릿 값을 조회하거나**, 시크릿 생성 및 상태를 변경하는 등 암호화 또는 관리 작업은
> **수행할 수 없습니다.**

> **Secrets Manager 매니저(Manager)**: … 시크릿 생성, KMS 키 변경, 버전 생성, **시크릿 값 조회** 등
> KMS 키를 사용해 암호화·복호화를 하려면 **KMS 사용자(User) 역할 이상이 추가로 필요**합니다.

**결론**

```
앱이 시크릿 값을 읽으려면   Secrets Manager 매니저  +  KMS 사용자
KMS 뷰어는 암복호화 불가 → 못 씀
```

→ `catchap-backend`가 이미 이 조합입니다. **새 계정을 만들 필요가 없어졌습니다.**
→ 예비 계정(`catchap-app-b`) 계획 폐기.

# 2. Object Storage — ★IAM 역할만으로는 객체를 못 읽는다

출처: [Object Storage 주요 개념](https://docs.kakaocloud.com/service/storage/object-storage/object-storage-main)

> IAM에서 프로젝트 관리자·멤버·뷰어·Object Storage 매니저·뷰어 역할은
> **최초에 버킷에 대한 생성 및 목록 조회에 대한 권한만** 가질 수 있습니다.
> 다만 버킷을 생성하게 되면 **버킷 생성 시 초기 역할 정보에 따라 Object Storage 역할이 버킷에 부여**됩니다.

**2단 구조입니다.**

```
IAM 역할   →  버킷 "생성·목록조회" 까지만
버킷 역할   →  실제 객체 읽기·쓰기
```

**버킷 생성 시 자동 부여되는 역할**

| IAM 역할 | 받는 버킷 역할 | S3 ACL |
|---|---|---|
| 프로젝트 관리자 | `storage.admin` | FULL_CONTROL |
| 프로젝트 멤버 | `storage.editor` | READ+WRITE |
| **Object Storage 매니저** | **`storage.editor`** | READ+WRITE |
| Object Storage 뷰어 | `storage.viewer` | READ |

**버킷 역할 종류**

| 역할 | 권한 |
|---|---|
| `storage.admin` | 버킷 삭제·권한정책 포함 전체 |
| `storage.editor` | 버킷 수정 + 객체 전체 |
| **`storage.objectAdmin`** | **객체 생성·삭제·조회·수정만** ← 앱에 적합 |
| `storage.objectReader` | 객체 읽기만 |
| `storage.objectCreator` | 객체 생성만 |

→ **`catchap-backend`가 동작하는 이유** = 그 계정이 버킷을 직접 만들어 `storage.editor`를 자동으로 받음.
   **새 계정에는 그 혜택이 없어** 버킷 권한을 따로 줘야 합니다.

★ 부여 경로: `Object Storage → 버킷 → 권한 탭 → 역할 → [역할 추가]` (유형에 **서비스 계정** 선택 가능)
★ `ALLUSERGROUP`에 쓰기를 주면 **익명 사용자가 업로드·삭제** 가능 — 절대 쓰지 말 것

# 3. Kubernetes — 접속 방법과 인그레스

출처: [kubectl 제어 설정](https://docs.kakaocloud.com/service/container-pack/k8se/how-to-guides/k8se-kubectl) ·
[인그레스 컨트롤러 배포](https://docs.kakaocloud.com/service/container-pack/k8se/how-to-guides/k8se-ingress) ·
[로드 밸런서 생성 및 삭제](https://docs.kakaocloud.com/service/container-pack/k8se/how-to-guides/k8se-create-delete-lb)

## 접속 구조

```
1. kubectl 설치
2. kubeconfig 다운로드              콘솔 [kubeconfig 파일] 버튼
3. kic-iam-auth 인증 클라이언트      카카오클라우드 전용 실행파일 (OS별)
4. IAM 액세스 키 발급
5. kubeconfig 의 users > user > exec > env 에 입력
     OS_AUTH_URL   https://iam.kakaocloud.com/identity/v3
     OS_AUTH_TYPE  v3applicationcredential
     OS_APPLICATION_CREDENTIAL_ID / SECRET
     OS_REGION_NAME  kr-central-2
```

★ **우리가 apiserver에 IAM 토큰으로 인증됐던 이유가 이것입니다.**
   `kic-iam-auth`가 하는 일을 우리가 API로 직접 한 셈입니다.
★ kubeconfig에는 **서버 주소 + CA 인증서**가 들어 있습니다. 주소는 알아냈고 CA만 없습니다.

## 인그레스 — ★`hostNetwork: true` 가 필수

> 현재 Kubernetes Engine 서비스에서는 **Admission Webhook을 지원하지 않습니다.**
> Admission Webhook 설정된 서비스를 배포하려면 **`hostNetwork: true` 설정이 필요합니다.**

카카오클라우드가 그 설정을 넣은 커스텀 YAML을 제공합니다.

```bash
kubectl create namespace ingress-nginx      # 먼저 만들어야 함(안 그러면 배포 실패)
kubectl apply -f https://raw.githubusercontent.com/kakaoenterprise/kakaocloud-tutorials/refs/heads/k8se-public-guides/controller-v1.12.1/deploy.yaml
```

★ **인그레스 컨트롤러는 카카오클라우드가 지원하지 않고 선택·운영이 우리 재량**이라고 명시.

## ★인그레스를 배포하면 로드밸런서가 새로 생긴다

> 인그레스 컨트롤러 YAML을 배포하면 **인그레스 컨트롤러 서비스를 위한 로드 밸런서가 함께 생성**됩니다.

```
service.beta.kubernetes.io/openstack-internal-load-balancer
  true (기본)  →  프라이빗 IP 로드밸런서
  false        →  퍼블릭 IP 로드밸런서
```

**우리는 지금 `catchap-lb-2a`을 그대로 쓰는 쪽이 낫습니다** — 거기에 우리 SAN 인증서가 이미 붙어 있고,
새 LB에 인증서를 붙이는 건 우리 권한 밖입니다. `hostNetwork`면 노드 포트를 직접 쓰므로
지금 LB 대상그룹이 노드를 가리키면 그대로 동작합니다.

★ 다중 AZ 클러스터는 **노드풀이 1개 AZ에만 있어도 로드밸런서가 모든 AZ에 생성**됩니다.

## 쿼터

```
클러스터  프로젝트별 10   ·  노드 풀  클러스터별 20   ·  노드  클러스터별 100
```

★ **자동 생성 리소스(인스턴스·볼륨·보안그룹)의 프로젝트 쿼터가 초과되면 노드를 못 만듭니다.**
   3개 팀이 함께 쓰므로 노드를 늘릴 때 프로젝트 전체 여유를 먼저 봐야 합니다.

# 4. Load Balancer — 프로토콜 조합 규칙

출처: [대상 그룹](https://docs.kakaocloud.com/service/networking/lb/main/lb-target-group)

| 로드밸런서 | 리스너 프로토콜 | **대상 그룹 프로토콜** |
|---|---|---|
| **ALB** | HTTP | HTTP, PROXY |
| **ALB** | **HTTPS** | **HTTP** ← 이것만 |
| NLB | TCP | HTTP, HTTPS, TCP, PROXY |

★ 우리 대상 그룹이 `HTTP`인 것은 **규격상 맞는 설정**입니다.
★ 그러므로 **LB가 TLS를 종료하고 노드로는 평문 HTTP**를 보냅니다.
   → 대상 포트가 `443`이면 인그레스가 TLS를 기대해 어긋납니다. **`80`이 맞습니다.**

**운영 상태 정의**

```
Online     대상이 모두 Healthy
Degraded   하나 이상 Error
Offline    생성 직후, 첫 상태 확인 전
```

# 8. ★VPC — 퍼블릭/프라이빗은 이름이 아니라 라우팅 테이블이 정한다 (해소)

출처: [라우팅 테이블](https://docs.kakaocloud.com/service/networking/vpc/main/vpc-route-table)

> 로컬 외 모든 IPv4 트래픽(`0.0.0.0/0`)에 대해 인터넷 게이트웨이를 대상으로 설정할 수 있습니다.
> **인터넷 게이트웨이를 포함한 라우팅 테이블에 연결된 서브넷을 퍼블릭 서브넷이라고 합니다.**

★ **우리 서브넷은 이름만 private 이었고 실제로는 전부 퍼블릭 서브넷입니다.**
(★0804 에 `catchap-jump-2a` · `catchap-core-2a` · `catchap-core-2b` · `catchap-gpu-2a` 로 이름을 고쳤습니다.)
그래서 NAT 인스턴스가 필요 없습니다. 한때 "문서와 어긋난다"고 적었던 것은
**인터넷 게이트웨이 문서만 읽고 라우팅 테이블 문서를 안 읽어서** 생긴 오판이었습니다.

**교훈 — 한 문서에서 모순이 보이면 결론 내기 전에 옆 문서를 마저 읽는다.**
같은 서비스의 문서 여러 개가 정의를 나눠 갖고 있습니다.

## NAT — 카카오클라우드엔 관리형 NAT 게이트웨이가 없다

AWS의 `NAT Gateway`에 해당하는 별도 서비스가 없습니다. 문서에는 **`NAT 인스턴스`** 뿐입니다.
즉 **VM 하나를 띄워 NAT 장비로 만드는 방식**(AWS의 옛 NAT Instance 패턴)입니다.
출처: [부록. NAT 인스턴스 사용](https://docs.kakaocloud.com/service/networking/vpc/how-to-guides/vpc-appx-1)

```
퍼블릭 서브넷에 VM 생성 + 퍼블릭 IP
  → ip_forward=1 · iptables MASQUERADE
  → 콘솔에서 "패킷 송신 허용 IP"에 0.0.0.0/0  (AWS의 source/dest check 끄기)
  → 프라이빗 서브넷 라우팅 테이블에 0.0.0.0/0 → 인스턴스
```

★ 카카오클라우드 고유 개념: **패킷 송신 허용 IP**.
기본적으로 네트워크 인터페이스는 자기 앞으로 온 트래픽만 받습니다.
NAT처럼 남의 트래픽을 포워딩하려면 이 값을 열어 줘야 합니다.

## 남은 미세한 의문

인터넷 게이트웨이 문서는 "퍼블릭 IP가 연결되어야 인터넷에 통신할 수 있다"고 하는데,
VM2는 퍼블릭 IP 없이도 `210.109.82.130`으로 나갑니다. 경로에 `100.64.0.0/10`이 보이므로
**IGW가 공유 SNAT을 해 주는 것**으로 보입니다. AWS와 다른 점입니다(AWS는 퍼블릭 IP 없으면 안 나감).

# 10. Codeflow — 러너를 우리가 직접 띄워야 한다

출처: [주요 개념](https://docs.kakaocloud.com/service/dev-tools/codeflow/codeflow-main) ·
[워크플로우 관리](https://docs.kakaocloud.com/service/dev-tools/codeflow/how-to-guides/codeflow-workflow) ·
[액션 설정](https://docs.kakaocloud.com/service/dev-tools/codeflow/how-to-guides/codeflow-action)

★ **관리형 러너가 없습니다. `Self-hosted runner`만 지원**합니다.
→ CI를 돌리려면 우리 VM 하나(예: VM3)를 러너로 등록해야 합니다. 실행 방식은 2가지 —
**실행 파일 방식**(수동 등록·별도 실행)과 **컨테이너 방식**(자동 등록·실행 시 자동 수행).

```
워크플로우 파일   기본 브랜치의 .codeflow/workflows/*.yml
트리거           push · workflow_dispatch  ← 이 둘뿐 (PR 트리거 없음)
리포지토리 토큰   무기한·재발급 불가·조회 권한자 전원이 볼 수 있음
                ※ 실제 인증은 IAM 액세스 키. 토큰은 러너↔리포지토리 매핑용 식별자일 뿐
```

★ **`Codeflow 매니저`만 주면 PR 리뷰어를 못 고릅니다** — 사용자 목록 조회에
`프로젝트 리더` 이상 또는 `IAM 프로젝트 관리자`가 추가로 필요합니다.

# 11. ★KMS 접근 제어 — 우리 `kms11` 문제의 근거

출처: [KMS 주요 개념](https://docs.kakaocloud.com/service/security/kms/kms-main)

> **접근 제어 사용**: 허용 대상을 설정할 수 있습니다. 설정 가능한 대상은 동일 프로젝트 내
> 사용자, 그룹, **서비스 계정**, 서비스 에이전트 계정이며, 실제 사용 권한은 해당 IAM 역할을 따릅니다.
> **접근 제어 미사용**: 키 사용에 필요한 **IAM 역할을 가진 대상은** 해당 키를 사용할 수 있습니다.

★ 즉 접근 제어가 켜진 키는 **허용 목록 등재 + IAM 역할** 둘 다 필요합니다.
콘솔 확인 결과 **`kms11`은 켜짐, `kms12`는 꺼짐**이고 프로덕션 시크릿 4건이 전부 `kms11`입니다.
→ 서비스 계정을 새로 만들면 반드시 `kms11` 허용 대상에 추가해야 합니다.

# 13. Cloud Trail — 90일치만, 조직 이벤트는 조직 역할이 있어야

출처: [주요 개념](https://docs.kakaocloud.com/service/management/cloud-trail/cloud-trail-main)

- 이벤트는 **최근 90일**만 조회. 장기 보관은 별도 로그 저장 기능
- **조회 작업도 이벤트로 기록됩니다** — 우리가 콘솔을 훑은 것도 전부 남습니다
- 조회 범위: `조직 관리자`·`트레일 뷰어`만 **조직 이벤트**를 봄.
  프로젝트 역할(관리자/멤버/리더)은 **프로젝트 이벤트만**
- ★ 사장님 계정은 **조직 관리자**라 조직 이벤트가 보입니다. 다만 프로젝트 역할이 없어 프로젝트 이벤트는 제한적입니다

# 문서 경로 규칙 (다음에 찾을 때)

주소를 추측하면 계속 틀립니다. **서비스별 실제 경로는 이렇습니다.**

```
Kubernetes Engine    /service/container-pack/k8se       ← kubernetes-engine 아님
Container Registry   /service/container-pack/cr
Object Storage       /service/storage/object-storage
MySQL / MemStore     /service/data-store/mysql · /memstore
VPC / LB / DNS       /service/networking/vpc · /lb · /dns
Secrets Manager      /service/security/secrets-manager
KMS                  /service/security/kms
IAM / Monitoring     /service/management/iam · /monitoring
Cloud Trail          /service/management/cloud-trail
Codeflow/Deployflow  /service/dev-tools/codeflow · /deployflow
```

★ **`주요 개념` 문서의 파일명 규칙이 서비스마다 다릅니다.** KMS는 `/kms/kms-main`인데
VPC는 `/vpc/main/vpc-route-table`처럼 `main/` 폴더가 낍니다. **주소를 짓지 말고 목차 페이지에서 링크를 뽑을 것.**

**각 서비스의 `주요 개념` 문서에 역할별 상세 권한이 적혀 있습니다.**
`IAM 역할` 문서만 보면 안 나옵니다 — 오늘 그것 때문에 헛돌았습니다.
