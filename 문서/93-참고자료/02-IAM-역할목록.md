| 프로젝트 관리자 + IAM 프로젝트 관리자 | ❌ 중복 |

# 2-B. ★★공식 문서가 서로 어긋난다 — Container Registry 역할 (2026-08-03 확인)

이미지 push 권한을 정하려다 **공식 문서 두 곳이 반대로 말하는 것**을 찾았다.

| 문서 | 뭐라고 하나 |
|---|---|
| [이미지 관리](https://docs.kakaocloud.com/service/container-pack/cr/how-to-guides/cr-manage-image) | > "이미지 Push는 **Container Registry 관리자**와 프로젝트 멤버 권한이 있어야 할 수 있습니다." |
| [서비스 역할](https://docs.kakaocloud.com/service/management/iam/roles/service-roles) | ★Container Registry가 **목록에 없다.** Billing·Object Storage·File Storage·Codeflow·Kubeflow·Cloud Trail·Alert Center·DNS·Pub/Sub·KMS·Secrets Manager·IAM 뿐 |

**어느 쪽이 맞나 — 콘솔이 판정한다.**

```
콘솔 IAM → 역할 화면 (2026-07-29 직접 확인)   37개
   조직 10  +  프로젝트 27
   프로젝트 27 = 공통 3 (관리자·멤버·리더) + 서비스 24

서비스 24개를 전수 대조   →  ★Container Registry 없음
역할이 있는 서비스: alert-center · codeflow · deployflow · dns · file-store ·
                  identity · kms · kubeflow · object-store · pubsub · secrets-manager
```

살아 있는 토큰으로도 확인했다 — `catchap-ops` 가 실제로 지닌 역할 11개 어디에도
Container Registry 관련 항목이 없다.

★**결론: `Container Registry 관리자` 라는 역할은 콘솔에 없다.** how-to 문서의 표현이
앞서 나간 것으로 보인다(IAM 개편 공지도 *"앞으로 서비스별 역할 체계를 더 세분화해
나갈 계획"* 이라고만 한다).

★**그래서 push 를 좁은 권한으로 줄 방법이 없다.**

```
프로젝트 관리자 / 프로젝트 멤버   사람·서비스 계정 다 가능   ★2조 자원까지 삭제 가능
저장소별 리포지토리 멤버          ★사람 계정만              서비스 계정 불가
```

⚠️**다만 문서에 이름이 나온 이상, 콘솔 역할 화면을 한 번 더 보는 게 좋다.**
0729 이후에 추가됐을 수도 있다. 서비스 계정 만들 때 역할 고르는 화면에
`Container Registry` 가 보이면 **그것만 주면 된다** — 그게 가장 좁다.

| **프로젝트 리더 + 서비스 매니저** | **적합.** 전체는 조회만, 특정 서비스만 운영 위임 |
| 프로젝트 관리자 + 서비스 뷰어 | ❌ **중복.** 관리자가 이미 다 포함. 관리자만 주면 됨 |
| 프로젝트 리더 + 서비스 뷰어 | ❌ **중복.** 리더가 이미 조회를 다 포함. 리더만 주면 됨 |

★ 이 표가 우리 계정 설계를 그대로 뒷받침합니다 — **조회 계정엔 리더만, 운영 계정엔 리더 + 필요한 매니저.**

# 6. 하위 역할 포함 관계

상위 역할을 주면 하위는 자동 포함이라 **따로 줄 필요가 없습니다.**

```
KMS 매니저          →  KMS 사용자, KMS 뷰어
KMS 사용자          →  KMS 뷰어
Secrets Manager 매니저 →  Secrets Manager 뷰어
Object Storage 매니저  →  Object Storage 뷰어
Alert Center 매니저   →  Alert Center 뷰어
IAM 프로젝트 관리자   →  IAM 프로젝트 뷰어
DNS·Codeflow·File Storage·Pub/Sub 매니저 → 각 뷰어
```

# 7. ★서비스 계정의 역할 변경 — 공식 문서 확인 결과 (2026-07-30)

## 결론

**공식 문서에 "변경할 수 없다"는 문장은 없습니다.**
대신 **변경하는 절차가 어디에도 없고**, 역할 변경 문서가 다루는 대상에 서비스 계정이 빠져 있습니다.
→ **"금지 명시"가 아니라 "절차 부재"로 뒷받침되는 결론**이며, 멘토님 말씀과 일치합니다.

## 근거 1 — 서비스 계정 문서에 역할 변경 절차가 없다

출처: [서비스 계정 생성 및 관리](https://docs.kakaocloud.com/service/management/iam/how-to-guides/iam-manage-service-account)
캡처 `20-카카오문서/IAM-02-서비스계정생성및관리.png`

문서의 목차가 이게 전부입니다.

```
서비스 계정 기능별 관리 권한 · 조회 · 생성 · 상태 변경 · 삭제
자격 증명 발급 · 자격 증명 삭제 · 서비스 에이전트 조회
```

- **역할은 `생성` 절차 안에서만 정해집니다** — 생성 팝업의 `프로젝트 역할` 필드
- **`상태 변경`은 `사용/미사용` 전환일 뿐**입니다. 역할과 무관합니다
- 권한 표에는 *"서비스 계정 생성, **수정**, 삭제"* 라는 표현이 있으나,
  **문서화된 "수정" 절차는 상태 변경뿐**입니다

## 근거 2 — 역할 변경 문서의 대상에 서비스 계정이 없다

출처: [역할 관리](https://docs.kakaocloud.com/service/management/iam/how-to-guides/iam-manage-role)
캡처 `20-카카오문서/IAM-03-역할관리-할당변경대상.png`

> **역할 할당 및 변경** — **사용자 또는 그룹**에 역할을 할당하거나 변경하는 작업은 …
> → Management > IAM > **사용자 / 그룹 / 프로젝트**
> → 콘솔 대시보드 > Project Management > **사용자 / 그룹**

**`서비스 계정`이 대상에 없습니다.** `역할 제거` 절도 마찬가지로 사용자·그룹만 다룹니다.

## 근거 3 — 그룹으로 우회할 수도 없다

> **서비스 계정은 그룹에 소속될 수 없습니다.** IAM 사용자 계정과 달리, 서비스 계정은 개별적으로
> 생성되며, 필요한 IAM 역할은 **서비스 계정 단위로 직접 할당**해야 합니다.

사용자라면 그룹 역할을 바꿔 우회할 수 있지만, 서비스 계정은 그 길도 막혀 있습니다.

## 근거 4 — 콘솔

서비스 계정 상세의 `프로젝트 역할` 표에 **추가·수정 버튼이 없습니다.**
(표 옆 `설정`은 페이지당 개수 같은 표 표시 설정입니다)
다만 **우리 계정은 프로젝트 역할이 없어 버튼이 비활성**이므로, 콘솔만으로는 확정 근거가 못 됩니다.

## ★반대로 사람(사용자) 계정은 언제든 바뀝니다

`IAM → 사용자 → [프로젝트 역할] → [역할 수정]` 화면이 실제로 열리고 `[수정]` 버튼도 활성입니다.
캡처 `01-IAM-계정-권한/20260729-18a~18f`.
→ **불변인 것은 서비스 계정뿐입니다.** 사람 계정은 최소로 받고 나중에 늘려도 됩니다.

## 그래서 우리 방침

**명세가 한 번에 맞아야 합니다.** 틀리면 계정 재생성이고, 재생성하면
**`kms11` 접근 명단과 버킷 권한을 다시 설정**해야 합니다(그게 진짜 비용입니다).
→ 모자란 것보다 남는 편으로 잡고, 동작 중인 계정을 먼저 지우지 않습니다.
[00-서비스계정-명세.md](../93-참고자료/03-서비스계정-명세.md) 참고.

**아직 100% 확정은 아닙니다** — `프로젝트 관리자` 권한을 가진 사람이 실제 화면을 봐야 끝납니다.
다만 우리 명세는 어느 쪽이든 안전하게 설계했습니다.
